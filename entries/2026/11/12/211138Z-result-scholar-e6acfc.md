## Touch points: Endo (endojs/endo-but-for-bots @ llm)

Design paths below are on `llm` as of the local bare clone (`3aa902d0`, 2026-09-28), which may lag the live branch.

1. **The daemon git capability and remotes (git-integration arc).** `designs/daemon-git-remotes.md` already separates CapTP control from the bulk data plane: "git packfile bytes travel on the bounded HTTPS data plane outside CapTP messages". Pando's `packfile-uri` model (§ *Line-rate fetch and clone*) pushes the same idea further: the negotiation answer is small and names immutable packs, and the bytes come from a cache. A future `GitRemote` serving side, or a daemon-hosted remote, could give out attenuated, cacheable pack URIs (bearer tokens that designate a specific immutable pack, which the garden treats as ocap-consistent) instead of streaming every pack through one connection. Pando's trunk-only advertisement and explicit haves (§ *Scaling pushes*, § *Contributing back*) also matter to `GitRemote.push` and the force-with-lease push tier merged in #705. A server that advertises only trunk makes the client resend a whole stacked branch on every push. Endo's frozen-base stacked PRs fit that pattern exactly, so a Pando-like remote would make stacked-PR pushes larger.
2. **`designs/endor-git-bindings.md` (libgit2 vs `gix`) and the minion.town git-remote prior-art section it cites.** Pando shows that a server can be a pure pack-selector that never unpacks pushes into a local repository (§ *Causal consistency*, last paragraphs). That matters for any Endor or minion.town server half: the pluggable-object-database seam can be "pack blobs + ref-version metadata" rather than a full ODB. The upstream client fixes (parallel pack download and indexing, resuming interrupted downloads) are worth tracking whichever binding wins, because both libgit2 and `gix` have to interoperate with `packfile-uri` servers.
3. **Daemon storage, CAS, and the compare-and-swap identity direction.** `designs/daemon-cas-management.md` (the Rust `ContentStore`: SHA-256, retain/release, mark/sweep GC) and the storage-CAS draft #1358 are the nearest Endo analogs. Three Pando lessons carry over:
   - Pando never GCs packs. It compacts them into LSM covers and keeps every level for different readers (§ *Compaction*). That is a counterpoint to mark/sweep GC as the only space policy for an append-heavy CAS.
   - The single contended key is a ref pointer guarded by CAS, with everything else immutable and append-only (§ *Scaling pushes*). This matches the maintainer's 2026-11-03 direction: CAS on an opaque identity rather than an exposed hash, with the root pointer as the only mutable cell.
   - Per-ref serializability with no global snapshot (§ *Causal consistency*) argues against requiring a cross-directory atomic snapshot in the fs CAS design (#1586, `designs/exo-git-follow-root-advancement.md`). That design already separates per-stage root sequences in the same spirit.
4. **The npm-CAS registry (`designs/endor-npm-registry-proxy.md`, `designs/npm-registry-as-directory-tree.md`).** The analog is Express's regional pack cache with consistent hashing and more than 99% hit rates, which serves immutable content-addressed artifacts with little computation (§ *Line-rate fetch*, § *Deploying Pando*). So is the proxy-first migration: a read/write-through proxy that deduplicates and combines requests while warming the cache (§ *Deploying Pando*). The registry proxy is already shaped this way (fetch, CAS-ingest, `--offline` replay). Pando adds request coalescing for concurrent identical fetches, which matters once many workers resolve the same dependency tree at the same time.
5. **CI and PR flow.** The motivation section describes the load Endo's fleet creates: "each push can set several jobs fetching the same commit" (§ *Why we needed a new source control system*). Endo's frozen-base weaves trigger full-CI reselection, and every weave of a stacked PR causes the CI fan-out Pando optimizes for. Endo runs on GitHub, so this changes no code. The useful observation is that minimizing redundant fetches (shallow or blobless CI checkouts, shared caches) matters more than push size. The verification recipe (§ *Building Pando*) is the other transferable piece: a conformance suite agents test against, deterministic simulation harnesses, and agent-written TLA+/Lean. This matches the ironhorse and test262 conformance practice and supports formal-model work on the daemon's formula and CAS invariants.

## Touch points: Git itself, and the garden's shared-repo, worktree, and journal practices

1. **The journal2 CAS is the WAL pattern the post rejects (§ *Existing distributed Git service patterns*, WAL).** Every garden producer CAS-pushes to one shared ref (`origin/journal2`) and on conflict re-reads the intervening commits and retries (`commit_and_push`, `land-journal-edit.sh`, concept `journal-ref-rmw-cas`). The post's diagnosis fits the garden: "even pushes to unrelated branches require updating the same manifest", so CAS round-trip time caps the publish rate, and replicas that must read and index every pack fall behind. `designs/journal-contention-watch.md` measures exactly this pressure. Pando's fix is to make the ref the unit of serialization, so unrelated writes never contend (§ *Causal consistency*, § *Scaling pushes*). `designs/journal3-and-shared-journal-reads.md` (draft, 2026-11-10) points the same way by splitting append-only `tada` and ledger data onto their own branches. The post suggests taking that further: per-domain refs (board, inbox, entries, library) could CAS independently, at the cost of losing a single point-in-time view across them. The post's argument that consumers care only about per-ref order is the evidence to weigh when deciding whether the board needs that view.
2. **Readers carrying the whole branch (§ *Compaction*, § *Line-rate fetch*).** journal3's motivating numbers (131 GB of per-job journal clones; a 605 MiB pack every reader carries) are the read-side cost Pando avoids by serving prebuilt packs. The garden's mitigations are already close to Pando's approach: shallow, borrowed-object staging clones (alternates), shared read-only bind mounts, and the `GARDEN_FETCH_MAX_AGE` freshness window plus the per-repo fetch mutex in `designs/host-local-git-repo-locks.md`. The freshness window is the garden's form of Pando's request deduplication (§ *Deploying Pando*): concurrent identical fetches collapse into one.
3. **Repository maintenance (§ *Compaction and time to first byte*).** The root-repo guard exists because a failed `git gc` leaves a `gc.log` that disables auto-maintenance permanently (`designs/root-repo-guard.md`, the sysop `maintain` op). Pando avoids repack/GC on the serving path entirely by compacting in the background into geometric levels. Stock Git offers a partial version of this for the garden's shared root repo: `git maintenance` with the incremental-repack and geometric (`repack --geometric`) strategies, plus commit-graph and multi-pack-index. These would replace periodic full `gc` with cheap background compaction and keep the shared object store maintainable without the gc.log failure mode. That suggests a follow-up design.
4. **Explicit haves and `--force-with-lease` (§ *Contributing back*).** The garden's weaver and frozen-base flow, and the push tier in Endo #705, rely on `--force-with-lease`. OpenAI's explicit-haves extension decouples "check that the branch hasn't moved" from "build the pack against what". If it lands upstream, it would let lease-guarded force pushes of rebased PR heads send packs built against the base branch alone. On GitHub that changes nothing; it matters only for a self-hosted remote.
5. **Protocol features worth knowing for any garden-hosted remote.** `packfile-uri` (protocol v2), the trunk-only advertisement trick, and the cost of the ref advertisement itself ("with millions of branches the advertisement alone can exceed 100 MiB", § *Scaling pushes*). The garden's job refs and frozen `<base>-<sha>` branches accumulate on GitHub forks. Protocol v2 `ls-refs` prefix filtering already keeps fetches cheap, but unbounded frozen-base refs are a slow-growing advertisement cost for any v0 client or full mirror.
6. **Agent-scale build practice (§ *Building Pando*, § *Deploying Pando*).** A 10-week, agent-implemented, single-designer build; migration through a CLI wrapper plus skills that teach agents the new system. This is the garden's own operating model (wrapped `git`/`gh` in `scripts/jobs/bin`, skills as the migration vehicle), confirmed independently.
