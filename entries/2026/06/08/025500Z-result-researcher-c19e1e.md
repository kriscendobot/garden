- **The "replace vs extend" reframing at inline 363**: the current design body (Design Decision 7) says *"Extends, never replaces, the existing form-based provisioning"*; the maintainer's inline 363 says *"my intention is that this should replace lal fae form provisioning. Provisioning becomes a dependency of the Chat application but not a dependency of the daemon"*. The designer rewrites Design Decision 7 to acknowledge the directive: provisioning logic moves into Chat (which installs the provisioning capabilities into the root host agent); the lal-fae *daemon-side substrate* (the manager-worker-split, the form-request / value-message protocols) remains; the *daemon's role as the provisioning entry point* retires. The rewrite preserves the inbox-as-durable-config-store property by making Chat replay the inbox on first launch and provision via root host capabilities.
- **The `@root` endowment's scope**: inline 363 frames `@root` as universal (*"add an `@root` endowment to all Endo hosts so the user can enter from below"*). The designer surfaces whether `@root` is preformulated as a `Specials` entry analogous to `@apps`, or whether the chat client installs it lazily on first-launch via the self-provisioning bootstrap pattern. The familiar-bundled-agents §three-option-powers-analysis is the parallel rubric.
- **The deferred complication at line 484**: the current design's Open Question 2 (*Provider-key recovery and rotation*) is what line 484 absorbs into a separate design. The placeholder design's slug name and scope (key recovery only, or also key rotation and the gateway-key-recovery parallel?) is the maintainer's call; the designer drafts the dispatch prompt's task statement and surfaces it for the steward to relay.
