Two procedural observations from the PR #238 fixer engagement,
offered as candidate landings. Both are single-engagement evidence,
so they fit the "Notes from the field" threshold rather than a new
rule.

**1. yarn-lock-separate-commit: rebase typically conflicts on the
yarn.lock commit.**

When a PR carries `chore: Update yarn.lock` and the base branch has
moved (any other PR that touched dependencies has landed in the
interim), `git rebase` will conflict on `yarn.lock`. The procedure
that worked here:

```sh
git rebase origin/<base>
# conflict on yarn.lock
git rebase --skip                     # drop the old lockfile commit
# apply review-feedback fixes on top
npx corepack yarn install             # regenerate lockfile against new base
git add yarn.lock
git commit -m "chore: Update yarn.lock"
```

The skill already says the separate-commit form is "regenerated by
re-running `npx corepack yarn install`" but does not call out the
rebase-conflict-and-skip flow. Worth a one-line "Notes from the
field" on `skills/yarn-lock-separate-commit/SKILL.md` pointing at the
skip-then-regenerate pattern.

**2. review-feedback-followup-commits: amending an existing commit's
author header is fine when only the author changes.**

The skill's core rule says "do not amend." This engagement's PR
#238 included a kriskowal review item asking to reset the feat
commit's author to @dckc (the upstream playground PR's original
author). I treated this as a permitted amend, since:

- The tree did not change; reviewers see byte-identical content.
- The author-header amend was the maintainer's explicit ask, on a
  reviewed commit, in the same review that authorized the push.

This is a different case from amending content (which forces the
reviewer to re-diff and is the rule's actual target). A clarifying
half-sentence on the existing "Add a follow-up commit on top; do not
amend" bullet would resolve the apparent contradiction:

> Amend only the just-rebased tip when nobody else has pushed since,
> _or when a maintainer review explicitly asks for an
> author-only / message-only amend that does not change the tree._

Not pre-empting. Both candidates are scoped tightly to existing
skill files. If the threshold of "one vivid observation" is met,
landing them is mechanical.
