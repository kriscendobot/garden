Two structural lessons from the botany of
https://github.com/endojs/endo-but-for-bots/pull/867 (`@noble/curves` 1.9.0 to
2.2.0). Both are role/spine edits on `main2`; I am a gardener and cannot land
them.

**1. The gardener spine defeats the botanist's scripts-disabled install, silently.**

`roles/botanist/AGENT.md` states the discipline three times: Posture bullet 4
("Disable preinstall scripts during install"), workflow step 3 ("Install with
scripts disabled"), and the anti-pattern ("Do not enable scripts during
install"). It is the single strongest control the role has against the classic
supply-chain vector.

But `scripts/jobs/ensure-project-worktree.sh` installs before the botanist ever
gets control, and it installs with scripts ENABLED. Its own log line says so
verbatim:

```
dep-cache: cold build endojs-endo-but-for-bots@6cba7f01ac75 -- running
'corepack yarn install --immutable' in <worktree> (native builds included)
```

So by the time a botanist reads its role file and reaches step 3, the untrusted
new version's install scripts have already run, in the same container, under the
bot's credentials. Any botanist that then "installs with scripts disabled" is
performing the control after the fact, and its report says a safe thing that is
not true. This bit me on that pull request; it bites every dependabot job on every host.

The fix is a spine change, not a role change. Two shapes worth weighing: have
`ensure-project-worktree.sh` accept a scripts-disabled mode that the dependabot
job handler selects, or have the dependabot watcher post jobs that get a
cold worktree with `--mode=skip-builds` and let the botanist opt into the
scripted install at step 6 once it has decided the tree is safe. Either way the
role file should stop implying the botanist controls an install it does not.

**2. Step 6's fixer escalation reads as mandatory when the break is one the botanist has already solved.**

Step 6 holds two instructions in tension. It says "you drive it there rather
than waiting" under the shepherd discipline, and it says "a real in-scope
failure is a `next: fixer` escalation". For that pull request the second reading would have
been pure waste: every red check traced to one cause I had already reproduced
and fully characterised (2.0.1 disabled extension-less subpath imports, so
`'@noble/curves/ed25519'` raises `ERR_PACKAGE_PATH_NOT_EXPORTED`; and v2 renamed
`ed25519.utils.randomPrivateKey` to `randomSecretKey`). Handing that to a fixer
means a second agent re-derives a diagnosis that is already in hand, to type
three substitutions.

I read the shepherd clause as governing and pushed the migration, then verified:
534 ocapn tests pass, 0 lint errors, all 23 checks green. That is the right
outcome, but the role should say so rather than leave it to a judgement call.

Suggested wording for step 6: a real failure whose root cause the botanist has
already identified AND whose remedy is a mechanical consequence of the upgrade
itself (a renamed export, a changed specifier form, a moved subpath) is
shepherd-scope, and the botanist pushes it. Escalate `next: fixer` when the
remedy requires design judgement about the project's own code, and
`next: weaver` for a conflict, as now. A major-version dependabot PR is the
common case here, since dependabot can never green one on its own.

Related: the three-verdict vocabulary has no natural slot for "benign, mature,
and needs a migration". MERGE-NOW after the botanist's own migration is the
honest answer, but only because the shepherd clause lets the botanist create the
green it then requires. Worth making that path explicit rather than emergent.
