# Self-improvement: the fleet built @endo/sha256 twice (endojs/endo-but-for-bots#836 and endojs/endo-but-for-bots#903)

**Structural proposal — for the liaison to weigh, not to land in this job.**

## What happened

Two independent PRs implemented platform-neutral `@endo/sha256` on
endojs/endo-but-for-bots:

- **endojs/endo-but-for-bots#836** ("feat: add platform-neutral @endo/sha256"), created 2026-07-22
  against the **frozen** base `llm-bfc91f5`. Merged 2026-08-06 — but only into
  that frozen snapshot, so `packages/sha256` exists on `llm-bfc91f5` and is
  **absent from live `llm`**.
- **endojs/endo-but-for-bots#903** ("feat(sha256): platform-neutral SHA-256, unblocking the XS daemon
  bundle"), created 2026-08-01 against **live `llm`** — a from-scratch
  reimplementation of the same package plus the daemon/rust integration endojs/endo-but-for-bots#836
  never carried.

Same public API (`sha256`, `sha256Into`; xs/browser/node/default conditions), so
this was duplicated work, not a design fork. ~10 days and two full
review-and-CI cycles were spent building the same package twice.

## Why it happened — the frozen-base blind spot is causal

A producer scoping "does `@endo/sha256` exist yet?" reads **live `llm`**, where
the answer is correctly *no* — because endojs/endo-but-for-bots#836's merge landed on the frozen
`llm-bfc91f5`, invisible from `llm`. The second producer had no way to see the
first PR's merged content by reading the base it was targeting. Nothing in the
scoping step looks sideways at **open or recently-merged PRs for the same
package name** across sibling bases.

This is not isolated. `llm-bfc91f5` currently strands **three** PRs (endojs/endo-but-for-bots#836 merged,
endojs/endo-but-for-bots#888, endojs/endo-but-for-bots#943) at 254 commits behind live `llm`, and the fleet has separately hit
frozen-base drift on endojs/endo-but-for-bots#621, endojs/endo-but-for-bots#503, endojs/endo-but-for-bots#475, and endojs/endo-but-for-bots#910. The frozen-base pattern
routinely hides landed work from producers reading the live branch.

## Proposed fix (two candidates, both producer-side, neither landed here)

1. **Supersession / new-package check at build-scoping time.** Before a producer
   starts a brand-new package or feature, query open + recently-merged PRs
   fleet-wide for the same package name / changeset slug (`gh pr list --search`
   on the package path or `.changeset` name), across **all** bases, not just the
   target. A hit surfaces "this may already be built on base X" for a human/
   liaison decision before work starts. Cheapest high-value guard: the collision
   here would have been caught by a single search on `packages/sha256`.

2. **A policy on merging into frozen bases.** Merging a *new package* into a
   frozen base guarantees it is invisible to live-branch producers until the
   frozen stack rebases forward (254 commits later, here). Candidate rule:
   new packages / net-new features land on the **live** base; frozen bases take
   only fixes to work already on that base. At minimum, a merge into a frozen
   base should emit a fleet-visible note "package/feature X now exists on frozen
   base Y" so the next scoping read can find it.

Recommend (1) first — it is a narrow additive check at one point in the build
producer's flow, needs no policy change, and directly closes the blind spot that
produced this pair. (2) is the deeper fix but is a fleet-wide policy the
maintainer should rule on.
