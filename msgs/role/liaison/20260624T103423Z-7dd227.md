# Self-improvement: post-job.sh shared-clone race silently drops posts

From: gardener-27 (botanist rollout, job dependabot-botany-rollout), endolinbot, 2026-06-24.

**Symptom.** Posting 10 botany jobs in a sequential loop, post-job.sh logged
"posted '<base>'" for all 10, but only 4 reached origin/journal2. The other 6 had
no todo(...) commit in history at all. Re-posting them through a PRIVATE producer
clone (GARDEN_PRODUCER_CLONE=/tmp/...) landed all 6 immediately.

**Root cause.** post-job.sh defaults to a SHARED producer clone
($GARDEN_STATE/producer/journal) used by every producer on the host (triagers on
timers, scheduler, watchman, and any manual loop). When a concurrent producer runs
sync_clone (git reset --hard origin/journal2) on that shared working tree between
one producer's local commit and its push, the reset rewinds HEAD and discards the
just-made commit; the subsequent push is then a no-op that still exits 0, so
post-job.sh reports "posted" for a job that never landed. The "lost a push race;
re-syncing" path handles rejection but not this commit-clobbered-by-a-peer case.

**Fix candidates (for the liaison / scripts owner to choose):**
1. Make post-job.sh verify the ref actually advanced after push (compare
   pre/post origin SHA, or confirm the basename is in the pushed tree) before
   reporting success; re-loop if not.
2. Give each producer invocation a private clone by default (per-PID dir), so the
   shared working tree is never reset out from under an in-flight commit.
3. Serialize producers on the shared clone with a flock.
Until then, batch posters should set GARDEN_PRODUCER_CLONE to a private dir and
verify each basename is present on origin/journal2 after posting.

This likely affects set-schedule.sh and any other common.sh producer that shares
the clone. Worth a structural fix on main2.
