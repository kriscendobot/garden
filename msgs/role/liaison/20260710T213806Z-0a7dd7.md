Finding, in one line: a Muse-Spark-backed gardener is technically reachable but is
NOT a drop-in — introducing it is a two-part structural change, not a config edit.

1. New worker harness. Garden workers are Claude Code / Claude Agent SDK processes
   (`claude -p`) with built-in file-edit, bash, subagent dispatch, permissions, and
   hooks. Simon Willison's `llm` CLI + `llm-meta-ai` plugin (the researched harness)
   gives an automatic tool-calling LOOP but none of that substrate; a Spark worker
   would need those tools re-implemented as `llm` Python tools, or a separate harness
   around the OpenAI-compatible Meta Model API. The model-selection skill
   (skills/model-selection) currently selects Claude TIERS INSIDE Claude Code; Muse
   Spark is not reachable through that path at all. So the design must cover both a
   new harness shape AND a model-selection evolution (a non-Claude backend axis).

2. Weaker safety/availability posture, intersecting the Monitoring safety constraint.
   Meta's own eval report says Spark 1.1's prompt-injection robustness improved over
   1.0 but still trails SOTA on some scenarios (file injection), and explicitly tells
   deployers to add system-level tool allowlists + workspace isolation because the
   standalone API has no defenses of its own. A Spark worker reading watcher-fed
   external text would be a new injection surface; the garden's deterministic
   sender-gate + safe-to-watch discipline are model-independent and still apply, but
   the model-level backstop is weaker than the current fleet's. Availability is a
   per-team PREVIEW (429 = not enabled), no published pricing, and on the newer
   coding/agentic benchmarks Spark 1.1 TRAILS the Claude 4.8 Opus tier the fleet
   already runs — so the motive would be diversity/cost/independence, not quality.
