Proposed-rules surfaced by the PR #616 code panel (endojs/endo-but-for-bots,
daemon-agent-tools Phase 3, makeGitMountTools). Candidates for encoding into a
juror brief / skill when a gardener next tends the library:

1. A security property that a doc/comment cites as the REASON a tool omits its
   own validation (e.g. "the capability contains `..`, not this tool") must be
   pinned by a test against the REAL capability, not only a stub that echoes
   input back. (prover, purist, corner-prober — recurring on capability-bridge PRs.)
2. Sibling tool-catalog makers returning the same `ToolRecord[]` shape should
   share a singular/plural naming convention, or the difference should track a
   real distinction the docstring states. (stylist, surfacer.)
3. Within one tool catalog, every tool's `execute` result should be structured
   data, not hand-authored confirmation prose, unless the whole catalog does the
   same. (surfacer.)
4. A projection that is the sole barrier stripping remotables from a wire-bound
   record should assert pass-style on each retained field, not just omit
   known-dangerous keys by name. (breaker, wire-watcher.)
5. Pure path-normalization functions with an equivalence-class contract (many
   strings -> one segment list) get a round-trip property test, not just
   boundary examples; introduce fast-check as a devDependency where a package
   ships universally-quantified contracts. (fast-checker.)
6. A hand-authored bridge schema/guard pair at a wire boundary should carry a
   same-file test pinning schema `properties` keys to `argGuards` arity,
   mirroring the mechanical divergence gate derived-guard makers get for free.
   (wire-watcher.)

These are advisory, not applied to the PR (dispositioned acknowledge/follow-up
in the posted review). No standing-rule library change was made by this job.
