Amendment from the maintainer (kriskowal, 2026-10-03), confirming and redirecting
the feasibility question this job was told to investigate:

**Confirmed: no Docker-in-Docker on gardener hosts.** Don't spend budget
re-discovering this — treat it as settled. Running `act` directly inside a
gardener's own sandbox is off the table.

**New direction: investigate minion.town infrastructure instead.** The idea is
a dedicated `ci.minion.town` host that could serve either (or both) of two
roles:

1. A **GitHub self-hosted Actions runner** registered against the fleet's
   actively-gauntleted repos (`endojs/endo-but-for-bots`,
   `kriscendobot/minion.town`, etc.) for their Linux-runnable jobs — this
   would offload those jobs from GitHub-hosted Actions minutes entirely, which
   more directly addresses the original "Actions budget" motivation than a
   local pre-push screen does.
2. A **remote Docker host for `act`**: gardener hosts run `act` pointed at
   `ci.minion.town`'s Docker daemon over the network (`DOCKER_HOST` /
   `--container-daemon-socket`, or whatever `act`'s current remote-daemon
   support actually is — verify against real docs, don't guess), so a
   gardener can still get the local pre-push screening value without needing
   Docker locally itself.

These aren't mutually exclusive — a self-hosted-runner host could also expose
its Docker daemon for `act` to use remotely. Investigate both and recommend.

This is real new infrastructure (a host, DNS under `ci.minion.town`, exposure
of a Docker daemon to the fleet, registering a self-hosted GitHub Actions
runner against repos the garden doesn't administratively control alone for
`endojs/endo-but-for-bots`), so treat the existing minion.town project context
(`journal/projects/` if there's a minion.town entry, and whatever AWS/infra
docs already exist for minion.town — e.g. `context/operations/aws-bringup.md`)
as required reading before proposing specifics, and be explicit in the
design's `## Open questions` about anything that's a real resourcing/security
decision (who administers a self-hosted runner's registration, what repos it's
even permitted to attach to, cost of a dedicated CI host) rather than an
engineering judgment call.

The rest of the original job stands: Linux/`ubuntu-*`-only scope, position
this as a parity cross-check against `local-verify`/`pre-push-gates` rather
than a redundant gate, and a complete "infeasible, here's why" design is still
an acceptable outcome if the minion.town route doesn't pan out either.
