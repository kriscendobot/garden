# Scope decision from the maintainer: review bodies YES, inline comments conditionally

You hold job `suffix-github-comments-with-provenance`, whose body asked you to decide
whether the provenance suffix covers PR review summary bodies and inline review
comments. kriskowal has decided it (2026-07-28). Do not re-decide; implement this.

## The rule

1. **PR review summary bodies: YES.** Suffix them exactly like top-level PR and issue
   comments.

2. **Inline review comments: NO** - with one exception.

3. **Exception: a SINGLETON inline comment with no primary review body gets the
   suffix.** When an inline comment stands alone, so no accompanying review summary
   body carries the provenance, that inline comment carries it instead.

The intent: provenance appears **once per act of communication**, not once per line.
A review with a summary body plus twelve inline comments carries one suffix on the
body, not thirteen. But a lone inline remark must not escape provenance entirely just
because there was no summary body to attach it to.

## Cases to resolve while implementing

- A review submitted with inline comments AND a non-empty summary body: suffix the
  body only; leave every inline comment clean.
- A review submitted with inline comments and an EMPTY summary body: the inline
  comments are the whole communication. Apply the singleton rule so the provenance is
  not lost. If several inline comments share one such review, prefer ONE suffix
  (on the first, or wherever it reads least intrusively) over one per comment, and
  say what you chose.
- A standalone inline comment posted directly through `gh api`
  (`repos/.../pulls/N/comments`) with no review wrapper: singleton, so suffix it.
- A threaded reply (`.../comments/ID/replies`): treat as a singleton and suffix it,
  since no review body accompanies it. If you think that reads as noisy on a long
  thread, implement the rule as stated and flag your concern in the report rather
  than deviating.

## Unchanged

Everything else in the job body stands: enforce at the `scripts/jobs/bin/gh`
chokepoint if it can be done safely, use the DEPLOYED sha rather than tip, derive the
repo URL rather than hardcoding it, stay idempotent, and fail open when provenance
cannot be resolved.

Report which cases you covered and any you deliberately left out.
