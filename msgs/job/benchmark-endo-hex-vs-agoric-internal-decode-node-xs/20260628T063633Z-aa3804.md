# AMENDMENT (maintainer 2026-06-28) — decodeHex benchmark: input distribution + a heuristic to evaluate

Clarifying the input model and adding a third contender. Fold this into the benchmark and the
PR #7 report.

1. **Common case = UNIFORM case.** Expect real inputs to be either ALL-lowercase or
   ALL-uppercase. These uniform-case inputs are the MOST RELEVANT — make them the PRIMARY,
   headline metric (run an all-lower and an all-upper corpus and weight them heavily).

2. **Mixed-case is correctness, not the headline.** Handle mixed-case for CORRECTNESS, but
   treat its cost as a RARE SLOW PATH — report it as a worst-case data point, not the main
   number.

3. **Add a THIRD approach to the comparison — the first-char-establishes-case heuristic.**
   Alongside (a) the Agoric 484-entry four-permutation Map and (b) the Endo per-char
   `charCodeAt` arithmetic, benchmark an approach that:
   - assumes the **first character establishes the expected case convention** for the whole
     string;
   - decodes the entire input on a **single-case fast path** (a single-case table or
     arithmetic — NO four-permutation Map);
   - on hitting a value **out of range** (a digit not valid under the assumed case — i.e. the
     input was actually mixed-case), **falls back to a much slower approach**, e.g. re-entering
     / re-decoding on `input.toLowerCase()` from the start.
   On the common uniform-case inputs this should beat both incumbents (no/smaller table,
   minimal branching), paying the slow fallback only for rare mixed-case. Measure it on BOTH
   engines (Node wall-clock; XS wall-clock + metered cost) like the other two, and verify it
   decodes correctly including the mixed-case fallback.

Net: a THREE-way comparison (Agoric four-permutation Map / Endo arithmetic / first-char-case
heuristic + toLowerCase fallback), measured **primarily on uniform-case inputs** (the common
case), with mixed-case as a correctness + worst-case-fallback check. Still avoid `flatMap`
anywhere in the harness (XS metered-stack hazard).
