SCOPE EXTENSION from the maintainer (kriskowal, 2026-09-19), for the job you hold,
`design-cpu-back-pressure-job-dispatch-20260918`:

  "We should also put back-pressure on job dispatch to cap when using too much
   memory, when kernel queue latency gets too high, in addition to high CPU
   utilization."

So the admission gate is MULTI-SIGNAL, not CPU-only. Design it as one gate over a
set of saturation signals, refusing a claim when ANY signal is saturated, rather
than three bolted-on checks:

1. CPU — as already briefed.
2. MEMORY — available memory, not "used". On this box `free -h` reads 125Gi total /
   ~40Gi used / ~84Gi available, so a "used" threshold would be badly misleading
   given page cache. Prefer MemAvailable, and consider `/proc/pressure/memory` for
   the same reason PSI is attractive for CPU: it measures actual stall, not a level.
   Note the concrete harm already observed — the harness killed two background
   tasks citing low memory during this episode, and the failing units below peaked
   at ~330MB each while starved.
3. KERNEL QUEUE LATENCY — `/proc/pressure/io` is the natural signal (time tasks
   spend stalled on I/O). Say what you are actually measuring: run-queue depth
   (`procs_running`/`procs_blocked` in /proc/stat, or loadavg's blocked component)
   is a different thing from I/O pressure, and the maintainer's phrase could mean
   either. Pick, justify, and state the distinction plainly so a reader knows which
   stall is being defended against.

Everything already briefed still holds and applies per-signal: hysteresis with
separate high/low-water marks reusing `budget-level`'s 0.85 pattern; FAIL OPEN on an
unreadable signal (deliberately opposite the budget gate — an unreadable load or
pressure file must not cause a fleet-wide outage); admission-only with no preemption
of running work; and coalesced visibility through `watchdog-notice.sh`, which should
name WHICH signal tripped, since "host refused on memory" and "host refused on I/O"
demand different operator responses.
