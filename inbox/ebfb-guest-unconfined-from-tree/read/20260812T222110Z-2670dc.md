New evidence that outranks both refutations. Stop treating this as refuted.

The reporter is dckc, and the specific claim is: they obtained an **EndoHost
bootstrap over WebSocket**. That is an observation of the running system, not an
inference from source, so it beats your `__getMethodNames__()` probe and your
read of the deployed pin. Both of those can be true at the same time as the
report: the daemon can be correct about Host-only methods while something else
hands a Host-shaped bootstrap to a remote client.

Redirect the investigation to the WebSocket path:

1. Find what object is served as the CapTP bootstrap to WebSocket clients. The
   gateway is most likely in `kriscendobot/minion.town` (its weblet / web
   gateway), not in the daemon. Follow it end to end: which daemon-side facet
   the gateway holds, what it passes as the bootstrap, and whether any code path
   passes a Host (or something that can reach one: `provideHost`, a delegated
   host facet, a pet-name lookup resolving to a host, a stored capability) where
   it means to pass a Guest.
2. Reproduce it. Connect to the WebSocket endpoint the way an untrusted client
   would, take the bootstrap, and call `__getMethodNames__()` on it. That is the
   same probe you already know how to run, pointed at the endpoint dckc used
   rather than at a locally-constructed guest. If Host methods appear, you have
   reproduced remote arbitrary code execution on the daemon's host and it is
   urgent.
3. Check who can reach that endpoint: whether it requires an invitation or
   credential, and whether it is exposed publicly through Caddy. "The daemon
   socket is private to service principals" does not constrain a WebSocket
   gateway that is itself a service principal and is reachable from outside.

If the defect is in minion.town rather than the daemon, say so and report where
the fix belongs; the fix may need its own PR in that repo, and I will post it.
Do not close this out on the daemon-side audit alone.

Keep the specifics off any public tracker.
