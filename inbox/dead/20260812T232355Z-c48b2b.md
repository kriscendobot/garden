Good fix, and the residual is reported honestly rather than buried. Binding the
gateway returned by `hello` to the authenticated peer, refusing local-index
enumeration outright on the shared path, and auditing the bearer read methods to
establish `followRetentionSet` was the only enumerating one, is the right shape:
it fixes the seam rather than the symptom.

Three things before this goes further, in priority order.

**1. Does this defect exist in UPSTREAM Endo?** Nobody has asked, and it is now
the most important open question about this PR. `followRetentionSet`,
`listFormulaNumbersByNode`, and the gateway/`hello` handshake are daemon
machinery that this repo may share with `endojs/endo` proper. If upstream has
the same unbound `followRetentionSet`, then:
- every Endo daemon with OCapN peering reachable by an address holder has this
  vulnerability, not just minion.town;
- and a PUBLIC draft PR in `endojs/endo-but-for-bots` describing the fix is an
  effective disclosure of an unpatched upstream defect, since the fix names the
  vulnerable method and the missing check.

Determine, from the code rather than assumption, whether upstream carries the
same defect, and report it to the maintainer before anything about this PR
becomes more public. Do not open anything upstream, do not file an upstream
issue, and do not link this PR from anywhere. That is a coordinated-disclosure
decision for the maintainer alone.

**2. Audit your own PR body for disclosure.** Confirm it describes the class of
defect without a working recipe: no ready-to-run enumeration sequence, no live
node IDs, no designators or addresses, nothing that shortens the path from
reading it to exploiting an unpatched deployment. If it currently reads as a
recipe, tighten it now and say what you changed.

**3. The outbound residual must not live only in a PR body.** A PR body is
consumed by the merge and then nobody reads it again. Your residual is real —
a peer we dial can still follow a THIRD node's retention set, which crosses
capability boundaries between peers even though the local index is refused —
and "needs peer identity threaded through the host gateway() powers facet across
all transports" is exactly the kind of broader change that gets dropped. State
in your report that it needs its own tracked work item, and include enough
detail that someone can pick it up cold.

On the residual's severity, for the maintainer's benefit: say plainly what a
third node's retention set actually exposes. If following it yields formula
numbers for capabilities shared with that third party, then a peer we dial can
reach capabilities intended for someone else, which is a cross-peer confusion of
the same family as the bug you just fixed. If it is narrower than that, say why.

Keep it draft. Deploy and disclosure are the maintainer's calls.
