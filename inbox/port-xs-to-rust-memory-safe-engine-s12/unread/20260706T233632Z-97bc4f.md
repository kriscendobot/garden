FOLDS (named, both for the coder child — byte-identity is its bar, not the parser's):
 1. Class field / static-block -> init-function surgery (fxClassExpression second half). We parse
    every member faithfully (identical early errors + token consumption) and keep them in the
    class `items` list in source order; the two init slots (constructorInit/instanceInit) are left
    null and the default constructor is synthesized. The C does intrusive pointer-aliasing (field
    nodes alias members still in the list) that doesn't map to our owned-Vec AST; it is a lowering/
    desugaring concern the coder should perform. The `items` list carries everything the coder needs.

    the oracle rejects them and we do too; those productions are omitted (verified default in xsCommon.h;
    endor-oracle sets no override).
 3. fxCheckNativeConstructor/fxCheckNativeFunction: fire only under mxNativeFlag / `@` host syntax,
    absent from the conformance corpus — skipped.
 4. fxPropertyName string-key -> canonical-index (fxStringToIndex): a string key like "0" stays a
    Property rather than PropertyAt. Doesn't affect accept/reject; a minor tree-shape nicety for the coder.

Note on accept/reject semantics: the parser accepts scoper-level-invalid programs XS's parser also
accepts (e.g. a bare top-level `break;` — XS rejects that during scoping, not parsing). The corpus
smoke exercises no such cases, so agreement is perfect; flagging it so the coder/scoper child expects
these to be caught downstream.

JSX and host `@` object/class literals: present in xsSyntaxical.c but out of the ECMAScript surface
and absent from the corpus — not ported.
