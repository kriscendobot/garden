# Addendum — computed/private fields need scope-bearing field-init functions

Follow-up to the class-fields fold report (slices 47-49). Confirmed the key
architectural blocker for the NEXT class-field slice:

The plain-data-field synthesis (`code_field_init_function` in coder.rs) emits the
instanceInit/constructorInit functions **scope-free** — it saves/restores coder
state and emits CONSTRUCTOR_FUNCTION/BEGIN_STRICT_FIELD/END directly, WITHOUT a
scoper scope. That works only because a plain `x = v` field function captures
nothing (THIS + value + NEW_PROPERTY).

**Computed keys** (`[e]=v`) and **private members** (`#x`) break this: per
fxFieldNodeCode (xsCode.c:3097), a PropertyAt field reads its key via
`GET_CLOSURE atAccess`, and a private field reads `NEW_PRIVATE symbolAccess` /
`GET_CLOSURE valueAccess`. Those atAccess/symbolAccess/valueAccess are anonymous
class-scope closures (xsScope.c:480-513, hoisted like instanceInit) that the field
FUNCTION must CAPTURE — i.e. the field-init function needs a real scope with
RETRIEVE/STORE aliases. The current scope-free synthesis cannot express that.

Two routes for whoever takes it:
1. Make the parser synthesize the FieldNode list into constructorInit/instanceInit
   (children[3]/[4]) the way XS does, so the field functions get normal scoper
   scopes — then hoist_class's field loop, fxFieldNodeBind, and fxFieldNodeCode
   port almost verbatim. Bigger parser change, cleaner long-term.
2. Keep the coder-side synthesis but build synthetic scoper scopes for the field
   functions (with the atAccess/private aliases) during hoist_class. Contained to
   scoper+coder, but re-implements what the parser already knows how to do.

Also: the key expression for a computed field is evaluated ONCE at class-definition
time (in fxClassNodeCode's member loop) and stored into the atAccess closure — so
code_class's member loop grows a PropertyAt-field branch that codes the key + AT +
CONST_CLOSURE atAccess, separate from the field function that later reads it.

Everything else in the fold report stands. Static blocks, `using`, and modules
(untestable via the eval-script oracle) remain independent folds.
