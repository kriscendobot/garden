# Maintainer clarification — `llm` owes no backward compatibility; the removal IS the goal

From the maintainer (kriskowal, 2026-08-31), correcting the framing in your job
body. Read this before you finish the PR description or write the changesets.

## The correction

> It is fine to remove base64 streaming methods on the `llm` branch, as that
> branch is entirely experimental and runs far ahead of master and obligations
> for backward compatibility. We ran ahead on byte arrays specifically to
> obviate the need to introduce base64 stream methods on master.

Three consequences for how you should be working:

1. **Do not treat this as a delicate breaking change.** The job body told you to
   mark majors and write careful migration prose because the surface is
   load-bearing across ~10 packages. The blast radius is real and you still have
   to update every consumer correctly — but `llm` carries no compatibility
   obligation to anything downstream, so there is no deprecation period, no
   transitional dual-method window, and no need to preserve `streamBase64` as an
   alias anywhere. Delete it. Changesets should describe the change accurately
   but need not agonize over migration burden for external consumers; there are
   none on this branch.

2. **Do not stage a dual-live series for compatibility reasons.** The job body
   offered a stacked shape that keeps both `stream()` and `streamBase64()` live
   through a migration window. That justification is void. Split the work into a
   stack only if the single diff is genuinely too large for a reviewer to hold —
   a reviewability decision, not a compatibility one. If you do stack, every
   PR in it may assume the base64 path is going away.

3. **The removal is not conditional on the measurement.** The job body said you
   could "scope the removal to where it is a genuine win" if immutable-byteArray
   handling turns out to cost more than base64 on some path. Withdraw that
   escape hatch: byte arrays were built ahead of master *specifically* to obviate
   base64 stream methods, so the methods are going regardless. Still measure the
   immutability/copy cost and still report it in the PR — if some path regresses,
   that is a real finding worth a follow-up issue against the byteArray or
   `@endo/immutable-arraybuffer` path, not a reason to leave `streamBase64`
   standing.

Everything else in the job body stands: no `streamBase64` in any `packages/**`
source, type declaration, generated file, or test; regenerate rather than
hand-edit under `packages/agent-tools/generated/`; full local verify green.
