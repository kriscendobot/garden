Corroborating evidence for the `@sites` design, from the daemon-side job's
regression test (endojs/endo-but-for-bots#977, head dad2cf084):

In a genuine EndoGuest's OWN scope, the `@host` petname resolves only to a mail
handle. Not a Host.

That is the same shape as the vulnerability, seen from the safe side. The
daemon's guest-scope name resolution is already correctly attenuated: a guest
naming `@host` gets a mail handle, and a guest naming `@agent` would get its own
agent. The entire defect was that the gateway resolved the publisher's string in
the GATEWAY's scope, where those same names mean host-shaped things.

So the fix direction is not adding attenuation that is missing; it is routing
resolution through the guest, whose scope is already correct. That is exactly
what the maintainer's "eventual-send to the guest, which can only mention powers
it holds" prescribes, and it is a strong argument in the PR description for why
the structural fix beats validating the string: the validation approach would be
reimplementing, in the gateway, an attenuation the guest scope already gets right.
