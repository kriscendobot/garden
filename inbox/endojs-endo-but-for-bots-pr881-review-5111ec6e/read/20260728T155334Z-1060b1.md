## What the added constraint asks for, against the current code

Current shape (PR head `build-exo-google-sheets-facets`): a single
`makeFacet(kind, scope)` closure switched at call time by a `kind` string
(`'read' | 'writer' | 'append' | 'write'`), with `Object.assign` branches, an
interface chosen by nested ternary, and a mutable `readOnly` closure variable
consulted by `if (readOnly) throw` at six write call sites.

The mereology-builder ask is that authority be fixed **by construction**, and that
narrowing return **parts of a whole**:

1. **One maker per authority, not one maker per `kind` string.** `makeReader`,
   `makeAppender`, `makeWriteOnly`, `makeWriter` as separate constructors. A
   reader's closure must never capture `client.values.update` / `.append` /
   `.clear` at all — that is the operational reading of "statically not have
   access to write authority": the implementing code holds no reference to the
   authority it lacks, so there is no guard to forget.

2. **`whole.part('A')` returns a narrower whole of the same authority.**
   `spreadsheet.sheet('A')` yields a sheet-whole; `.range('A1:C10')` on that yields
   a range-part. The part axis (which cells) and the authority axis (which verbs)
   stay orthogonal: narrowing never widens verbs, and attenuating verbs never
   widens cells. Today's `narrow(kind, field)` accumulates a `scope` record and
   re-derives confinement per call, which gets the arithmetic right but keeps the
   authority in a runtime string.

3. **Attenuation is downward-only composition.** `writer.readOnly()` should be
   literally `makeReader(scope)` over the same part; no reader/appender/write-only
   facet may expose any method that reaches back up to a writer. (This mostly
   holds today, but only because the `if (kind === 'writer')` branch happens to be
   the only one assigning the attenuators.)

4. **`setReadOnly` is the sharpest instance of the parent comment's smell — and
   the one I'd most like you not to drop.** It lets a facet *already held* by a
   client silently lose write authority via a boolean six call sites remember to
   check; miss one and it is a silent privilege escalation. Replace it with
   revocation of the write authority itself: build the write facets on a
   revocable forwarder around `client.values.{update,append,clear}`, and let the
   control facet sever it (`revokeWrites()`). Severing a shared authority object
   cannot be forgotten at a call site. Same argument applies to the `revoked` flag
   currently checked only inside `charge()` — `sheet()`, `range()`, and `help()`
   bypass it today.
