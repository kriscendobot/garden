# Skill: yarn-lock-separate-commit

Every change that touches `yarn.lock` ships in its own commit, separate from the
`package.json` change that caused the update, with the message
`chore: Update yarn.lock`. Implementation and the tests covering it stay
together in the package's own commit; only the lockfile splits out.

Consumed by the builder and fixer steps of the gardening state machine
([`../../scripts/jobs/gardening/garden-pr.sh`](../../scripts/jobs/gardening/garden-pr.sh);
design [`../../designs/gardening-state-machine.md`](../../designs/gardening-state-machine.md)),
and applied retroactively across a whole branch by the
[retcon](../retcon/SKILL.md) job. Several jury seats (packager, changeset-auditor)
read for this split when they review diff hygiene.

## Why

A separate lockfile commit can be dropped and regenerated cleanly on rebase. A
combined commit turns lockfile churn into merge conflicts that have to be
resolved by re-running `yarn install` and hand-stitching, which is error-prone
and pollutes history. The split is what makes the rebase recovery below a
mechanical drop-and-regenerate rather than a manual merge.

## Procedure

After making the dependency change in `package.json`, commit the package change
and the lockfile as two commits, lockfile last:

```sh
git add packages/foo/package.json
git commit -m "feat(foo): add bar dependency (#NNNN)"

npx corepack yarn install
git add yarn.lock
git commit -m "chore: Update yarn.lock"
```

When force-pushing a rebased branch, the order of the two commits matters: put
the lockfile commit *after* the package.json commit, so a reviewer dropping the
lockfile commit lands at a still-coherent state.

## Pitfalls

- **`git commit --amend` on the package.json commit silently drags the lockfile
  in if it is staged.** Stage and commit the lockfile last, on its own.
- **Accidental combining.** If caught on review, `git reset HEAD~1`, re-stage
  selectively, and recommit as two. A retcon ([`../retcon/SKILL.md`](../retcon/SKILL.md))
  applies the same fix across a branch's whole history at once.
- **Package renames invalidate the lockfile.** Renaming a workspace's directory
  or `package.json` `name` field changes the workspace key
  (`"@scope/<name>@workspace:packages/<dir>"`) inside `yarn.lock`. It still ships
  in its own `chore: Update yarn.lock` commit, regenerated by re-running
  `npx corepack yarn install` after all renames are in place. Do not hand-edit
  the workspace key; the install produces the canonical form. See
  [rename-discipline](../rename-discipline/SKILL.md).

## Rebase recovery

A PR carrying `chore: Update yarn.lock` typically conflicts on the lockfile when
rebased onto a moved base (any other PR that touched dependencies has landed in
the interim). Because the lockfile lives in its own commit, the recovery is a
drop-and-regenerate, not a manual merge: skip the old lockfile commit during the
rebase, apply any review-feedback fixes on top, then regenerate the lockfile
against the new base as its own commit.

```sh
git rebase origin/<base>
# conflict on yarn.lock
git rebase --skip                     # drop the old lockfile commit
# apply review-feedback fixes on top
npx corepack yarn install             # regenerate lockfile against new base
git add yarn.lock
git commit -m "chore: Update yarn.lock"
```

This is the weave/rebase step's standing move when a base has moved under a
dependency-touching PR. The weaver-to-fixer escalation and the conflict
discipline live in [conflict-resolution](../conflict-resolution/SKILL.md).

The gardening state machine now runs this exact drop-and-regenerate
deterministically as its rebase stage:
[`scripts/jobs/gardening/safe-rebase.sh`](../../scripts/jobs/gardening/safe-rebase.sh)
does the fresh-base/head check, replays the reviewed commits, and — when the *only*
conflict is a lockfile-only commit — skips it and regenerates the lockfile against
the new base as its own `chore: Update yarn.lock`. Any other conflict fails closed
(rc 3) for a weaver/fixer. It was added to automate the routine stale-branch recovery
a gardener did by hand for the approved Dependabot PR endojs/endo-but-for-bots#868.
