# Property-by-consumer matrix

Which tool reads which `package.json` property, and how. The consumer families are: **package managers** (npm, Yarn Classic v1, Yarn Berry v2+, pnpm, Bun-as-PM), **module systems / runtimes** (Node.js CJS+ESM, Deno, Bun runtime, Endo `@endo/compartment-mapper`), and **bundlers / compilers** (webpack, Rollup, esbuild, Vite, Turbopack, Parcel, swc, Babel, plus TypeScript).

Rows grounded in ingested library sources: Node traces to [`../../library/sources/node--doc-api-packages.md`](../../library/sources/node--doc-api-packages.md) (`cc37ad5`), npm to [`../../library/sources/npm--configuring-npm-package-json.md`](../../library/sources/npm--configuring-npm-package-json.md) (`ce7681f`), TypeScript to its handbook sources (`c8170c35`), Deno to its [configuration](../../library/sources/deno--runtime-fundamentals-configuration-md.md) and [Node compatibility](../../library/sources/deno--runtime-fundamentals-node-md.md) guides (`7bf3190`), Bun to its [module-resolution guide](../../library/sources/bun--docs-runtime-module-resolution-mdx.md) (`6352b79`), and Endo to the [compartment-mapper manifest sections](../../library/sources/endo--pkg-compartment-mapper-readme-package-manifest.md) (`46d4edf`). The package-manager columns are now library-backed: Yarn Berry to the [manifest schema](../../library/sources/yarn-berry--manifest-schema.md) (`ab0afaf`), pnpm to its [`package.json` fields](../../library/sources/pnpm--package-json.md) (`047db9a`) and [settings](../../library/sources/pnpm--settings.md) (`0cf4bd3`), Bun to its [overrides](../../library/sources/bun--overrides.md) and [lifecycle](../../library/sources/bun--lifecycle.md) guides (`16a7269`), and `packageManager`/Corepack to the [Corepack README](../../library/sources/corepack--readme.md) (`05bc5f3`). The bundler/compiler columns are now library-backed across both ingest cycles: webpack to its [resolve](../../library/sources/webpack--config-resolve.md) and [tree-shaking](../../library/sources/webpack--guides-tree-shaking.md) docs (`c0038eb`, `6f1e6f2`), Rollup to the [`@rollup/plugin-node-resolve` README](../../library/sources/rollup--node-resolve-readme.md) (`d455fff`), esbuild to its [API documentation](../../library/sources/web--esbuild-api.md) (content `2c986ac`), Vite to its [shared](../../library/sources/vite--config-shared-options.md) (`9beae37`), [SSR](../../library/sources/vite--config-ssr-options.md) (`01337ad`), and [dep-optimization](../../library/sources/vite--config-dep-optimization-options.md) (`9beae37`) options, Parcel to its [dependency-resolution](../../library/sources/web--parcel-dependency-resolution.md) (content `ce144ef`), [targets](../../library/sources/web--parcel-targets.md) (content `6dd8dea`), and [production](../../library/sources/web--parcel-production.md) (content `898c5ec`) docs, Turbopack to the [Next.js `turbopack` config](../../library/sources/web--nextjs-turbopack-config.md) (content `871ded2b`), and the two compilers swc ([compilation](../../library/sources/web--swc-compilation.md), content `2981937c`) and Babel ([options](../../library/sources/web--babel-options.md), content `068855fa`). Only Yarn Classic v1 specifics remain synthesis where marked.

## The property universe

Every property named in the job scope, grouped:

- **Identity / metadata:** `name`, `version`, `description`, `keywords`, `homepage`, `bugs`, `license` (+ deprecated `licenses`), `author`, `contributors`, `funding`, `repository`, `private`.
- **Entry points / module resolution:** `main`, `module` (non-standard, bundler convention), `browser`, `types`/`typings`, `typesVersions`, `exports`, `imports`, `type`, `sideEffects`.
- **Files / executables:** `files`, `bin`, `man`, `directories`, `gypfile`.
- **Scripts / config:** `scripts`, `config`.
- **Dependencies:** `dependencies`, `devDependencies`, `peerDependencies`, `peerDependenciesMeta`, `bundleDependencies` (+ alias `bundledDependencies`), `optionalDependencies`.
- **Resolution control (root-only):** `overrides` (npm), `resolutions` (Yarn), `pnpm.overrides` / `pnpm.*` (pnpm), `packageExtensions` (npm/Yarn/pnpm).
- **Environment constraints:** `engines`, `engineStrict` (legacy), `os`, `cpu`, `libc`, `devEngines`.
- **Publishing / workspaces / tooling:** `publishConfig`, `workspaces`, `packageManager`, and tool-namespaced blocks (`pnpm`, `parsers` for Endo, custom `exports` conditions).

## Compact matrix (property -> primary readers)

| Property | Primary readers | Notes |
|---|---|---|
| `name` | all PMs; Node (named imports / self-reference) | Node uses it for self-referencing via `"exports"`; PMs use it as the registry identifier. <=214 chars, URL-safe, optional `@scope/`. |
| `version` | all PMs | node-semver parseable; forms the unique identifier with `name`. Not read by the runtime. |
| `description`, `keywords`, `homepage`, `bugs`, `funding`, `author`, `contributors`, `license`, `repository` | PMs / registry / `npm fund` / `npm bugs` / `npm repo` | Pure metadata; runtimes and bundlers ignore. `license` uses SPDX identifiers/expressions; object/`licenses`-array forms deprecated. |
| `private` | npm, Yarn, pnpm, Bun (refuse publish) | Also gates `packageExtensions`/`overrides` publish refusal in npm. |
| `main` | Node runtime; all PMs; every bundler | The universal legacy entry. `"exports"` takes precedence when present (Node + modern bundlers). Defaults to `index.js` in npm. |
| `module` | bundlers (webpack, Rollup, esbuild, Vite, Parcel) | **Not a Node or npm field.** A bundler convention pointing at an ESM build for tree-shaking. Node ignores it entirely. Appears in `mainFields` for webpack (`["browser","module","main"]`/`["module","main"]`), Rollup (`['module','main']`), Vite (client `defaultClientMainFields` including `module`), and esbuild's auto `module` condition; Parcel checks `module` in its package-entry chain after `browser` — see the Bundlers section. |
| `browser` | bundlers; Endo (`browser` condition); Node ignores | String (replace `main`) or object (per-module replacement map). Endo draws in `browser` instead of `main` under its `browser` condition. |
| `types` / `typings` | TypeScript | Root declaration entry: legacy lookup prefers `types`, then synonymous `typings`, then `main`; retain `types` even when `exports` supplies declarations. Ignored by runtimes/PMs. |
| `typesVersions` | TypeScript | Ordered compiler-semver redirects for declaration layouts; supported in every TS resolution mode but not read when `exports` is active. |
| `exports` | Node runtime; bundlers (webpack, Rollup, esbuild, Vite, Parcel opt-in); TypeScript (`node16`/`nodenext`/`bundler`); Endo; Bun | The central field. Each bundler applies its own configurable condition set (webpack's dynamic `conditionNames`, Rollup's `exportConditions` base set, esbuild's platform-derived set, Vite's client/SSR sets, Parcel's ordered condition list — Parcel's `exports` support is opt-in via `packageExports`) and, once `exports` resolves, ignores the legacy `mainFields`. TS always matches `types`/`default` and selects `import` or `require` by resolution context; Bun reads ordered conditions including `bun`; Endo supports only `import`/`browser`/`endo` and no `*` patterns yet. Deno's ingested compatibility guide does not enumerate its export-condition algorithm. |
| `imports` | Node runtime; bundlers (webpack `importsFields`, Rollup, esbuild, Parcel); Endo (not yet) | `#`-prefixed private internal mappings; may map to external packages. webpack reads them via `resolve.importsFields`; Rollup's node-resolve, esbuild, and Parcel support subpath `imports`. Endo README notes `imports` support is a future TODO. |
| `type` | Node runtime; bundlers; TypeScript; Endo; Bun; Deno | Decides CJS vs ESM for `.js`. Read by nearly everything that parses JS. npm itself does not use it. |
| `sideEffects` | bundlers (webpack, esbuild, Rollup, Vite) — Parcel **not documented** | Tree-shaking hint: `false` = no side effects (whole unused modules prunable), or an array of side-effectful file globs to keep. webpack ([tree-shaking section](../../library/sections/webpack--guides-tree-shaking--sideeffects-flag.md)) and esbuild ([tree-shaking section](../../library/sections/web--esbuild-api--tree-shaking-and-sideeffects.md)) honor it directly; Vite rides its esbuild/Rollup passes. Parcel's [production docs](../../library/sections/web--parcel-production--tree-shaking-and-scope-hoisting.md) present tree shaking as whole-program static analysis + scope hoisting and do **not** document reading `sideEffects` (correcting the earlier synthesis guess). Node/PMs ignore. |
| `files` | npm, Yarn, pnpm, Bun (pack/publish); Endo (declared, not yet enforced) | Allowlist for the published tarball; defaults `["*"]`. Endo README: recognized but the `files` globs are not yet acted on. |
| `bin` | all PMs (link onto PATH) | String (= package name) or map. Target must start with `#!/usr/bin/env node`. |
| `man` | npm (metadata only since v12) | No longer installs system man pages. |
| `directories` | npm (`.bin`, `.man`) | `directories.bin` mutually exclusive with `bin`. Mostly vestigial. |
| `gypfile` | npm (node-gyp) | `false` opts out of automatic node-gyp build. |
| `scripts` | all PMs (lifecycle) | Runs at lifecycle events; `config` values surface as `npm_package_config_*`. |
| `config` | npm (scripts env) | Persists across upgrades; exposed to scripts. |
| `dependencies` | all PMs; Node/Endo (trust the arranged tree) | Rich specifier grammar (semver, tarball/git/GitHub/local URLs, dist-tags, `npm:` aliases). Runtimes do not read it; they trust the PM's `node_modules` arrangement. |
| `devDependencies` | all PMs (root install only) | Not installed for consumers. |
| `peerDependencies` | all PMs, differently | npm v7+ auto-installs (3-6 warned only); Yarn Berry supports **peer-dependencies-with-default** (dep listed in both `dependencies` and `peerDependencies`) ([yarn-berry--manifest-schema--dependency-metadata](../../library/sections/yarn-berry--manifest-schema--dependency-metadata.md)); pnpm surfaces peer issues loudly and relaxes them via `peerDependencyRules` ([pnpm--settings--package-extensions-and-peer-rules](../../library/sections/pnpm--settings--package-extensions-and-peer-rules.md)). See inconsistencies. |
| `peerDependenciesMeta` | npm, Yarn, pnpm | Marks a peer `optional`. |
| `bundleDependencies` / `bundledDependencies` | npm (pack), Yarn, pnpm | Names bundled into the `npm pack` tarball; boolean form bundles all/none. |
| `optionalDependencies` | all PMs | Build/fetch failure does not fail install; overrides same-named `dependencies`. The vehicle for per-platform prebuilt binaries. |
| `overrides` | npm, Bun (Bun reads npm `overrides`, top-level only) | Root-only tree rewrite. Bun's is library-backed ([bun--overrides](../../library/sources/bun--overrides.md)); Bun supports no nested selectors. |
| `resolutions` | Yarn Classic + Berry; Bun (migration compat) | Yarn's override dialect: flat glob-path selectors (`parent/dep`), one level of specificity, root-only ([yarn-berry--manifest-schema--resolutions](../../library/sections/yarn-berry--manifest-schema--resolutions.md)). Bun also reads `resolutions`, top-level only. |
| `overrides` / `packageExtensions` / `peerDependencyRules` / `patchedDependencies` (pnpm) | pnpm | **Since pnpm v11 these live in `pnpm-workspace.yaml`, not a `pnpm` block in `package.json`** ([pnpm--package-json--pnpm-field-moved-and-engines](../../library/sections/pnpm--package-json--pnpm-field-moved-and-engines.md), [pnpm--settings--overrides](../../library/sections/pnpm--settings--overrides.md)). `overrides` supports `parent>dep` selectors, `catalog:` refs, and `-` removal (applies to peers too). |
| `packageExtensions` | npm; Yarn Berry (origin); pnpm (in `pnpm-workspace.yaml` since v11) | Adds/corrects third-party manifest dependency metadata (`dependencies`/`optionalDependencies`/`peerDependencies`/`peerDependenciesMeta`). Root-only; npm refuses to publish a non-private package containing it. pnpm + Yarn co-maintain a shared `@yarnpkg/extensions` DB ([pnpm--settings--package-extensions-and-peer-rules](../../library/sections/pnpm--settings--package-extensions-and-peer-rules.md)). |
| `engines` | all PMs (advisory unless `engine-strict`) | `node`/`npm`/other tool versions. |
| `engineStrict` (legacy) | npm (removed) **(synthesis)** | Formerly a per-package strict-engine flag; removed in favor of the `engine-strict` config. Ignored today. |
| `os`, `cpu`, `libc` | all PMs (install gate) | Allowlist plus `!`-blocklist; `libc` only when `os` is `linux`. The install-gating mechanism behind per-platform packages. |
| `devEngines` | npm (before install/ci/run) | Distinct shape from `engines`; keys `cpu`/`os`/`libc`/`runtime`/`packageManager` with `onFail`. |
| `publishConfig` | npm, Yarn, pnpm (publish time) | Overrides `registry`/`tag`/`access` at publish. |
| `workspaces` | npm, Yarn, Bun; pnpm uses `pnpm-workspace.yaml` instead | Yarn and Bun read root `package.json` glob patterns. pnpm workspace membership comes from YAML `packages:` include/exclude globs, with the root always included ([pnpm workspace YAML](../../library/sections/pnpm-io--pnpm-workspace-yaml--packages-and-root-membership.md)). |
| `packageManager` | Corepack (Node), Yarn/pnpm via Corepack | `name@x.y.z[+sha224.<hash>]` (or a `.js`/`.tgz` URL); pins the PM. Corepack intercepts calls and enforces it ([corepack--readme--package-manager-field](../../library/sections/corepack--readme--package-manager-field.md)). `devEngines.packageManager` allows a version *range* + `onFail`. Not a runtime field. |
| `parsers` | Endo compartment-mapper | Per-package extension-to-language override (for example `{ "png": "bytes" }`). Endo-specific. |

## Per-consumer resolution and precedence notes

### Node.js (runtime)

Reads exactly five fields (`name`, `main`, `type`, `exports`, `imports`); everything else is package-manager metadata it ignores (source: field-definitions section). `"exports"` takes precedence over `"main"`. Condition order is object-key order, most-specific-first, `"default"` last; the built-in conditions are `node-addons`, `node`, `import`, `require`, `module-sync`, `default`. `"type"` plus `.mjs`/`.cjs` extensions decide module format. `require()` and `import` use two different resolution algorithms (extension search + folders-as-modules for `require`; fully-specified paths + URL support for `import`).

### npm (package manager)

Reads the full metadata + dependency + publishing surface. Does **not** read `type` (delegates to Node) or `module`/`sideEffects`/`types` (bundler/TS conventions). Override dialect: `overrides` + `packageExtensions`, root-only. Installs `peerDependencies` by default (v7+).

### Yarn Classic (v1) / Yarn Berry (v2+)

Both read `resolutions` (not `overrides`) — a flat glob-path override dialect, root-only, one level of specificity ([yarn-berry--manifest-schema--resolutions](../../library/sections/yarn-berry--manifest-schema--resolutions.md)). Berry's manifest schema is library-backed: `dependenciesMeta` (`built`/`optional`/`unplugged`), peer-dependencies-with-default, `peerDependenciesMeta.optional`, `publishConfig` (per-field publish-time replacements + `access`/`provenance`/`executableFiles`), `installConfig` (`hoistingLimits`, `selfReferences`), and `packageManager` ([dependency-metadata](../../library/sections/yarn-berry--manifest-schema--dependency-metadata.md), [publishing-and-install-config](../../library/sections/yarn-berry--manifest-schema--publishing-and-install-config.md)). Berry PnP generates `.pnp.cjs`, maps package locations, and rejects undeclared dependency access; `.yarnrc.yml` `packageExtensions` can supply missing regular or peer edges ([PnP resolver](../../library/sections/yarn-berry--plugnplay--resolver-and-strict-visibility.md)). `nodeLinker` can instead select pnpm-style or conventional `node_modules` layouts ([install modes](../../library/sections/yarn-berry--install-modes--pnp-pnpm-and-node-modules-linkers.md)). The `workspace:` protocol accepts a semver range or `^`/`~`/`*`, resolves locally by name, and rewrites shorthand forms for publication ([workspaces](../../library/sections/yarn-berry--workspaces--workspace-protocol-and-publish-rewrite.md)). No maintained Yarn Classic v1 documentation source with a separate layout specification was found; it remains the legacy hoisted comparison rather than a separate ungrounded claim.

### pnpm

**Correction (library-backed):** since **pnpm v11**, pnpm no longer reads settings from a `pnpm` block in `package.json`; `overrides`, `packageExtensions`, `peerDependencyRules`, and `patchedDependencies` now live in **`pnpm-workspace.yaml`** ([pnpm--package-json--pnpm-field-moved-and-engines](../../library/sections/pnpm--package-json--pnpm-field-moved-and-engines.md)). `overrides` uses `parent>dep` selectors, `catalog:` refs, and `-` removal, and applies to peer dependencies; `packageExtensions` extends `dependencies`/`optionalDependencies`/`peerDependencies`/`peerDependenciesMeta`; `peerDependencyRules` (`ignoreMissing`/`allowedVersions`/`allowAny`) relaxes pnpm's strict peer handling ([overrides](../../library/sections/pnpm--settings--overrides.md), [package-extensions-and-peer-rules](../../library/sections/pnpm--settings--package-extensions-and-peer-rules.md)). From `package.json` pnpm still reads `engines`/`engines.runtime`/`devEngines`, `dependenciesMeta.injected` (hard-linked copies so a workspace package's peers resolve per-consumer), `peerDependenciesMeta.optional`, and an extended `publishConfig` (`directory`/`linkDirectory`/`executableFiles`) ([pnpm--package-json--dependencies-meta-and-publishconfig](../../library/sections/pnpm--package-json--dependencies-meta-and-publishconfig.md)). pnpm hardlinks packages beneath `node_modules/.pnpm`, then uses symlinks for the graph; distinct peer contexts get distinct store-path variants ([symlinked layout](../../library/sections/pnpm-io--symlinked-node-modules-structure--store-and-strict-visibility.md), [peer contexts](../../library/sections/pnpm-io--how-peers-are-resolved--peer-context-store-variants.md)). Workspace membership is YAML `packages:` include/exclude patterns, not the manifest `workspaces` field ([workspace YAML](../../library/sections/pnpm-io--pnpm-workspace-yaml--packages-and-root-membership.md)).

### Bun (PM + runtime)

As a runtime, Bun honors ordered `exports` conditions including `bun`, `node-addons`, `node`, importer-specific `require`/`import`, and `default`; it honors `imports`, then falls back to `main` (or implicit `index.*`) before `module`. As a PM, Bun reads **both** npm `overrides` and Yarn `resolutions` (top-level only, no nested selectors — [bun--overrides](../../library/sections/bun--overrides--overview.md)) and is **default-secure**: it runs a dependency's lifecycle scripts only for packages on an allow list, named via `trustedDependencies`, which *replaces* (not extends) the curated built-in list and covers only npm-source packages ([bun--lifecycle--trusted-dependencies](../../library/sections/bun--lifecycle--trusted-dependencies.md)). Bun reads root `workspaces` globs and links local packages; its `workspace:` forms rewrite on publication ([Bun workspaces](../../library/sections/bun--workspaces--manifest-globs-and-workspace-publish-rewrite.md)). Its isolated linker uses a `.bun` store plus symlinks to prevent phantom dependencies and is the default for new `configVersion = 1` workspace projects ([isolated installs](../../library/sections/bun--isolated-installs--bun-store-and-strict-layout.md)).

### Deno (runtime)

`package.json` and `deno.json` are first-class and composable: package dependencies and scripts come from the former, while Deno tool configuration and import maps come from the latter. `npm:<name>[@<range>][/<sub-path>]` is the explicit package-specifier form. For existing Node projects Deno installs package dependencies into manual `node_modules`, runs scripts with `deno task`, honors `type`, and warns on `node`/`deno` engine mismatches. The ingested Deno guide does not specify its `exports` condition set or ordering, so claims about a `deno` condition remain pending primary-source backing.

### Endo `@endo/compartment-mapper` (runtime)

Reads `name`, `type`, `main`, `exports`, `browser`, `dependencies`, and `files` (source: compartment-mapper README at `46d4edf`). Only three conditions are supported: `import` (prefer ESM over CJS), `browser` (also swaps in the `browser` property over `main`), and `endo` (signals the tool is in use). If no `exports` applies to `"."`, `main` is the default. `imports` and `*` patterns in `exports`/`imports` are future TODOs. A package-local `parsers` property overrides extension-to-language mapping; type-specific hooks support `.ts` as `.cts` or `.mts` semantics.

### TypeScript (compiler)

Reads `types`/`typings` and `typesVersions`, subject to a key precedence boundary: `typesVersions` is not read when the modern `exports` path is active. Under `moduleResolution` `node16`/`nodenext`/`bundler`, TypeScript reads `exports`, always matches `types` and `default`, and chooses `import` or `require` based on the resolution context. The correct dual-package recipe nests a first `types` condition inside each `import`/`require` branch, using `.d.mts` and `.d.cts` respectively. `bundler` supports exports/imports but permits extensionless and directory paths; `node16`/`nodenext` model Node's strict ESM paths and pair with Node-aware `module` settings. Sources: [`declaration-publishing`](../../library/sources/typescript-website--packages-documentation-copy-en-declaration-files-publishing.md), [`modules-reference`](../../library/sources/typescript-website--packages-documentation-copy-en-modules-reference-reference.md) (`c8170c35`).

### Bundlers and compilers (webpack, Rollup, esbuild, Vite, Turbopack, Parcel, swc, Babel)

Resolver-bundlers honor `exports` (with a bundler-chosen, usually configurable condition set), the legacy `main`/`module`/`browser` fallback chain used when `exports` is absent, and `sideEffects` for tree-shaking. `module` is a de-facto standard for "the ESM build" (an unadopted Node ESM proposal that bundlers took up) preferred over `main` for better tree-shaking. The condition set and default `mainFields` **differ per bundler** (a major inconsistency; see the inconsistencies topic). All eight are now library-backed:

- **webpack** ([resolve](../../library/sections/webpack--config-resolve--main-fields-and-condition-names.md), [tree-shaking](../../library/sections/webpack--guides-tree-shaking--sideeffects-flag.md)): `resolve.conditionNames` is composed dynamically — base `["webpack", <mode>, <target-condition>]` (e.g. `["webpack", "production", "browser"]` for a production web build) plus per-dependency-type conditions (`["import", "module-sync", "module", "..."]` for ESM, `["require", ...]` for CJS). `resolve.mainFields` defaults to `["browser", "module", "main"]` for web targets and `["module", "main"]` for node. `resolve.exportsFields`/`importsFields`/`aliasFields` name which manifest fields drive `exports`/`imports`/`browser`. `sideEffects: false` prunes whole unused modules; an array names side-effectful file globs to keep.
- **Rollup** (via [`@rollup/plugin-node-resolve`](../../library/sections/rollup--node-resolve-readme--export-conditions-main-fields-and-browser.md)): Rollup itself reads no manifest; the plugin honors `exports`/`imports` by default with a base condition set `['default', 'module', 'import', 'development|production']` (`['default', 'module', 'require']` for requires with `@rollup/plugin-commonjs` v16+). `exportConditions` adds conditions (set `['node']` for Node behavior); `mainFields` defaults to `['module', 'main']` and is used only when `exports` is absent; the `browser` option adds `browser` to conditions/mainFields and takes precedence over `mainFields`.
- **esbuild** ([conditions/main-fields/packages](../../library/sections/web--esbuild-api--conditions-main-fields-and-packages.md), [tree-shaking](../../library/sections/web--esbuild-api--tree-shaking-and-sideeffects.md)): conditions are platform-derived — `import`/`require` by import kind, `browser` only when `platform: browser`, `node` only when `platform: node`, and the bundler `module` condition auto-included for browser/node **only when no custom `--conditions` are configured**. Default `mainFields` depend on `platform`. `--packages=external` marks every bare dependency external in one flag. esbuild respects the `sideEffects` field and `/* @__PURE__ */` for any imported file; `--ignore-annotations` disables both.
- **Vite** ([shared](../../library/sections/vite--config-shared-options--resolve-conditions-main-fields-and-dedupe.md), [ssr](../../library/sections/vite--config-ssr-options--ssr-conditions-and-externalization.md), [dep-optimization](../../library/sections/vite--config-dep-optimization-options--optimizedeps-dependency-prebundling.md)): client resolution uses `resolve.conditions` = `['module', 'browser', 'development|production']` (`defaultClientConditions`) and `resolve.mainFields` = `['browser', 'module', 'jsnext:main', 'jsnext']`; `import`/`require`/`default` always apply on top. SSR swaps in `ssr.resolve.conditions` = `['module', 'node', 'development|production']` (`node` in place of `browser`) with `ssr.resolve.externalConditions` = `['node', 'module-sync']`; `ssr.external`/`ssr.noExternal` decide which dependencies are bundled versus left as runtime imports. `mainFields` is ignored whenever `exports` resolves an entry. Tree-shaking rides its underlying esbuild/Rollup passes. Separately, the dev-only **`optimizeDeps`** pre-bundler discovers a project's bare `node_modules` dependencies (crawling `.html`/`input`/`entries`), converts CommonJS/UMD packages to ESM, and caches them — with `include`/`exclude`/`noDiscovery`/`holdUntilCrawlEnd`/`needsInterop`/`force` controls; this is how Vite consumes a CJS-only package that publishes no ESM `exports`/`module` entry.
- **Parcel** ([dependency-resolution](../../library/sections/web--parcel-dependency-resolution--entries-order-exports-and-conditions.md), [aliases/specifiers](../../library/sections/web--parcel-dependency-resolution--aliases-source-field-and-specifiers.md), [targets](../../library/sections/web--parcel-targets--targets-source-engines-and-output-format.md), [production](../../library/sections/web--parcel-production--tree-shaking-and-scope-hoisting.md)): package-entry precedence is `source` → `exports` → `browser` → `module` → `main`. `exports` is **opt-in** (enabled per project via the `@parcel/resolver-default` `packageExports` flag) and, when active, resolves an ordered condition set (`import`/`require`/`module`, style conditions, `node`/`browser`/`worker`/`worklet`/`electron`, `development`/`production`, `default`) in manifest key order. Reads `imports` (`#`-prefixed) and `browser` (string/object). Parcel-specific: the `alias` field (package/file/glob/shim/global forms), the `source` field (compile-from-source for symlinked packages), and the distinctive **`targets`** field — the built-in `main`/`module`/`browser`/`types` targets read their like-named manifest field as the output entry, where `main` outputs CJS (ESM when `"type": "module"`/`.mjs`), `module` ESM, `browser` a CJS browser override, `types` declarations; environment comes from `engines` (`node`, `browsers`) and `browserslist`. Tree shaking is documented as whole-program static analysis + scope hoisting; the `sideEffects` field is **not** documented (see the [production section](../../library/sections/web--parcel-production--tree-shaking-and-scope-hoisting.md)).
- **Turbopack** ([Next.js `turbopack` config](../../library/sections/web--nextjs-turbopack-config--module-resolution-aliases-and-extensions.md)): the public config reference documents `resolveAlias` (Node-style conditional aliasing, but only the `browser` condition today), `resolveExtensions` (default `['.mdx', '.tsx', '.ts', '.jsx', '.js', '.mjs', '.json']`, overwritten wholesale when set), and loader-rule `condition` built-ins (`browser`, `foreign` = `node_modules`, `development`, `production`, `node`, `edge-light`). It resolves `exports`/`imports`/`browser`/`module`/`main` in a webpack-compatible manner but does **not** publicly enumerate an `exports` condition set or a `mainFields` chain — the one honest gap remaining in the bundler rows.
- **swc** ([compilation](../../library/sections/web--swc-compilation--compiler-not-resolver-env-targets-and-module.md)) and **Babel** ([options](../../library/sections/web--babel-options--compiler-not-resolver-browserslist-and-sourcetype.md)) are **compilers/transformers, not resolvers**. Neither resolves `package.json` `exports`/`main`/`module`/`browser`; each reads its own config (swc: `.swcrc` — `jsc`/`env`/`module`/`isModule`; Babel: `babel.config.json`/`.babelrc` via `configFile`/`babelrc`/`rootMode`). Module-vs-script is chosen by swc's `module.type`/`isModule` and Babel's `sourceType`, **not** the `package.json` `type` field. The one `package.json` field in play is `browserslist`: Babel reads it (via `browserslistConfigFile`, default on) to feed `@babel/preset-env` `targets`; swc's `env.targets` takes browserslist-style queries but its docs do not describe auto-reading the manifest `browserslist` key.
