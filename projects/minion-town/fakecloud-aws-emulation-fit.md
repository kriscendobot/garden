# fakecloud as minion.town's AWS emulation tier: fit and gaps

> Abstract: fakecloud fits minion.town well, but only for a narrow slice. Its one strong win is the **DynamoDB adapter layer**. That is the only AWS SDK dependency on the app's portable path, and today its tests are marshaling-shape tests against a hand-rolled `send()` fake, so the conditional-write and exactly-once transaction semantics have never run against anything except real AWS. fakecloud's DynamoDB is Full/Full with transactions. **Cognito** is a real fidelity upgrade for CI: fakecloud issues Cognito-shaped RS256 tokens and runs the PreTokenGeneration Lambda, while the current `oauth2-mock-server` harness hand-imitates Cognito claims (it even sets an RFC 8707 `aud` that real Cognito never issues). **Secrets Manager** and **S3** fit but matter little, since they are touched only by deploy tooling and one Lambda. The **gaps** are the SSM `send-command` deploy delivery (SSM's data plane is Partial, and Run Command execution is not documented), App Runner in the CDK stack (not emulated), and IAM `dynamodb:Attributes` condition-key enforcement (not documented). Recommendation: add a fakecloud-backed DynamoDB integration tier in CI (follow-on build job below). Keep `mock-as` for Docker-free `npm run dev`. Written 2026-09-28 by `scholar-ingest-fakecloud-dev` against minion.town `main` @ `f69bf87` (2026-09-27).

## 1. What minion.town actually touches in AWS (surveyed, not taken from the README)

The project README lists the AWS services as "DynamoDB account store, Cognito, Secrets Manager, S3 presigned artifacts". Surveying the repo confirms that list, but splits it into three very different layers:

| Layer | Service use | Where |
|---|---|---|
| **App runtime, portable path** (`src/`) | **DynamoDB only.** `@aws-sdk/client-dynamodb` is the sole AWS SDK dependency in `package.json`. It is imported lazily (`await import(...)`) and only when `ACCOUNT_STORE=dynamodb`. | `src/auth/stores/dynamodb.ts` (account store: `GetItem`, `PutItem` with `attribute_not_exists(iss)`, `UpdateItem`, AES-256-GCM sealed recovery material). `src/billing/stores/dynamodb.ts` (credit ledger: one `TransactWriteItems` made of a `Put` marker conditioned `attribute_not_exists(session_id)` plus an `Update` `ADD credits :c` conditioned `attribute_exists(iss)`, then a `ConsistentRead` `GetItem`. A duplicate is detected from `TransactionCanceledException.CancellationReasons`). |
| **App runtime, protocol-level** | **Cognito as OAuth AS / OIDC issuer**, reached over HTTP rather than through an SDK: the JWKS is fetched with `jose`, and `iss`+expiry are checked. Audience binding is replaced by a `client_id` allowlist, because Cognito access tokens cannot carry the resource URL in `aud`. | `src/auth/verifier.ts`. Secrets such as `minion/account-endpoint-token` arrive as env vars rendered from Secrets Manager at deploy time, so `src/` never calls Secrets Manager. |
| **Deploy and infra tooling** (not unit-tested) | AWS CLI calls in `deploy/aws/scripts/*.sh`, most frequent first: `secretsmanager get-secret-value/describe-secret/create-secret`; `s3 presign` (8 sites), `s3 cp/rm`, `s3api create-bucket/head-bucket/put-public-access-block/head-object`; `iam create-role/put-role-policy/attach-role-policy/get-role`; `lambda create-function/update-function-code/add-permission/wait`; `cognito-idp describe/update-user-pool(-client)`, `create/update-identity-provider`, `update-resource-server`; `dynamodb create-table/update-table/update-time-to-live/describe-table/wait/get-item/update-item/scan`; `ssm send-command/get-command-invocation`; `route53 change-resource-record-sets`. The CDK stack (`infra/lib/minion-town-stack.ts`) declares `cognito.UserPool`, a Route 53 zone, and an **App Runner** service. The stack's own header says it has not been synthesized or deployed; the live box is EC2 driven through SSM. | Lambdas: `deploy/aws/lambda/github-oidc-thunk/src/secret.js` (Secrets Manager `GetSecretValue`, the only other AWS SDK import) and `deploy/aws/lambda/pre-token-gen/` (pure claim enrichment plus a zero-dependency `self-test.js`). SIWE thunk: `deploy/thunks/siwe/adapters/{dynamodb-store,lambda}.js`. |

**How the tests cover this today.** No test uses LocalStack, DynamoDB Local, Moto, or any other emulator (the repo contains none of them). The AWS-adjacent tests are:

- `test/accounts.test.ts` (17 cases) runs only `makeInMemoryAccountStore`. **The DynamoDB account adapter has no test at all.** It also builds its own `DynamoDBClient`, with no injectable-client seam.
- `test/billing.test.ts` (27 cases) runs the in-memory ledger. It checks the DynamoDB ledger (`makeDynamoCreditLedger`) through an injected `{ send(cmd) }` fake that captures commands and asserts their **marshaled shape**: table names, the `ConditionExpression` strings, and `ADD credits :c`. It also *fabricates* a `TransactionCanceledException` with `CancellationReasons: [{Code:"ConditionalCheckFailed"},{Code:"None"}]` to test the duplicate-mapping branch. So the code's assumptions about how real DynamoDB orders and reports cancellation reasons are asserted, never observed.
- `test/auth.test.ts`, `test/endo-guest-http.test.ts`, and `test/endo-guest-memory-http.test.ts` run the verifier against `dev/mock-as.ts`, an `oauth2-mock-server` wrapper. It threads `sub`/`idp`/`email`/`client_id` into tokens "exactly as a real IdP (Cognito…) would", and it also sets `aud` to the RFC 8707 `resource`, which real Cognito access tokens do **not** do. `test/account-endpoint.test.ts` and `test/claude-submit.test.ts` hard-code Cognito-shaped `iss` strings.
- The Lambdas: `pre-token-gen/self-test.js` tests the pure `enrich` function. The SIWE thunk has its own `siwe-verify`/`oidc-face` tests. The `claude-*` tests (account endpoint, credentials, quota, reauth, links, wiring) exercise no AWS service. Credentials are kept deliberately out of DynamoDB (`src/endo/claude/credentials.ts` secret-hygiene note).

So the README's "the same code runs locally against a mock AS" holds for **auth**. For **storage** it holds only by *substitution*: locally the in-memory store replaces the DynamoDB adapter, so the adapter itself runs nowhere but production.

## 2. Service-by-service fit against fakecloud

The parity column below uses the matrix's own control-plane and data-plane grading. Its conformance headline ("248,557/248,557 variants") certifies API *shape*, not behavior ([conformance vs behavior parity](../../library/sections/web--fakecloud-parity--conformance-versus-behavior-parity.md)).

| Service (minion.town use) | fakecloud status | Fit | Notes |
|---|---|---|---|
| **DynamoDB** (account store, credit ledger, SIWE nonce store; tables created by deploy scripts) | Full / Full, 57 ops. Transactions, PartiQL, streams, TTL-bearing `UpdateTable` family. IAM-enforced under `--iam strict` ([core-service rows](../../library/sections/web--fakecloud-parity--core-service-parity-rows.md), [identity/data services](../../library/sections/web--fakecloud-llms-txt--identity-data-and-secrets-services.md)) | **Close; highest value** | Would run the real conditional `PutItem`, the two-action `TransactWriteItems`, the `ADD` update, and `ConsistentRead` read-back. This turns the ledger's exactly-once, duplicate, and missing-account branches from asserted-shape into observed-behavior tests, and gives the untested account adapter its first test. **Verify in the build job:** that fakecloud fills `CancellationReasons` per action the way AWS does (not documented either way). |
| **IAM condition keys** (`dynamodb:Attributes` scoping the serving role's `UpdateItem` to `credits`, which is the "admin ceiling survives billing" invariant) | DynamoDB IAM enforcement documents action/resource mapping, per-table batch and transaction checks, and **tag conditions**. The `dynamodb:Attributes` / `LeadingKeys` condition keys are **not mentioned** ([identity/data services](../../library/sections/web--fakecloud-llms-txt--identity-data-and-secrets-services.md)) | **Gap (unverified)** | Do not treat a fakecloud pass as proof of the attribute-scoped ceiling until a negative test (role tries to `SET role = …` and must be denied) passes under `--iam strict`. |
| **Cognito User Pools** (AS/issuer, resource-server scopes, app clients, OIDC IdPs for GitHub/SIWE, PreTokenGeneration Lambda) | Full / Full, 132 ops. Real RS256 JWTs, JWKS and OIDC discovery, `/oauth2/token`, `/authorize`, `/userInfo`, `/revoke`. **The PreTokenGeneration trigger invokes the configured Lambda and merges claims.** OIDC identity providers and resource servers present ([core-service rows](../../library/sections/web--fakecloud-parity--core-service-parity-rows.md)). Confirmation codes are exposed at `/_fakecloud/cognito/confirmation-codes` ([test introspection](../../library/sections/web--fakecloud-llms-txt--test-introspection-endpoints-and-sdks.md)) | **Close; real fidelity upgrade for CI** | A Cognito-faithful issuer would test the verifier's documented `client_id`-allowlist deviation against Cognito's real token shape, where `mock-as` injects an `aud` Cognito never sends. It would also run the actual pre-token-gen Lambda end to end instead of only its pure function. **Gaps:** the issuer URL is localhost, not `cognito-idp.<region>.amazonaws.com/<pool>` (fine, since the verifier reads `issuer`/`jwksUri` from config, but the hard-coded `ISS` strings in tests would stay synthetic). Trigger Lambdas need Docker ([positioning](../../library/sections/web--fakecloud-llms-txt--positioning-and-conformance-claims.md)). Federation out to the GitHub OIDC thunk or the SIWE thunk means Cognito calling an external IdP, which the ingested pages do not document. |
| **Secrets Manager** (github-oidc-thunk `GetSecretValue`; deploy scripts' create/describe/get) | Full / Full, 23 ops, plus rotation via Lambda and real KMS ([core-service rows](../../library/sections/web--fakecloud-parity--core-service-parity-rows.md)) | Close; low value | Useful for rehearsing the deploy scripts' create-if-absent idempotency, and for a thunk test that no longer needs a stub. |
| **S3 presigned artifacts** (deploy only: tarball → `s3 cp` → `s3 presign` → GET on the box) | S3 Full / Full, 107 ops. `--verify-sigv4` flag exists ([install/config](../../library/sections/web--fakecloud-llms-txt--install-and-configuration.md)). **Presigned-URL (SigV4 query-auth) behavior is not called out** on the parity page ([core-service rows](../../library/sections/web--fakecloud-parity--core-service-parity-rows.md)) | Probable; unverified | Only the deploy pipeline uses it, so it matters only if deploy rehearsal is adopted. |
| **SSM `send-command`** (the deploy delivery mechanism onto EC2) | SSM Full / **Partial**. The Session Manager data plane is not implemented, and whether `AWS-RunShellScript` executes on a target is not stated. EC2 instances run as containers executing user-data ([core-service rows](../../library/sections/web--fakecloud-parity--core-service-parity-rows.md)) | **Gap** | An end-to-end deploy rehearsal (scripts → SSM → box) is not supported by what fakecloud documents. |
| **Lambda / IAM / Route 53** (deploy scripts) | Full / Full, real Docker execution; Route 53 with an opt-in local DNS resolver | Close (deploy rehearsal only) | Could rehearse the scripts' control-plane idempotency, not production behavior. |
| **App Runner** (`infra/` CDK stack) | **Not in fakecloud's service list** ([identity/data services](../../library/sections/web--fakecloud-llms-txt--identity-data-and-secrets-services.md)). CloudFormation is emulated | Gap (low stakes) | The CDK stack is documented as un-synthesized and is not the live path. |
| Stripe (billing) | Not AWS | n/a | Already faked in-process (`fakeCheckout`, signature-only `Stripe` client). |

The fakecloud [never-implement list](../../library/sections/web--fakecloud-parity--will-never-implement.md) (real CA, public DNS, outbound email/SMS, edge network) does not intersect minion.town's tested surface. Its ACM and Route 53 caveats would matter only for a TLS/DNS deploy rehearsal, which Caddy's ACME path handles outside AWS anyway.

## 3. Recommendation (for the liaison to post; the scholar does not build)

**Adopt fakecloud as an opt-in CI integration tier for the DynamoDB adapters. Do not replace `mock-as` or the in-memory stores.** The portable-path design is sound: the in-memory stores stay the fast default, and `npm run dev` stays Docker-free and cloud-free as the README promises. fakecloud fills the one hole that design leaves, which is that the AWS adapter code never runs outside production.

- **Follow-on build job (suggested base `build-minion-town-fakecloud-dynamodb-tier`):** in kriscendobot/minion.town, add a vitest integration suite, gated on an env var such as `FAKECLOUD_URL` so the default `npm test` is unchanged, plus a CI job that runs `ghcr.io/faiscadev/fakecloud` pinned by version or digest. It would:
  1. create the accounts and billing-events tables with the key schema the deploy scripts use;
  2. exercise `src/auth/stores/dynamodb.ts` (first-ever coverage; will need an endpoint seam or `AWS_ENDPOINT_URL_DYNAMODB`, which recent AWS SDK v3 releases honor, to be confirmed in the job) for create-once, conflict, and update;
  3. exercise `makeDynamoCreditLedger.creditOnce` for applied, duplicate (`applied:false`, balance unchanged), and missing-account (rethrow), asserting against real `CancellationReasons`;
  4. `POST /_fakecloud/reset` between tests ([test introspection](../../library/sections/web--fakecloud-llms-txt--test-introspection-endpoints-and-sdks.md)).

  Use raw HTTP for reset rather than the `fakecloud` npm SDK until that SDK's license is checked. fakecloud itself is AGPL-3.0, which is harmless as an external test process but deserves a look before adding a devDependency.
- **Optional second job (suggested base `build-minion-town-fakecloud-cognito-tier`):** a CI-only auth tier that stands up a fakecloud user pool, resource server, and app client and runs the verifier against real Cognito-shaped tokens, including the pre-token-gen Lambda (Docker required). Its first deliverable should be an assertion that the token lacks `aud`, which pins down the allowlist deviation `mock-as` currently hides.
- **Not recommended now:** a full deploy rehearsal against fakecloud. SSM Run Command delivery and App Runner are the gaps above.
- **Separate, real-AWS verification still needed:** the `dynamodb:Attributes` IAM ceiling, unless a fakecloud negative test demonstrates enforcement.
