  Twenty-third comment-fragment ingest. The 300-line file is the
  *legacy-guard-tolerance adapter layer* that cycle 118's
  exo-tools.js defendPrototype imports `getInterfaceGuardPayload`
  from. Solves *one problem at three granularities*: extract the
  typed payload from a guard that might be in the pre-1712
  `klass:`-discriminator record shape OR the post-1712 `payload:`
  envelope shape.

  The §pre-1712-vs-post-1712 worldview shift: PR #1712
  (https://github.com/endojs/endo/pull/1712) changed guards from
  raw records (`{ klass: 'methodGuard', callKind: 'sync',
  argGuards, returnGuard }`) to wrapped envelopes
  (`methodGuard.payload = { callKind, argGuards, returnGuard }`).
  The `get*GuardPayload` adapters normalize both forms to the
  post-1712 payload shape. End-of-life marker explicit: *At such
  a time that we decide we no longer need to support code
  preceding PR #1712 or guard data generated by that code, all
  the adaptation complexity in this file should be deleted*.

  §three-granularities adapter chain (bottom-up): (1) `getAwait-
  ArgGuardPayload` — leaf with `LegacyAwaitArgGuardShape`; (2)
  `getMethodGuardPayload` — middle with `LegacyMethodGuardShape`
  (union of `LegacySyncMethodGuardShape` and `LegacyAsyncMethod-
  GuardShape`); (3) `getInterfaceGuardPayload` — top with
  `LegacyInterfaceGuardShape`. The pattern repeats at each level:
  *match-current-or-legacy → destructure → recursively-adapt-
  children → harden → re-validate*.

  §single most structurally interesting subtlety: the §exploitable-
  bug warning vs §why-this-isn't-exploitable distinction. The
  §AwaitArgGuard adapter carries an *exploitable-bug-acknowledged*
  warning — *a record that matches LegacyAwaitArgGuardShape is
  also a valid parameter pattern that should allow an argument
  that matches that pattern*. The §method-guard and §interface-
  guard adapters are NOT exploitable because *there is not
  currently any context where either a methodGuard or a
  copyRecord would both be meaningful*. The *shape-collision-only-
  matters-where-overlap-exists* discipline.

  §nine *TODO manually maintain correspondence* markers (seven
  Legacy shapes × 1 marker each + the AwaitArgGuard one and a
  cross-cutting general comment) — the canonical abstraction-
  debt-marker idiom. Each Legacy shape must stay in sync with its
  current counterpart by hand because legacy shapes are frozen
  (callers may emit them) and current shapes evolve.

  §one-place-the-correspondence-is-natural exception: no
  `LegacyRawGuardShape` — raw guards were introduced in PR #1831,
  *well after* PR #1712, so *there was never a `klass:` form of
  the raw guard*. Cycle 118 sees post-1712 raw guards directly,
  without legacy translation.

  §`adaptMethodGuard` re-builder — legacy methodGuard
  reconstructed by calling the public builder chain (`M.call(...)`
  or `M.callWhen(...)` depending on sync/async, then `.optional`,
  `.rest`, `.returns`). The §builder-chain-restores-the-current-
  shape discipline keeps the upgrade tracking-free even when the
  internal shape changes.

  §`getInterfaceMethodKeys` + §`getNamedMethodGuards` introspection
  surface — `getInterfaceMethodKeys` returns *union of string-named
  and symbol-named method keys* (uses `Reflect.ownKeys` for
  strings + `getCopyMapKeys` from cycle 102's checkKey for
  symbols, with `emptyCopyMap` sentinel for symbol-free cases);
  `getNamedMethodGuards` returns *only string-named method guards*
  for the *interface-guard inheritance pattern* (canonical
  `M.interface('I2', { ...getNamedMethodGuards(I1), doMore: ... })`
  spread idiom). The §symbol-named-methods-are-deprecated note
  pairs with cycle 118's symbolMethodGuards handling.

  §use of `mustMatch` as *internal-consistency-post-check* — the
  §`mustMatch(payload, MethodGuardPayloadShape,
  'internalMethodGuardAdaptor')` calls at the end of the adapter
  functions are *check-that-our-reconstruction-is-internally-
  consistent* invariants. *Hoare-logic-style postcondition-on-an-
  adapter*.

  §tests-co-located-with-consumer-not-implementation discipline:
  *Because the main use case for this legacy adaptation is in
  @endo/exo or packages that depend on it, the tests for this
  legacy adaptation are found in the @endo/exo
  `test-legacy-guard-tolerance.js`*. Repeated for `getNamedMethod-
  Guards`: *Tested in @endo/exo by exo-wobbly-point.test.js since
  that's already about class inheritance, which naturally goes
  with interface inheritance*.

  The §how-this-file-serves-cycle-118 connection: cycle 118
  section 2's defendPrototype calls `getInterfaceGuardPayload` to
  extract methodGuards + symbolMethodGuards + defaultGuards +
  sloppy + interfaceName; iterates over keys returned by both for
  symmetric listDifference validation; stores the interface guard
  for later `GET_INTERFACE_GUARD` introspection. The §sloppy:
  true ↔ defaultGuards: 'passable' aliasing visible at cycle 118
  matches this file's `LegacyInterfaceGuardShape` optional
  `sloppy: M.boolean()` and `defaultGuards: M.or(M.undefined(),
  'passable', 'raw')` fields.
