# subject-routing

How dialog-db routes a capability effect to the storage that backs its subject. A subject DID says *who* but not *where*, so the runtime must both resolve a human name to a DID (name→DID, by loading a keypair) and route effects on that DID to a location (DID→storage). Three designs were weighed — carry the location in `Subject` (breaks when a Subject is rebuilt from a bare DID), a `Did → Provider` routing table in the environment (robust but shared mutable state), or filesystem layout convention (simplest but single-provider) — and the implementation is a **hybrid**: a `Router` in `Storage<S>` (the routing-table option) for DID-based dispatch, plus per-space layout convention, with a `Loader` creating providers from platform-specific `Location` address resolution and registering them under each space's DID. This is the *first* level of the two-level dispatch (by subject DID → which space); the second level (by capability → which provider within the space, generated by `#[derive(Provider)]` on `Space`) lives in the space-and-storage sections. For remotes, a `RemoteAddress` pairs a `SiteAddress` (`S3 | Ucan`) with the `subject: Did` naming which repository at the site.
