# mint-purse-money

The **canonical capability-based money example** from *Capability-Based Financial Instruments* (Miller-Morningstar-Frantz 2000) §3.4 — a complete money implementation in ~25 lines of E, built entirely from object-capability primitives plus sealer/unsealer pairs. The construction has three nested layers: **MintMaker** (a function that returns a new currency mint, with its own sealer/unsealer pair as the brand of that currency), **mint** (a per-currency object that can mint new purses of that currency), and **purse** (the per-balance object that supports `getBalance`, `sprout`, `getDecr`, and `deposit`). The deposit method is the rights-amplification step: `unsealer unseal(src getDecr)(amount)` recovers the source purse's hidden `decr` function only if the source is a same-currency purse, then decrements the source and increments the receiver. The construction is deliberately minimal — explicitly does *not* provide blinding, non-repudiation, accounting controls, or asset backing — but it demonstrably has **six security properties verifiable by visual inspection of the code** (Property 1: only mint-holders can violate currency conservation; Property 2: mint inflates only its own currency; Property 3: purse balance is protected by capability scope; Property 4: same-currency transfer works; Property 5: balances are always non-negative; Property 6: deposit-report trust is bounded by trust in the receiving purse).

This is **the most-cited single example in the capability-security literature** and the ancestor of every Agoric ERTP issuer-kit deployment. The Endo / Agoric production enactment is `@agoric/ertp`'s `makeIssuerKit` → `{ mint, brand, issuer }` triple; the structural pattern is identical — only the implementation language differs (Hardened JavaScript instead of E). The example anchors several library-defining structural claims: (1) capability-system rules + scoping rules enable *visual-inspection security proofs* (three lines of scoping arguments are sufficient to prove all six properties); (2) brand discipline = sealer/unsealer pair; (3) rights amplification by composition (two references brought together yield authority neither has alone); (4) modularity gives access control for free — every well-encapsulated abstraction is also an access abstraction.

## Common confusions

- **"This is real money implementation guidance."** The §3.4 paper's opening disclaimer is explicit: *"We are not proposing to actually do money this way!"* The example omits blinding (anonymity), non-repudiation (reliable receipts), accounting controls (catching a cheating mint), and backing by widely-valued assets. It is a *minimal* example demonstrating that capabilities can express the structure of money; production systems like Agoric ERTP add the missing properties on top of the same structural pattern.
- **"The mint can inflate any currency."** No — §3.4 Property 2 is explicit: *the mint can only inflate its own currency*. Each MintMaker invocation creates a fresh sealer/unsealer pair scoped to that one mint; no other code can reach that pair, so no other code can create envelopes that unseal in that mint's purses' deposit method.
- **"Property 6 requires trusting the network."** No — Property 6 says trust in the *deposit report* is bounded by trust in the *receiving purse's code*. The receiving purse is the depositor's own; the depositor can inspect its code or otherwise have reason to trust it. The network is not in the trust path because the receiving purse's deposit method is what verifies the source purse's same-currency claim.
- **"Visual inspection isn't a proof."** §3.4's closing argument: scoping + sealing arguments are *sufficient* given the language-level enforcement of *only connectivity begets connectivity*. The proof is informal but rigorous — the inspector identifies the load-bearing scope boundaries, verifies the sealer/unsealer never escape from same-currency purses, and concludes the six properties hold. Three lines of scoping arguments suffice. This is the *security-as-extreme-modularity* discipline applied to the canonical example.
- **"The `name` parameter is part of the security."** No — the `name` string passed to `BrandMaker pair("MarkM")` is *purely for documentation and debugging*. Strip it (along with `printOn`) and all six properties still hold. The brand's *identity* is its sealer/unsealer pair, not the string label.
- **"Agoric ERTP is just this code in JavaScript."** Closer than not. ERTP's `makeIssuerKit` produces a `{ mint, brand, issuer }` triple structurally analogous to the §3.4 mint + brand pair + (implicit) issuer. ERTP adds: `AmountMath` for fungible/non-fungible/copyBag/copySet variants (the §6.2 four-axis rights taxonomy at the type level); explicit issuer-as-third-facet (vs implicit in §3.4); cross-vat purse semantics via Pluribus / OCapN. The structural pattern is the same; ERTP is the production scaling.
