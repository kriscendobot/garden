# frb-incremental-update

The defining mechanism of `kriskowal/frb`: a derived value is maintained by applying the **delta** of each change rather than recomputing the whole result. When a value is added to or removed from a source collection, an aggregation folds only that value into the last known result (`sum()` adds/removes just the changed value's contribution; `average()` adjusts a running sum and count); a `map`/`filter`/`sorted`/`group`/`flatten` block splices only the affected elements into the output collection in their proper positions, as if the whole collection were regenerated by brute force but without the cost. A key invariant follows: the **identity of a bound output collection never changes**, because every change is applied in place rather than by reassigning a freshly-built array. FRB calls this property "incremental," one of its six self-described adjectives (functional, generic, reactive, synchronous, incremental, unwrapped). Incrementality is what makes long query chains affordable: `departments.map{employees.sum{salary}}.sum()` updates by the delta of one salary change, not by re-summing the company. Changes enter at the collections layer as typed change records (property, ranged-content, mapped-content) and propagate through the compiled observer tree so each stage needs only the delta. Not every operator is incremental (`has` is recomputed, though cheap on the right data structure), but the bias of the library is delta-maintenance.

## Common confusions

- Incremental update is not the same as memoization or caching: there is no recompute-and-compare. The collection itself emits a typed delta (a splice/swap/range change) that the observer consumes directly.
- `has` (membership) is **not** incremental; it recomputes on change, but is cheap on a Set-like data structure. Incrementality is the bias of the library, not a guarantee for every operator.
