# Topic: xs-agent-runtimes

> Abstract: Running LLM **agents** (the tool-choosing, stateful, schedulable program around a model, not the model itself) inside Moddable's **XS** JavaScript engine, one small confined XS machine per agent, with a native host supplying the only capabilities and XS **heap snapshots** making an agent's whole live state a file that survives process exit and moves between machines. Seeded 2026-09-25 from two articles on **KaozKit** (Sébastien Burel's author account and Peter Hoddie's Moddable vendor post). Distinct from `llm-agent-frameworks` (Node/Python harnesses such as LangChain/LangGraph, which KaozKit positions itself against), from `persistence` (Endo/Agoric heap/virtual/durable regimes, where heap snapshots are one mechanism among several), and from the garden's own XS use (Iron Horse's XS oracle, endo-but-for-bots XS workers), which the cross-reference block below maps.

## Agreement and divergence between the two sources

Both describe the same project and agree on the core claims: XS is small enough to embed one engine per agent; the engine exposes no ambient I/O, so authority is added host function by host function rather than removed; API keys and OS access live in the Swift host; heap snapshots persist agents across process exit and machines. They differ where the vendor post is a summary: Hoddie adds a **no-known-vulnerabilities** claim for XS and says agents are **notified on suspend/resume** and that cross-device resume needs **a compatible KaozKit version**; only Burel describes one-machine-per-agent sub-agents, the synchronous-handler **Agha actor** framework, the tool allow-list policy, and the **LGPL-v3 / commercial-license** split. Full comparison on each source page ([Burel](../sources/web--haruni-kaozkit-xs-agents.md), [Hoddie](../sources/web--moddable-kaozkit.md)).

## Garden cross-references (ranked by relevance, as of 2026-09-25)

1. **Endo XS-worker snapshot design.** endo-but-for-bots `designs/daemon-xs-worker-snapshot.md` ([source](../sources/endo-but-for-bots--llm-designs-daemon-xs-worker-snapshot.md); In Progress, Phase 1 done) is the same mechanism KaozKit ships, reached independently, and it is more explicit on the hard parts: **suspend only when idle** (so no in-flight host call or CapTP session is frozen), snapshots streamed into **CAS** with ephemeral GC roots, an **append-only host-callback table** so function indices stay stable across resume, and three named incompatibility axes (XS version, architecture, callback-table layout). KaozKit's "copy the file to another machine" and "compatible version of KaozKit" are the informal versions of those axes. The sibling designs [worker-rust-xs](../sources/endo-but-for-bots--llm-designs-worker-rust-xs.md) (Rust host embedding XS, XS-native `Compartment` confinement plus cap-std, host functions in-process: architecturally KaozKit's Swift-host shape) and [xs-worker-metering](../sources/endo-but-for-bots--llm-designs-daemon-xs-worker-metering.md) (admission-control metering, re-create from snapshot on hard-limit abort) cover what KaozKit does not mention: **metering** a runaway agent.
2. **Agent confinement on minion.town.** kriscendobot/minion.town#87 (closed) wired the Claude-agents capability as an attenuated `@claude-agents` factory with a per-principal credential store whose token never enters mail/logs/MCP output; #106 (open, parked) is the Agent-SDK prototype whose Gap 1 is the lack of a credential broker (an `ANTHROPIC_API_KEY` in a root-owned env file), and #115/#116 (open) are the Codex drafts, where #116's Gap 1 is that CLI confinement is a *deny-list* a CLI upgrade can widen. KaozKit's rule that **API keys are resolved host-side and never enter JavaScript**, and its **no-default-services allow-list host**, are the positive form of both gaps: the agent program holds a `host.llm` capability, never a key, and has nothing to deny. Where KaozKit is *weaker* than the Endo model: its `host` global is one ambient-per-agent surface and tools are named by string, so an agent cannot attenuate or delegate a narrower capability to a sub-agent; Endo guests receive and pass object references (and the pending guest `invite`/`accept` work, endojs/endo-but-for-bots#1125, is exactly delegation between guests).
3. **XS as the garden's oracle and target.** The Iron Horse XS-in-Rust port differentially fuzzes against `xst`; the garden has found XS behavioral divergences there (non-shortest `fx_dtoa` for large-integer doubles, harness truncation artifacts), which bear on Hoddie's "no known security vulnerabilities" only as a reminder that correctness and escape-freedom are separate claims. [xs-debugging](../../../skills/xs-debugging/SKILL.md) (garden skill) covers XS value-stack overflow, relevant to anyone running many small XS machines with small default stacks. `test:xs` in endo-but-for-bots `packages/exo-stream` is still the stub `exit 0`; the parked #1100 follow-up (projects/endo-but-for-bots/followups/endo-but-for-bots--1100.md) needs Moddable 9.0.0 `xst` for a real run. KaozKit's recipe (symlink a subset of a local Moddable checkout into a SwiftPM build) is one more data point that a pinned Moddable checkout is the practical XS dependency, which the garden sandbox does not yet provision.
4. **Actors with synchronous handlers.** Burel's invariant (no `await` inside a handler; all async work in and out by message) is E's turn-based plan-interference discipline restated; see [distributed-objects](distributed-objects.md) for the actor/vat lineage. No Agha-specific page exists yet.
5. **Resident, scheduled agents.** `host.schedule` timers that fire after a restart are the in-heap analogue of [scheduled-agent-tasks](scheduled-agent-tasks.md); the garden's own fleet instead keeps durable state in the journal (git) and re-derives it on restart ([agent-fleet-durability](agent-fleet-durability.md)), the "serialize explicitly" style KaozKit argues against. The two are not in contradiction: whole-heap snapshots fit a single-owner local agent; a multi-host fleet needs inspectable, mergeable state.
