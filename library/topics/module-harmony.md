# Topic: module-harmony

> Abstract: The **module harmony** family of TC39 proposals that jointly reshape how JavaScript modules are compiled, phased, reified as first-class values, and virtualized — **source phase imports** (`import source`, `ModuleSource`, `%AbstractModuleSource%`), **import defer** (`import defer`, deferred synchronous evaluation), **module expressions** (`module { }` → a `Module` value), **module declarations** (`module x { }`, named inline modules for bundling), and the layered **Compartments** proposal (first-class `Module`/`ModuleSource`, virtual module sources, `Evaluators`, `Compartment`). The unifying idea is *phases of one module load*: `import source` / `import defer` / plain `import` all load the same module, executed at most once. This topic maps the landscape a **minimal Compartments spec must intersect** to stay coherent under module harmony; the synthesized per-proposal adopt/defer-to/stay-compatible-with analysis is the concept page [[module-harmony-intersection-surface]]. Ingested 2026-07-21 from the tc39 proposal repos (job `scholar-research-module-harmony-intersection`). Distinct from [`compartments`](compartments.md) (the SES/Endo Compartment isolation model as *implemented*, evidence not spec) and [`bundles`](bundles.md) (Endo's compartment-mapper packaging); module-harmony is the TC39-proposal-landscape axis those build toward.
