# Topic: agent-fleet-orchestration

> Abstract: Orchestrating a **fleet** of autonomous coding agents against a shared work queue — the *coordination* layer above a single agent. The defining move is to make an issue tracker (or job board) the **control plane**: every open task gets a dedicated agent running in an isolated per-task workspace, agents run continuously (restarted when they crash or stall), and humans review results rather than supervising sessions. Recurring concerns: a poll–dispatch–supervise–retry loop with bounded concurrency; a **dependency DAG** so blocked tasks wait and unblocked ones run in parallel; agents that **file their own follow-up work**; per-task filesystem isolation with safety invariants; a programmatic coding-agent protocol (headless app-server / JSON-RPC); least-authority credential handling (a scoped tracker tool, not a raw token); and the design stance that agents are given **objectives, not rigid state-machine transitions**. The canonical external example is **OpenAI's Symphony** (a `SPEC.md`-as-product orchestrator over Linear + Codex App Server). Distinct from `llm-agent-frameworks` (the single-agent build/runtime layer: LangChain/LangGraph) — this topic is the multi-agent *management* layer above it; Symphony sections are cross-filed under both.
>
> **Relation to the garden's own orchestration.** The garden is itself an agent-fleet orchestrator and is the closest in-corpus analogue, so read Symphony against it as an *independent convergent design*, noting both the parallels and the honest divergences:
>
> - **Work queue as control plane** — Symphony's Linear board ≈ the garden's git-backed job board (the `journal2` branch). Both make "every open task gets a worker" the invariant. *Divergence:* Symphony centralizes claim state in one authoritative orchestrator that reserves each issue; the garden has **no central authority** — gardeners on every host race to claim via a git-push compare-and-swap, and the accepted push is the serialization point. See [`../../../skills/job-board/SKILL.md`](../../../skills/job-board/SKILL.md).
> - **Dependency DAG** — Symphony's blocked-task DAG (unblocked tasks run in parallel) ≈ the garden's `blocked_on` + `unblock.sh` edges and its **orchestration jobs** (serial/parallel promotion of parked child jobs, with a failure policy). See [`../../../skills/orchestration/SKILL.md`](../../../skills/orchestration/SKILL.md) and the [orchestrator role](../../../roles/orchestrator/AGENT.md).
> - **Per-task workspace isolation** — Symphony's per-issue workspace + safety invariants (§9) ≈ the garden's per-job worktree (`ensure-project-worktree.sh`), keyed so peers on the same PR never share a tree.
> - **Policy as a versioned Markdown contract** — Symphony's `WORKFLOW.md` ≈ the garden's `roles/*/AGENT.md` + `skills/*/SKILL.md`, read just-in-time by the worker.
> - **Agents create their own follow-up work** — Symphony agents file new issues ≈ gardeners posting follow-on jobs.
> - **Objectives over rigid transitions** — Symphony's "give agents goals, not state-machine nodes" ≈ the garden's bounded-authority role briefs (a definition of done + skills, not a transition table).
>
> The connection is a genuine structural parallel, not a dependency: neither system builds on the other, and the claim to draw is convergent design under the same pressures (human attention as the bottleneck), not shared lineage.
