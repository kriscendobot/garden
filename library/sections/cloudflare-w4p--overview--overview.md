Abstract: Workers for Platforms is Cloudflare's product for building a **multi-tenant platform** on top of Workers: it lets a platform operator run untrusted code written by their own customers (or generated by AI) in a secure, isolated hosted sandbox, where each customer's code runs in its **own** Worker with complete separation between tenants. It targets four needs: running untrusted code at scale (deploy an unlimited number of applications), building multi-tenant platforms (each customer gets an isolated compute environment), extending Cloudflare's developer platform to customers (give each customer bindings to KV, D1, R2, and more through the operator's platform), and giving each application its own domain (a subdomain of the operator's domain or an integrated custom hostname). The management tooling it adds over plain Workers is custom limits (per-customer CPU-time and subrequest caps), observability (logs and metrics across all user Workers, exportable to Datadog/Splunk/Grafana), and tags (organize, search, and filter user Workers by customer ID, plan type, or environment).

## What Workers for Platforms is

Workers for Platforms lets you run untrusted code written by your customers, or by AI, in a secure hosted sandbox. Each customer runs code in their own Worker, a secure and isolated environment. The operator builds a multi-tenant platform that runs untrusted code in secure, isolated sandboxes.

## When to use Workers for Platforms

Use Workers for Platforms when you need to:

- **Run untrusted code at scale** — execute code written by your customers or generated by AI in a secure sandbox, with the ability to deploy an unlimited number of applications.
- **Build multi-tenant platforms** — give each customer their own isolated compute environment with complete separation between tenants.
- **Extend Cloudflare's developer platform to your customers** — use bindings to give each customer access to KV stores, D1 databases, R2 storage, and more. Your customers get the same tools, managed through your platform.
- **Give each application its own domain** — host applications under a subdomain of your domain (for example, `customer-name.myplatform.com`) or integrate with custom hostnames to allow customers to use their own domains.

## Features

Workers for Platforms provides tools to manage and control your customers' code:

- **Custom limits** — set per-customer limits on CPU time and subrequests.
- **Observability** — collect logs and metrics across all user Workers in your namespace; export to third-party platforms like Datadog, Splunk, and Grafana.
- **Tags** — organize, search, and filter user Workers by custom tags like customer ID, plan type, or environment.

The next architectural step (see the *how-it-works* sections) is that the operator provisions a **dispatch namespace** to hold customer Workers, writes a **dynamic dispatch Worker** to route requests to them, deploys **user Workers** on customers' behalf, and optionally adds an **outbound Worker** to control egress.
