The 444-line `packages/whylip/src/hooks/useConversation.js` is the React hook that implements Whylip's complete conversation state machine. It manages the local `ConversationTree` instance (backed by `MemoryBackend`, hard-coded — no abstraction layer), syncs that tree from the CapTP mailbox in two phases (batch initialization from `listMessages()`, then live streaming via `followMessages()`), and provides `send`, `navigateTo`, and parsed-node state to the rendering components. The hook is the implementation grounding for the dual-backend architectural framing introduced in cycle 443's README ingest: `MemoryBackend` is not chosen via config — it is the only backend the hook ever constructs. The `EndoPetstoreBackend` lives exclusively in Fae (daemon side). §the-named-memory-backend-hardcoded-not-configured names the architectural lock-in.

The `parseResponse` function (lines 72-160) is a three-tier LLM response parser: (1) direct `JSON.parse` of the trimmed text (with code-fence stripping); (2) greedy regex extraction of the first `{...}` block, then `JSON.parse` of that match; (3) targeted field-level regexes for `"narrative"` and `"scene"` fields using `lenientUnescape` to handle non-standard escapes like `\'` that LLMs produce when embedding JavaScript inside JSON strings. The total fallback — if the text starts with `{` and contains `"narrative"` but still cannot be parsed — returns `method: 'raw'` with a `parseError` string that describes what went wrong. The result shape (`{ narrative, scene, method, parseError? }`) is typed via `@typedef ParsedResponse`. This cascade handles the full surface of real LLM output including code-fenced JSON, double-encoded JSON strings, and JavaScript single-quote escapes. §the-named-three-tier-parse-cascade-for-llm-output names the pattern.

**The single most structurally interesting move for cycle 452 (100-cycle milestone): §the-named-format-retry-as-client-side-llm-correction-protocol.** When `parseResponse` returns a `parseError` (the response looked like JSON but failed to parse) and `formatRetryRef.current < MAX_FORMAT_RETRIES` (currently 1), the hook does NOT display the bad response. Instead it sends the error back to the Fae agent as a message:

```
FORMAT_ERROR: ${parsed.parseError}\n\nHere is your previous response that failed to parse:\n${text}
```

The Fae agent receives this as an ordinary user message and retries with a corrected format. The hook sets `activeNarrative` to `'Reformatting response...'` while the retry is in flight. This is a client-side error-correction loop that uses the same CapTP message channel as normal conversation turns — no special protocol, no Fae-side awareness required. `MAX_FORMAT_RETRIES = 1` prevents infinite correction loops while still giving the LLM one attempt to self-correct. §the-named-parse-error-as-injected-user-message (the error report arrives at Fae as an ordinary message from the user petname, not a system event). §the-named-single-retry-cap-for-correction-loop as tier-3 meta-pattern: the max-retry constant is the load-bearing correctness constraint — without it, a consistently-malformed LLM could loop the hook forever.

The initialization sequence (lines 244-291) maps endo mailbox messages to conversation tree nodes in the order returned by `listMessages()`, using a `messageToNodeId` Map to reconstruct parent-child threading from the `replyTo` field. Messages sent by the user (`fromId === selfId`, where `selfId` comes from `E(powers).locate('@self')`) are mapped to `role: 'user'`; all others map to `role: 'assistant'`. The threading reconstruction is exact: each `replyTo` messageId must be in `messageToNodeId` before it can be used as a `parentId`. Root messages (no `replyTo` or `replyTo` not yet seen) get `parentId: null`. This mailbox-to-tree reconstruction is the mechanism behind cycle 443's observation that `MemoryBackend` is "reconstructed from the mailbox on each page load" — it is a deterministic replay of the mailbox ordering. §the-named-mailbox-ordering-as-tree-reconstruction-invariant.

The live streaming phase (lines 294-375) uses `followMessages()` via an async iterator adapter over `E(iterRef).next()` — the same indirect-call pattern used throughout the CapTP layer to avoid holding a direct reference to the iterator. New messages arriving during streaming are deduplicated against `messageToNodeId` (messages seen during init are skipped). Messages sent by `selfId` are also skipped (they were already added to the tree on the `send()` call path). This two-phase init-then-stream pattern ensures the tree is consistent: all historical messages are loaded before any new messages are processed, and the `messageToNodeId` Map provides deduplication across the phase boundary. §the-named-two-phase-init-then-stream-with-deduplication.

The `send` function (lines 392-414) adds the user node to the tree locally BEFORE sending to Fae, attaching it as a child of `activeNodeId`. This optimistic-local-add before the remote `E(powers).send('fae', [text], [], [])` keeps the local tree consistent regardless of network latency. The three empty arrays in the send call (`[], [], []`) are the CapTP arguments for metadata slots that are not used by this sender. `setSending(true)` sets the loading state; it is cleared by the streaming phase when the assistant response arrives (or immediately on error). §the-named-optimistic-local-add-before-remote-send.

The `navigateTo` function (lines 421-433) switches `activeNodeId` and replays `parseResponse` on the node's first message if it is an assistant message, updating `activeScene` and `activeNarrative` to match the selected node's parsed content. This is the branching mechanism: a user can click any node in the tree sidebar, and `navigateTo` makes that node's scene and narrative the active display without sending any new message. No CapTP call is made by `navigateTo`; it reads only from the local tree (which holds all nodes loaded during init and streaming). §the-named-navigate-to-as-pure-local-state-switch. §the-named-branch-from-any-past-node-as-exploration-idiom (confirmed in source — cycle 443's README claimed this; cycle 452 confirms the implementation is exactly a local tree read with parse replay).

The `lenientUnescape` function (lines 45-57) handles the escape sequences LLMs produce when embedding JavaScript inside JSON strings. The primary path tries `JSON.parse('"' + raw + '"')`; if that fails, it falls back to a `replace` over `\\(u[0-9a-fA-F]{4}|.)` that handles standard Unicode escapes and maps non-standard escapes (like `\'` → `'`) by looking up in `JSON_ESCAPE_MAP` and falling through to the literal character for unknown escapes. This lenient unescaper is the reason the regex fallback can recover `narrative` and `scene` fields from otherwise-invalid JSON. §the-named-lenient-unescape-for-llm-generated-json as tier-3 meta-pattern: it acknowledges a documented LLM failure mode (JavaScript-style escaping in JSON contexts) and handles it at the boundary closest to the LLM output.
