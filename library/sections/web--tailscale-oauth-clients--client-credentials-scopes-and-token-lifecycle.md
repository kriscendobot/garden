A Tailscale **OAuth client** gives a program ongoing, non-interactive access to the Tailscale API through the OAuth 2.0 **client-credentials** grant. The durable credential is a `(client ID, client secret)` pair that the program exchanges, on demand, for a short-lived API access token; the token, not the client secret, authorizes individual API calls. The scopes selected at client-creation time are baked into every token the client can mint, so the client is a least-privilege capability whose reach is fixed when it is created.

## How it works

You create an OAuth client that **defines the scopes** the client application may use against the Tailscale API. A scope names a capability over a slice of the API. Examples:

- `dns:read` grants read-only access to a tailnet's DNS settings.
- `devices:core` grants read and write of the tailnet's device list (authorize or remove machines, manipulate device tags).

Tailscale **restricts each scope to only the necessary API endpoints** for that operation. A token carrying `dns:read`, for instance, can reach only:

- `GET /api/v2/tailnet/:tailnet/dns/nameservers`
- `GET /api/v2/tailnet/:tailnet/dns/preferences`
- `GET /api/v2/tailnet/:tailnet/dns/searchpaths`
- `GET /api/v2/tailnet/:tailnet/keys/:keyID` (for the token itself only)

So scope is a capability and the scope-to-endpoint table is the capability's reachable surface; an over-broad scope hands the bearer a wider surface than the task needs.

## Client identity and the token exchange

An OAuth client consists of a **client ID** and a **client secret**, both generated by Tailscale at creation time. The client application uses the ID and secret to request an **API access token** from the Tailscale OAuth token endpoint; it then calls the Tailscale API with that access token. The access token grants permission only for the scopes defined when the client was created.

The token endpoint is `https://api.tailscale.com/api/v2/oauth/token`. It accepts requests in the OAuth 2.0 client-credentials grant request format and returns responses in that grant's response format. A request can include `scope` and `tags` parameters (space-delimited lists); the client must already have permission to grant the requested scopes and tags. An `all`-scoped client (all scopes plus all device tags) can, for example, mint a token narrowed to `devices:core` and `tag:server`.

## Token lifecycle: short-lived tokens minted from a durable client

An API access token **expires after one hour**, and that lifetime cannot be changed. For continuous access, the application requests a fresh token from the token endpoint shortly before the current one expires. This is the core lifecycle shape: a **long-lived client (the durable ID + secret) mints short-lived access tokens on demand.** OAuth client libraries in popular languages (Go `clientcredentials`, Node `OAuth2`, PHP `ClientCredentials.php`, Ruby `client_credentials.rb`) handle token generation and renewal automatically, so the application code holds the secret and lets the library cycle the tokens.
