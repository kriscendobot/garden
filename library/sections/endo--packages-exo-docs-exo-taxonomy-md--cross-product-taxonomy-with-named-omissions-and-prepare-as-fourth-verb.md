The 53-line `exo-taxonomy.md` is the doc that the cycle 367 README explicitly pointed at via its "Complete API reference and make/define/prepare patterns" closing line. Reading it answers the question the cycle 367 lens raised: what is the full grammar of exo-creation across the @endo and @agoric package boundary? The answer is a cartesian product of two cross-cutting axes, with explicit named omissions, plus a fourth verb pattern that doesn't fit the cardinality axis at all. The single most structurally interesting move is §the-named-cross-product-taxonomy-with-named-omissions. The document organizes the entire @endo/exo + @agoric/vat-data exo-creation API surface as a cartesian product of cardinality (make vs define vs define-kit) and storage (heap vs virtual vs durable). The cross product gives nine nominal cells. Reality has fewer. The taxonomy explicitly names which cells don't exist: line 26 says "there is no `makeVirtualExo`," and line 29 says "there is no `makeDurableExo`." The reason is given in both cases: high cardinality is the only purpose of virtual/durable storage, so single-instance variants aren't useful. §the-named-omission-with-reason-not-just-omission names the tier-3 meta-pattern; the design discipline is to NAME the omissions AND state WHY they don't exist, so a future reader knows the absence is intentional rather than a gap. The cycle 367 README named the three runtime backing tiers as a tier-list; the cycle 368 doc reveals that the tiers are actually one axis of a two-axis grid, and the grid has structured omissions. The second most structurally interesting move is §the-named-prepare-as-fourth-verb-pattern. Line 36 introduces "prepare" as a different verb pattern entirely: prepareExo, prepareExoClass, prepareExoClassKit. The cycle 367 README named the three-verb trio (makeExo + defineExoClass + defineExoClassKit); the taxonomy doc reveals a fourth verb. The four verbs correspond to four lifecycle stances: makeExo is fresh-singleton; defineExoClass is fresh-factory; defineExoClassKit is fresh-multi-facet-factory; prepareExo (and its kin) is durable-restore-or-create-and-register. §the-named-four-verb-pattern-of-exo-creation names the extension of the cycle 367 cardinality ladder. The prepare verb shifts the design grammar from cardinality to lifecycle: instead of asking "how many instances?" it asks "is this fresh or recovered from baggage?" The doc explains the structural reason in line 36: "What is passed in baggage is only the state of the durable objects. Only the `prepare*` calls associate that state with code, giving it behavior." State and behavior are separated across vat upgrades; baggage carries data; the prepare call reunites data with code. §the-named-state-code-separation-across-vat-upgrades names the deep persistence design; §the-named-state-as-data-behavior-as-code-reunion-at-vat-start names the tier-3 meta-pattern. The persistence design presumes that state survives but code is replaceable across upgrades — a vat-upgrade-aware persistence model that does not write executable code into baggage. The discipline constraint is named directly. §the-named-first-crank-discipline observes that prepare* calls must happen on the first crank of the vat incarnation, because the state in baggage must be associated with behavior before any messages arrive. §the-named-crank-as-vat-lifecycle-unit names the underlying clock; §the-named-must-be-prepared-before-any-message-arrives names the tier-3 meta-pattern. The constraint is structural, not advisory. The doc's etymology section is small but load-bearing. Lines 3-5 explain that "exo" means "outside" — an exo object is reachable from outside the vat, and other vats hold capabilities to it — AND alludes to ExoSkeleton, a protective outside layer that is an effective first defense against threats. The double reading is intentional: outside means capability-style, and ExoSkeleton means defensive validation. §the-named-double-etymology-of-exo names the move. Line 7 adds: "Exo also forms a nice pairing with Endo itself." Endo means inside, Exo means outside; the package family's name carries the inside/outside duality. §the-named-exo-and-endo-pair names the pairing; §the-named-naming-as-conceptual-pairing names the tier-3 meta-pattern.
