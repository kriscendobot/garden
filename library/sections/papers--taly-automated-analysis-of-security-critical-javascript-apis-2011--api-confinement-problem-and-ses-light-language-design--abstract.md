§1 frames the problem: many contemporary websites embed *untrusted third-party JavaScript* (advertisements, Google Maps, so-called gadgets, social-network applications) directly into the hosting page, raising the *API confinement* question — *can the trusted code expose an API to untrusted code that mediates access to security-critical resources, and can the application *provably* establish that the API cannot be circumvented?* The §1 paper's answer is **the API+Sandbox approach** that Facebook FBJS, Yahoo! ADSafe, and Google Caja use: *the trusted code encapsulates all security-critical resources behind an API* that *provides JavaScript methods to safely access those resources*. The reference monitor is the API itself; the sandbox restricts the untrusted code so its only handle into the application is the API. But: *a JavaScript reference monitor can only be effective if it cannot be circumvented through programming tricks or programming language idiosyncrasies*. The §1 framing's motivating example: a write-only logging facility whose API exposes `push(x)` (only allows writing). The §1 *trick* shows that even the seemingly-confined `var api = {push: function(x){priv.push(x)}}` can be subverted via `api.store('push', function(){result = this[0]})` if the API exposes an additional method `store` that takes a function — the function's `this` gets coerced to the array, and the attacker reads `array[0]`. *A cursory reading shows that neither API method returns a reference to the array, the API fails to confine the array. A client may gain direct access to the criticalLogArray by calling methods of the API and mutating external state.* This is the *Overt Confinement Problem for Capabilities* [19] cast in the API-confinement language. §2 establishes the language-design line: starting from full JavaScript (ECMA-262 5th-edition strict mode is the baseline), it identifies three properties that hold for **ES5S** (strict mode) but *fail* for full JavaScript: (1) **Lexical Scoping** — full JavaScript's `delete`/prototype-chain-on-scope-objects/`with` break ordinary renaming; (2) **Safe Closure-Based Encapsulation** — `.arguments.caller` exposes activation-record properties of the caller; (3) **No Ambient Access to Global Object** — full JavaScript provides multiple ways (`this`-coerced-to-global; `sort`/`concat`/`reverse` of `Array.prototype`; `valueOf` of `Object.prototype`) for code to obtain a reference to the global object. ES5S enforces these via Figure 1's restrictions (no `delete` on variable names; no prototypes for scope objects; no `with`; no `this` coercion; safe built-in functions; no `.callee`/`.caller` on arguments objects; no `.caller`/`.arguments` on function objects; no arguments-and-formal-parameters aliasing). §2.B then names two *remaining* limitations of ES5S: (1) *ambient access to built-in objects* — all code has *undeniable write access to the built-in objects*, which can be maliciously used to alter the behavior of trusted code; (2) *eval* — code running inside eval is unavailable statically, so static analysis cannot know what global state it accesses. **SES_light** addresses both: (1) all built-in objects (except the global object) are *transitively immutable* (their properties non-writable, non-configurable, the objects themselves non-extensible; all built-in properties of the global object are also non-configurable and non-writable, so the global object itself is *deeply immutable*); (2) all eval calls must specify *an upper bound on the set of free variables of the code being eval-ed* — the *variable-restricted eval*. *At run-time, the code is evaluated only if its free variables are within the set specified by the arguments.*
