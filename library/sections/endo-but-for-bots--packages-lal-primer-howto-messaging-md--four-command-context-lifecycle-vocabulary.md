The 97-line howto-messaging.md is the user-facing complement to agent-facing messaging.md (cycle 413). Where messaging.md prescribes tool calls for the LLM layer (locate → listMessages → adopt+reply+dismiss), howto-messaging.md prescribes slash commands and @-addressing for the human layer. Both documents address the same underlying messaging protocol through different surfaces, confirming cycle 413's §the-named-style-as-part-of-surface-boundary pattern at the structural level. The user and agent surfaces differ not just in API shape but in audience, vocabulary, and interaction style. Cycle 441's most structurally interesting move is §the-named-four-command-context-lifecycle-vocabulary.

Lines 35-53 name four distinct user-facing strategies for managing conversation context. The first is starting a new conversation: "Create a fresh guest to get a clean slate. The agent's primer and tools carry over, but prior messages do not." This creates a new agent instance with an empty context window while preserving capability endowments. The second is replying to a specific message via `/reply <msgnum>`: "This is useful when a thread has branched and you want to pick up from the message that captures all the relevant context without the noise of subsequent back-and-forth." Thread control is an explicit user operation, not an implicit mechanism. The third is dismissing stale messages: `/dismiss 5` and `/clear` prune the inbox to reduce clutter. The fourth is the implicit baseline: simply continuing a conversation accumulates context until one of the first three interventions is applied. These four strategies constitute a complete vocabulary for managing the LLM context lifecycle at the user level. §the-named-four-command-context-lifecycle-vocabulary names the tier-3 meta-pattern. Context accumulation in LLM agents is a fundamental architectural constraint; Endo's user-facing vocabulary treats it as a first-class concern with four named operations at the human-UI layer.

The user-facing /reply is anchored to a specific message number, not to "the latest message." §the-named-threaded-reply-anchored-to-message-number-at-both-surfaces names the structural observation. Cycle 413's §the-named-mandatory-reply-for-responses-mandatory-send-for-initiation established that the agent MUST use reply(messageNumber, ...) for responses and send() only for initiating new conversations. Howto-messaging.md shows the USER-FACING equivalent: `/reply 5 Thanks for the update!` anchors to message 5 specifically. The threading discipline — reply to a named message, not to "the conversation" — is consistent from user-facing slash command all the way to LLM tool call. Both surfaces carry the same structural constraint: messaging is positional and the reply anchor is explicit.

Adopting values from messages follows the same dual-naming pattern cycle 413 named at the agent level. Lines 58-64: `/adopt 3 counter -n my-counter` takes the value the sender labeled "counter" from message 3 and stores it under the receiver's pet name "my-counter." §the-named-adopt-as-user-facing-cap-transfer-with-dual-naming names the user-facing confirmation of cycle 413's §the-named-dual-naming-across-trust-boundary pattern. The sender's edge name ("counter") and the receiver's pet name ("my-counter") are different; each side of the trust boundary names the capability in its own namespace. The user-facing adopt command exposes this duality explicitly via `-n` flag. The syntax `/adopt <msgnum> <edge-name> -n <pet-name>` is a compact encoding of the trust boundary.

The request-resolve-reject flow grounds the three-party capability grant protocol from the user's perspective. Lines 66-80: `/request @host I need read access to the database` (requesting agent asks); the recipient grants with `/resolve 7 my-database` or denies with `/reject 7`. This is the user-side instantiation of cycle 437's §the-named-request-resolve-as-explicit-cap-grant-flow pattern. Cycle 437 named the flow from the REQUESTER's perspective (request → host receives form → host resolves with capability); howto-messaging.md names it from the GRANTER's perspective (you receive /request; you /resolve or /reject). §the-named-grantor-perspective-on-request-resolve-reject names the structural addition; both perspectives of the three-party protocol are now grounded in the primer's how-to documents.

The form flow is bidirectional. Lines 82-90: `/form @recipient` opens a form builder where the user defines fields; the recipient fills in and submits. Cycle 413's messaging.md focused on agents receiving form submissions. Howto-messaging.md reveals users can also SEND forms to collect structured input from other parties. §the-named-user-can-initiate-forms-to-collect-structured-input names the bidirectional form picture. The form is not exclusively an agent-to-user mechanism; it is a general structured-communication tool usable in either direction. §the-named-form-as-bidirectional-structured-communication names the tier-3 meta-pattern.

The CLI Notes section (lines 92-97) confirms the CLI/Chat asymmetry from cycle 439's §the-named-chat-and-cli-as-non-overlapping-operation-sets. "Most messaging operations are available in Chat. The CLI equivalents (endo send, endo reply, endo adopt, etc.) are useful for scripting and automation but are not needed for interactive use." The default surface for messaging is Chat; CLI is for scripting. §the-named-chat-as-primary-messaging-surface-cli-as-automation-complement names the tier-3 meta-pattern. The pattern is consistent with cycle 409's CLI-as-privilege-escalation framing: the two surfaces are not interchangeable but complementary, each serving a distinct mode of use.
