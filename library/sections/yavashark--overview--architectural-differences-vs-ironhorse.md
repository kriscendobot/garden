## Abstract

Yavashark and Iron Horse make opposite bets on most axes. Yavashark is a spec-first, speed-seeking engine: an SWC parser, a tree-walk default with an operand-specialized register VM, an RC heap, lazy per-realm intrinsics, and host-coupled built-ins. Iron Horse is a parity-first port of XS: an XS bytecode stack machine, arena slots under a tracing collector, frozen eagerly booted intrinsics, a deterministic meter, and snapshots. Only two yavashark choices look worth studying for Iron Horse's goals (SES, XS parity, metering): **lazily materialized intrinsics**, which bear on the Proposed `ironhorse-intrinsic-fault-in` design, and **multi-realm structure**, which bears on Iron Horse's single Realm and the SES Compartment work. The rest show what Iron Horse gains by not following yavashark (determinism, persistability, auditable cost). Each axis below separates what the code shows from inference.

## Axis by axis

| Axis | yavashark (verified at `2e159150`) | Iron Horse (`48d6f3e0`) | What the difference buys or costs |
|---|---|---|---|
| Front end | SWC parser plus TS/JSX strip, then `swc_validator` for early errors. | Its own XS-derived lexer, parser, scoper, and coder; byte-identity with XS compile; parse-metered admission. | SWC gives spec breadth and TypeScript for free, but its cost cannot be metered or made byte-identical to XS. Iron Horse's admission metering (`PARSE_METER_RELEASE`) needs a front end it owns. **No change is recommended.** |
| Execution | Tree-walk over AST by default. Opt-in VM with 32 registers, an accumulator, and a stack. Instruction set generated as the cross product of operation × operand kinds (about 21k-line enum). | XS opcode set and decoding metadata (a stack machine), dispatched by `Interp`. | Operand specialization saves loads and stores, which is plausibly what yavashark's perf focus is chasing, but it multiplies the opcodes a meter must price and an audit must cover. Iron Horse's per-opcode cost table (`ironhorse-meter-9`) is easier to keep honest over a small opcode set. Speculative: no yavashark benchmarks were run. |
| Values | A plain Rust enum today (size not measured). NaN-boxing (`nan_boxed.rs`) is a proof of concept. | A 24-byte Rust `Slot` with arena `SlotIndex`/`ChunkOffset` integer references and explicit wire encoding for snapshots. | NaN-boxing shrinks values but ties representation to pointers. Iron Horse's integer handles exist so the heap can be snapshotted and validated, so NaN-boxed pointers would fight persistence. Not worth importing. |
| Memory / GC | `Rc`-style `Gc<T>`. The cycle collector is behind non-default `actual_gc`, so the default build leaks cycles. Collection is deterministic and immediate for acyclic garbage. | A tracing collector with `GcHooks` and a visitation registry, quiescent and paged collection, and GC scheduling assigned to the consumer (W6 decision 5). | RC gives prompt reclamation, but finalization timing becomes observable (WeakRef and FinalizationRegistry semantics) and cycles leak. Iron Horse's tracing plus consumer-scheduled GC keeps collection out of the deterministic crank. **Iron Horse's approach fits metering and determinism; RC does not.** |
| Strings | Hybrid: UTF-8 for ASCII-only content (inline up to 23 bytes), UTF-16 otherwise, plus ropes. 24-byte handle. | UTF-16 code units in chunks for guest strings; CESU-8 for symbol names. | ASCII-as-UTF-8 halves memory for typical source-derived strings and speeds host interop. A real, separable idea for Iron Horse's heap-envelope bar (measured 0.2–2.5× against a 1.1× bar). It would touch every string path and the snapshot codec, so it is a heavy change. **Speculative; worth a design note, not a port.** |
| Realms and intrinsics | `Intrinsics` fields are `Partial<…>` cells initialized on first use, one set per realm. `$262.createRealm` works. | One `Realm`, intrinsics booted and frozen once before `is_locked_down()`. Every other compartment has its own `CompartmentEnvironment` but shares the primordials. The Proposed `ironhorse-intrinsic-fault-in` design (2026-10-16) covers lazy member install on property miss. | Lazy materialization cuts boot time and memory for unused intrinsics, which is the problem the fault-in design is solving. Yavashark's `Partial::get_with` is a working shape for a whole intrinsic. It does **not** solve the hard SES parts: freezing must force-resolve everything first, or a frozen-but-unmaterialized intrinsic must be indistinguishable from a materialized one, and a snapshot must encode which cells are resolved. danfinlay's quickjs `lockdown` (two-phase: force-resolve AUTOINIT, then freeze; [section](danfinlay-quickjs--native-ses--lockdown-freeze-intrinsics.md)) is the closer precedent. Yavashark is a second data point. |
| Metering and sandboxing | None: no step or gas budget, no interrupt hook. Host clock, time zone, and RNG are read directly. | A deterministic meter with frozen weights and a digest, a `deterministic-math` provider, and no host clock or locale. | Yavashark cannot be an oracle for Iron Horse's meter or for determinism, only for spec results. |
| Test262 strategy | Pass or fail against Test262 assertions, the whole suite including intl, temporal, annexB, and staging, with a claimed ~81% (README; not verified). | Differential against the XS oracle. Reports covered, skipped, and divergent, with zero divergence required on covered cases. Non-hardened sweep. | Yavashark optimizes the headline pass rate. Iron Horse optimizes agreement with XS, so its pass rate is capped by XS's own Test262 conformance by construction. Yavashark's suite-wide number is not comparable to Iron Horse's "covered/divergent" split and should not be read as a target. A pure-spec yavashark-style pass column next to the XS-differential column would show where XS itself is wrong. Speculative, but cheap once the runner grafts land. |
| SES / hardened JS | Absent. | A core goal (stage 4, not yet met). | Nothing to learn here. |

## Bottom line

Yavashark is a useful sibling for **test-infrastructure ideas** and as a **spec-breadth reference** (Intl and Temporal surface, early errors). It is not a source of engine architecture for Iron Horse, whose determinism, metering, and persistence goals rule out yavashark's main structural choices: the RC heap, the SWC front end, host-coupled built-ins, and the specialized opcode explosion. The two ideas worth carrying into design discussion are lazy intrinsic materialization (feeding `ironhorse-intrinsic-fault-in`) and ASCII-compact strings (feeding the heap-envelope bar), and both are speculative.
