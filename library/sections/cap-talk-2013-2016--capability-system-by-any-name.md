Abstract: The list revisits whether outreach should stretch “capability” to cover systems that expose some capability-like handles but retain ambient naming or identity-based checks. The useful criterion is structural rather than promotional: authority should be conveyed by unforgeable, delegable designators; ordinary code should not recover broader ambient power merely by naming a resource or a principal; and attenuation should preserve the designation-authority coupling. Calling every sandbox, bearer token, or access-control API a capability system may win familiarity while erasing the property the term is meant to communicate.

The thread does not settle a perfect boundary. It does converge on a communication tactic: describe concrete properties first, qualify the term as “object capability” when ambiguity matters, and do not treat a project's chosen label as evidence of its authority semantics.
