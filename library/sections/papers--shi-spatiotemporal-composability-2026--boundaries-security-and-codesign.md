Abstract: This derived digest, not the original paper, captures the discussion section's engineering extensions, including the one most relevant to an object-capability reader: the paper independently observes that its dependency-declaration mechanism *is structurally capability-based access control* — a component can only access dependencies it declared (`inject` = a capability request; the context proxy = a capability mediator; undeclared access errors), authority conferred by possession of a reference rather than by ambient authority. Interception adds fine-grained, orchestrator-adjustable policy on how a held dependency is used. Language-level access control is acknowledged insufficient for untrusted code, which needs an external execution boundary (SFI, separate runtime, sandboxed process, container) bridged as an ordinary attenuable fiber.

**System boundary (§6.1).** Every effect carries an inverse, and what that inverse *is* is settled by the *system boundary*. A location is *inside* when the system can modify it exclusively and restore its prior state (tracked in `Γ`, recoverable); *outside* when either ability fails (the operation acts as `id_Γ` — untracked, unrecoverable). A coeffect *moves the boundary* by reifying an external location: it confines access to a set of operations it can supply inverses for, so an operation that was `id_Γ` becomes tracked. The boundary is drawn per location, not per medium (a scratch file under a private path is inside; a shared path is outside). *Acquisition vs emission*: reaching outside proceeds in two stages — acquisition installs a revertible record inside the boundary (`open`/`close`, `malloc`/`free`, `fork`/`kill`), while emission pushes data through that channel (`write`, `send`) and acts as `id_Γ`. Recovering an emission needs either *withholding* (delay until the state is certain to persist — the output-commit problem) or *compensation* (an application-supplied action restoring state up to a coarser equivalence — delete the created file, refund the charge); compensations compose in the same LIFO order as inverses.

**Service multiplexing (§6.2).** A service is the interface behind a key; providers provide it, consumers inject it. Multiple providers can be handled by *exclusive binding* (at most one bound at a time; switching perturbs every consumer) or a *service broker* (a central component injected by both providers and consumers that dispatches requests, absorbing provider changes so consumers see no reload). The broker underlies *load balancing* (distribute among coexisting providers; each registers via a revertible effect so unloading drops it from the routing set), *rolling updates* (load the new provider, shift traffic by weight, unload the old once drained — blue-green/rolling deploy as an application-level pattern), and *cross-process invocation* (each process hosts its own Cordis context; a coordinating component links them as remote providers over an RPC mechanism that preserves the interface; cross-process interfaces must be designed against an asynchronous contract).

**Capability-based access control (§6.3).** The paper draws the connection explicitly: dependency access *already constitutes access control* — a component can only access dependencies it has declared, and an undeclared access raises an error. This is *structurally similar to capability-based security*, where authority is conferred by possession of a reference rather than by ambient authority: the `inject` declaration acts as a *capability request* and the context proxy as a *capability mediator*. Because requests are declared statically, the complete set of proxy-mediated capabilities is known before the component runs, so an orchestrator can *review and approve them at load time*. *Interception* generalizes this to fine-grained policy: access-control metadata carried by the context (not in either party's code) is consulted by the provider on each invocation — e.g. a filesystem dependency whose metadata declares which paths a component may read/write, or granting a community component read-only database access while a core component keeps full access — and it can be installed, reconfigured, or removed at runtime without any reload.

**Sandboxing untrusted components (§6.3).** When code cannot be trusted, language-level access control is insufficient: a malicious component with access to the host runtime can reach underlying objects directly. Sandboxing needs an execution boundary beyond language means — software fault isolation, a separate language runtime, a sandboxed process, or a virtualized container. Whatever the mechanism, the untrusted component runs in its own sandboxed context and reaches host dependencies through a *bridge*, generalizing cross-process invocation; on the host side the bridge is an ordinary fiber whose capabilities can be *attenuated* by the access control above.

**Language independence, granularity, versioning, co-design (§6.4–6.7).** The paradigm is language-agnostic given closures (to capture inverses) plus a runtime module registry or dynamic link/unlink, and a dependency-injection mechanism with typed keys (Haskell typeclasses, Rust traits/impls, TypeScript module augmentation) and transparent access mediation (JS `Proxy`, Python descriptors, or reflection). *Mutual dependencies* leave both components permanently inactive but are predictable from declarations alone (unlike schedule-dependent deadlock) and are usually decomposable into finer unidirectional components (at a quadratic worst-case count, mitigated by bundling/convention/scaffolding). *Dependency typing/versioning*: nominal key-identity linking admits interface drift and key collision; the paper weighs key namespacing (`K × P`), peer dependencies (Cordis's current choice, via npm peer ranges), and structural compatibility (undecidable in general) — a unified model is an open problem. *Co-design*: a language built around the paradigm could make the context implicit again (closing the leak where a component reaches another's context through a closure or global), and an operating system co-designed with it could *supply the sandbox §6.3 defers to*, bounding a component to exactly its declared dependencies as a WebAssembly module receives its imports from its embedder.
