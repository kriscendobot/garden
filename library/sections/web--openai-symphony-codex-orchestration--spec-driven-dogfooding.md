Abstract: How Symphony was built and why it ships as a spec. The repository's first artifact is a single **`SPEC.md`** — a definition of the problem and intended solution, giving agents high-level steering rather than a complex hand-built supervision system. The team dogfooded ("used Symphony to build Symphony"), reached internal product-market fit, then extracted the idea into a standalone `SPEC.md` and asked Codex to implement it; the reference implementation is **Elixir** (chosen for concurrency/supervision primitives, built in one shot), and to polish the spec they had Codex implement it in TypeScript, Go, Rust, Java, and Python to surface ambiguities. The implicit human development workflow (put an issue in progress, open a PR, move to Review, attach videos) is now captured in a version-controlled **`WORKFLOW.md`**. Symphony uses **Codex App Server** (a headless JSON-RPC mode) and exposes a `linear_graphql` dynamic tool so subagents never see the raw Linear token. It is intentionally minimal, a reference implementation (not a maintained product), and had garnered over 15K GitHub stars within weeks.

**Symphony is technically just a `SPEC.md`.** Opening the repository, the first thing you notice is that Symphony is a single `SPEC.md` file — a definition of the problem and the intended solution. Rather than building a complex supervision system, the team defined the problem and intended solutions and gave agents high-level steering. The reference implementation is written in **Elixir** — because when code is effectively free you can pick languages for their strengths, and Elixir has excellent primitives for orchestrating and supervising concurrent processes — but the core idea can be expressed in a simple Markdown document. The authors encourage readers to point their favorite coding agent at the spec and have it implement its own version.

**Version history.** The first version of Symphony was just a Codex session running in tmux, polling Linear and spawning sub-agents for new tasks; it worked but was not particularly reliable. The second version lived inside the team's main project repository — already built with agents in mind, with a harness giving agents skills and context — so Symphony simply connected it all. Once basic functionality existed, they used **Symphony to build Symphony.** When an internal demo showed the system managing tasks and attaching proof-of-work videos, the reaction was overwhelmingly positive; the project channel grew and teams adopted it organically. Internal product-market fit is a prerequisite for launching externally at OpenAI, so based on that usage they decided to share it beyond company walls.

**Extraction and multi-language validation.** They extracted the idea into a standalone `SPEC.md` and asked Codex to implement it; for the reference they chose Elixir (a relatively niche language with excellent concurrency/supervision primitives), and **Codex built the Elixir implementation in one shot.** To polish the spec they even had Codex implement it in several other languages — **TypeScript, Go, Rust, Java, Python** — using the results to identify ambiguities and simplify the system; it succeeded in every language. Through the process they removed incidental complexity (dependencies on specific repositories, the Linear MCP), so Symphony no longer depends on internal repos or workflows. The core approach became simple: **for every open task, guarantee that an agent is running in its own workspace.**

**`WORKFLOW.md` captures the implicit process.** The development workflow — work on an issue, check out a repo, put it in progress so the PM knows it is being worked on, add the PR, move it to Review, attach videos — was a process humans followed but never documented. Rather than relying on implicit steps, they now document it in a simple `WORKFLOW.md`, and Symphony ensures agents follow it. If they decide agents should also attach self-reflection to finished work, they add that to `WORKFLOW.md` and Symphony guides agents through it.

**Codex App Server.** They used Codex in **app server mode** — a built-in headless mode letting them run Codex and talk to it programmatically via a well-documented JSON-RPC API (start a thread, react to turns). It is more convenient and scalable than driving Codex via CLI or live tmux sessions, and a perfect fit: they take advantage of the harness Codex provides while having knobs and hooks to plug into. For example, to avoid exposing the Linear access token to subagents, they use **dynamic tool calls** to expose a raw `linear_graphql` function that executes arbitrary requests against Linear — without relying on MCP or exposing the token to containers.

**What's next, and adoption.** Symphony is an intentionally minimal orchestration layer, open-sourced to demonstrate the power of Codex App Server paired with workflow tools like Linear. The team does not plan to maintain it as a standalone product — think of it as a **reference implementation**, the way developers pointed coding agents at the harness-engineering post to scaffold repos. The power comes from Codex and its app server; Symphony was a way to connect Codex to Linear (two tools the team already used) to solve work management. As coding agents get better at reasoning and following instructions, the bottleneck is expected to shift from writing code toward **managing agentic work**, and the barrier to experimenting with these systems is now low. Community adoption was rapid: over **15K GitHub stars** as of April 23.

> The spec-as-product move — "point your coding agent at the `SPEC.md`" — is the same posture the garden takes with its roles and skills: a role/skill is a Markdown contract an agent reads just-in-time, not a compiled system. Symphony's `WORKFLOW.md`-captures-the-implicit-process is the direct analogue of the garden documenting operating norms in `roles/*/AGENT.md` and `skills/*/SKILL.md`.
