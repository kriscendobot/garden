> Abstract: The decision: **causal information is a querying concern, not a modeling concern.** The default query path returns plain domain types (`Query::<Employee>` yields an `Employee`), so a tool reads values and writes updates without touching provenance. The macro still generates a `Conclusion<T>` type, but it is not the default return type. Tools that genuinely need causal information opt into a richer query mode — `Query::<Proof<Employee>>`, from which `proof.name().cause()` reads provenance — so the `Proof<T>` cost (Option 2) is paid only by those who need it, imposed on no one else. Five rationale points: most tools likely don't need it (forcing everyone through `Proof<T>` is cognitive overhead for an unused capability); the transactor can do the right thing without it (cardinality resolution depends on the current claim set the transactor always has, and works whether the writer provides an observed value or a causal reference); value-based CAS should cover the common staleness case (following Datomic — "is the value still what I read?" catches the meaningful conflicts, and the value-matches-but-cause-differs edge case is rare and not clearly actionable); provenance-aware queries can be added later if a real need arises, without imposing costs on all use cases; and cardinality resolution and staleness detection are *separate concerns* (the transactor handles cardinality by inspecting claims at write time; staleness is a CAS concern, value-based by default) that a universal wrapper would wrongly conflate. This decision is the query-API counterpart to the divergence-clock and value-model work: the provenance exists in the associative layer, but the surface deliberately keeps it optional.

## Decision

**Causal information is a querying concern, not a modeling concern.**

The default query path returns plain domain types. Tools that need causal information opt into a richer query mode. The `Conclusion<T>` type still gets generated by the macro, but it is not the default return type.

```rs
fn demo(session: Session) -> Result<(), Error> {
    // Default: just give me the data
    let query = Query::<Employee> {
        this: Term::var("alice"),
        name: Term::Constant("Alice"),
        role: Term::var("Intern"),
    };
    let [alice] = query.perform(&session).try_vec().await?;

    let mut tx = session.edit();
    tx.assert(Role::of(alice).is("Cryptographer"));
    session.commit(tx).await?;
}
```

If some use cases genuinely need provenance, the interface can be extended to support `Proof<T>` (inspired by Option 2) without imposing costs on all use cases:

```rs
let query = Query::<Proof<Employee>> { this: Term::var("alice"), name: Term::Constant("Alice"), role: Term::var("Intern") };
let [proof] = query.perform(&session).try_vec().await?;
println!("{:?}", proof.name().cause()); // prints provenance for the name
```

## Rationale

1. **Most tools likely don't need it.** The vast majority of authors want to read values and write updates. Forcing everyone through `Proof<T>` imposes cognitive overhead for a capability most would never use.
2. **Transactor can do the right thing without it.** The cardinality-resolution rules (sole claim vs multiple claims, promotion, etc.) depend on the current claim set at transaction time, which the transactor always has. This works just as well if the writer provides the observed value instead of a causal reference.
3. **Value-based CAS should cover the common staleness case.** Following Datomic's lead, checking "is the value still what I read?" likely catches the meaningful conflicts. The edge case where the value matches but the cause differs seems both rare and not clearly actionable.
4. **Provenance-aware queries can be introduced if the need arises.** If use cases genuinely require causal information, extend the query interface with `Proof<T>` as shown, without imposing costs on all use cases.
5. **Cardinality resolution and staleness detection appear to be separate concerns.** The transactor handles cardinality by inspecting claims at write time; staleness detection is a CAS concern, value-based by default. Bundling them behind a universal wrapper would conflate two things better kept apart.
