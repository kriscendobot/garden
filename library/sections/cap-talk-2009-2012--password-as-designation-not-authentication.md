Abstract: Rob Meijer noticed a concept hiding inside a bug. Building a MinorFs PAM module that derived a root capability from a valid password, he hit a defect where a user could log in with *any* password, and each distinct password designated a *different* MinorFs root directory. The "bug" reframes a password as a **designation** rather than an **authentication**: instead of a password proving you are the account owner (one true password, all others rejected with an error), a password *selects which capability you get* (every password names a home, and a wrong one names an empty new home rather than failing). Mechanically he took `HMAC-SHA256(username:password, system-secret)` as a read/write sparse-cap for that user's top-level directory (root Key1), creating an empty directory on first use; everything below the per-user root attenuates via MinorFs's 3-step hashing. Alan Karp's core question — "how would you make a separately revocable, attenuated capability from a password?" — went essentially unanswered (Meijer had "not worried about revocation yet"). The thread surfaced the real tradeoff: deriving the root from the password means the administrator *cannot* reach a user's data (good confidentiality) but also cannot reclaim that user's storage or delete just their data (bad manageability), whereas not deriving from the password gives the admin both powers. Bill Frantz noted the duress-password angle (a secondary password designating an innocent file set); David-Sarah Hopwood flagged the usability hazard of a wrong password silently "working" instead of producing an obvious error; Jed Donnelley argued this is just capabilities-as-data (Amoeba/WalNUT/NLTSS "password capabilities"), with the known caveat that data-caps are awkward to membrane; and David Barbour cautioned that human passwords should be treated as insecure regardless (weak, reused, phishable, forgettable).

## Selecting a capability versus proving an identity

The insight is that the two readings of a password are orthogonal security models. Authentication asks "are you who you claim?" and treats any non-matching password as an attack to reject. Designation asks "which resource does this string name?" and treats every string as a valid name for *some* (possibly empty, possibly nonexistent-until-now) resource — there is no "wrong" password, only a different designation. Meijer's HMAC construction makes the password a bearer secret whose knowledge *is* the authority: knowing the string lets you resynthesize the sparse-cap, so it is capabilities-as-data (Donnelley's point) and knowledge-limited rather than permission-limited. That yields the confidentiality/manageability tradeoff cleanly — if authority is derived from a secret only the user knows, no third party (not even the administrator) can produce it, which is exactly why the admin loses both the ability to snoop and the ability to reclaim. Karp's revocation question is the unresolved crux: a password-derived cap has no separate handle to revoke or attenuate short of changing the secret and re-deriving everything, so the elegance of designation-by-password comes at the cost of the caretaker/membrane machinery that reference-based caps get for free. Hopwood's usability objection is the human-factors dual of the same property: a model with no "wrong" input gives the user no feedback when they err.

## Bearing on Endo

Endo's petname and web-key machinery sits on the authentication-versus-designation distinction this thread names, and comes down on the designation side while avoiding the password-as-secret pitfalls. A web-key is a designation whose possession is the authority (knowledge-limited, like Meijer's HMAC root), but Endo derives it from unguessable high-entropy material, not a human-chosen password, sidestepping Barbour's weak-password caution. The confidentiality/manageability tradeoff Meijer hit is the same one Endo faces for guest data: authority derived so the host cannot reach guest state buys confidentiality at the cost of host-side reclamation, which is why Endo keeps reclamation an *accounting* property (budgets and formula storage the host can garbage-collect) rather than folding it into the secret. Karp's unanswered revocation question is exactly why Endo prefers a revocable reference (a facet behind a caretaker) over a bearer secret when revocation matters: a designation you cannot revoke is a poor fit for anything but a deliberately non-revocable root.
