The 506-line `packages/daemon/src/networks/ws-relay.js` is the WebSocket relay network backend for the Endo daemon. It closes the ws-relay rung of the three-backend connectivity ladder named in cycle 445 chat-reference: relay-mediated, where both peers connect through a public relay server rather than directly. Reading it answers how a relay-mediated network module differs structurally from the direct-connection modules (TCP in cycle 446, libp2p still open). The single most structurally interesting move is the multiplexed channel architecture: where TCP and libp2p each maintain one CapTP session per transport connection, ws-relay multiplexes N simultaneous CapTP sessions over a single WebSocket to the relay server, demultiplexed by integer channelId. §the-named-multiplexed-captp-channels-over-single-websocket-connection names the tier-3 meta-pattern; one WebSocket supports many logical peer-to-peer CapTP sessions, each isolated by channelId. This is the defining structural characteristic that distinguishes relay-mediated networking from direct networking.

The `make` signature has three parameters: `make(powers, context, { env = {} } = {})`. This extends the two-parameter network-module shape from cycle 446 (tcp-netstring used `make(powers, context)`). The third parameter carries formula env directly — `relayUrl` and `relayDomain` are extracted from `env` on lines 95-96 with mandatory-presence checks. This contrasts with tcp-netstring, which called `E(powers).request('SELF', ...)` to solicit configuration at activation time; ws-relay receives its configuration as formula state baked in at install time by setup-ws-relay.js. §the-named-env-as-third-make-parameter names the tier-3 meta-pattern; the three-parameter form is the module's way of receiving persistent formula state without an interactive request dialog.

The challenge-response authentication handshake appears in the WebSocket `message` handler on lines 318-332. When the relay sends `MSG_CHALLENGE`, the module concatenates `domainBytes` and `nonce`, calls `E(powers).sign(toHex(challengeData))`, and sends back the signature. The `sign` capability is a daemon power: the daemon's node keypair signs on behalf of the module. §the-named-challenge-response-auth-via-sign-power names the tier-3 meta-pattern; the module does not hold a key itself, it holds the `sign` power, keeping the key isolated in the daemon. `MSG_AUTH_OK` resolves the `authed` promise; `MSG_AUTH_FAIL` rejects it. This is a fully capability-mediated authentication: the credential is a power, not a secret value.

The `makeChannelStreams` factory on lines 56-82 creates a `{ reader, writer, sink, closed, resolveClosed }` tuple from `sendDataFn`, `sendCloseFn`, and a `channelId`. The writer's `next()` method calls `sendDataFn(channelId, bytes)` (a closure that fires `currentWs.send(encodeData(channelId, bytes))`); `return()` and `throw()` both call `sendCloseFn(channelId)`. The reader is the pipe end of a `makePipe()` pair; the `sink` is the write end that the frame dispatcher pushes bytes into. §the-named-makeChannelStreams-as-channel-to-stream-adapter names the tier-3 meta-pattern; the factory translates the multiplexed WebSocket channel model into the standard reader/writer/closed stream triple that `makeNetstringCapTP` expects. This is the abstraction that makes the two-layer framing stack from tcp-netstring composable over a relay channel rather than a TCP socket.

The exponential backoff reconnect appears in lines 369-376. `scheduleReconnect()` schedules a `connectToRelay()` call after `reconnectDelay` milliseconds, then doubles `reconnectDelay` (up to `MAX_RECONNECT_DELAY_MS = 30_000`). On `MSG_AUTH_OK`, `reconnectDelay` resets to `INITIAL_RECONNECT_DELAY_MS = 1_000`. The WebSocket `close` handler calls `scheduleReconnect()` unless `stopped` is true. §the-named-exponential-backoff-with-reset-on-success names the tier-3 meta-pattern; the delay doubles on each retry but resets to the initial value on a successful authentication, so the module is not permanently slowed after a long outage.

The `pendingOpens` Map (line 129) is the outbound-channel-open registry. When `connect()` opens a new channel, it creates a promiseKit, stores it under `channelId` in `pendingOpens`, sends `encodeOpen(channelId, targetNodeIdBytes)` to the relay, and awaits the `opened` promise. When the relay responds with `MSG_OPENED`, `handleOpened` resolves the pending promiseKit; `MSG_OPEN_FAILED` rejects it. Only after the channel is open does `connect()` start CapTP. §the-named-pending-opens-as-outbound-channel-registry names the tier-3 meta-pattern; the two-phase channel-open (request then confirm) is an explicit rendezvous before CapTP starts, ensuring the relay has routed the channel before protocol bytes flow.

The address format on line 493 is `${protocol}://${localNodeId}?relay=${encodeURIComponent(relayUrl)}`. The node ID is the URL hostname (all lowercase by URL parsing rules). This contrasts with libp2p.js, which puts the peerId in the URL pathname specifically to avoid hostname lowercasing. §the-named-node-id-as-url-hostname-in-relay-address names the tier-3 meta-pattern; the ws-relay address scheme encodes the identity as hostname because the node ID hex is lowercase-safe, while libp2p's base58-encoded peer ID is not. The relay URL is baked into the address as a query parameter, so the dialing side knows which relay to connect through without a separate lookup.

The `closeAllChannels` function on lines 155-165 calls `sink.return(undefined)` and `resolveClosed(undefined)` for every active channel, then clears both `channels` and `pendingOpens`. This is called from the WebSocket `close` handler and from `shutdown()`. §the-named-closeAllChannels-as-connection-loss-handler names the tier-3 meta-pattern; when the WebSocket drops, all active CapTP sessions are closed atomically (not individually signaled) and all pending outbound opens are rejected with "Connection lost". This is the relay-layer equivalent of tcp-netstring's `connectionClosedPromises` drain, but coarser: relay failure tears down every logical session at once.

The `dispatchFrame` function on lines 267-291 is a `switch(type)` over frame-type constants. Each case calls a dedicated handler (`handleIncoming`, `handleOpened`, `handleOpenFailed`, `handleDataFrame`, `handleCloseFrame`, `handlePeerGone`). The frame-type constants and decode functions are imported from `@endo/relay-server/protocol.js`. §the-named-dispatch-frame-as-typed-message-switch names the tier-3 meta-pattern; the relay protocol has eight message types; the switch centralizes all routing; each handler is a single-responsibility function. §the-named-protocol-codec-as-external-package (the framing codec lives in `@endo/relay-server`; ws-relay.js is a consumer, not the codec author); the decoupling means the relay server and the relay client share the same wire protocol definition.
