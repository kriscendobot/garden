The doc's single most structurally interesting move is §the-named-design-vs-implementation-arc-from-README-to-source: cycle 357's @endo/zip README named the attack via magic numbers in comment (a Zip implementation scans backward for EOCDB magic numbers; an attacker can plant decoy magic numbers in a comment); cycle 358's signature.js exports those magic numbers as NAMED EXPORTS (LOCAL_FILE_HEADER + CENTRAL_FILE_HEADER + CENTRAL_DIRECTORY_END + ZIP64_CENTRAL_DIRECTORY_LOCATOR + ZIP64_CENTRAL_DIRECTORY_END + DATA_DESCRIPTOR). When a format has attack vectors that depend on specific byte sequences, name those byte sequences as exports so the attack surface is grep-able. §the-named-PK-prefix-as-format-marker — every Zip signature starts with `PK\x...`. PK is Phil Katz's initials (PKZIP creator); the format's signature convention is named by the constant prefix. The discipline encodes BOTH the format identity (which historical format this is) AND the structural marker function (this is a header) into the two-byte prefix. §the-named-six-format-marker-set — six distinct signatures cover the Zip format's structural markers: (1) LOCAL_FILE_HEADER (PK\x03\x04) marks an individual file's data; (2) CENTRAL_FILE_HEADER (PK\x01\x02) marks an entry in the central directory; (3) CENTRAL_DIRECTORY_END (PK\x05\x06) marks the end-of-central-directory block (EOCDB); (4) ZIP64_CENTRAL_DIRECTORY_LOCATOR (PK\x06\x07) marks the Zip64 EOCDB locator; (5) ZIP64_CENTRAL_DIRECTORY_END (PK\x06\x06) marks the Zip64 EOCDB itself; (6) DATA_DESCRIPTOR (PK\x07\x08) marks the optional data descriptor following file data. §the-named-ZIP64-signatures-still-in-source-for-detection — first-explicit-observation. Cycle 357 README named that Zip64 support was dropped for security reasons; cycle 358 reveals that the Zip64 signatures are STILL exported. The implementation needs them to DETECT and REJECT Zip64 files (rather than parse them); detection requires recognizing the signature even when not supporting the feature. Tier-3 framing: when dropping a feature for security reasons, the implementation may still need to recognize the feature's markers in order to FAIL LOUDLY when encountering it. The signatures stay in source as "things we will reject"; absence of the signatures from source would mean silent fall-through. §the-named-detect-and-reject-via-named-signatures — first-explicit-observation as a tier-3 meta-pattern. §the-named-u-helper-converts-string-to-Uint8Array — lines 7-13 define a `u()` helper that converts a string of latin-1 chars (low 8 bits per char) to a Uint8Array. The `& 0xff` mask makes the intent explicit (we ONLY want the low byte). Tier-3 framing: when a small helper is used to construct multiple module-level constants, define it INLINE in the module rather than importing from a shared utility — this keeps the constants' construction discipline visible at their definition site. §the-named-inline-helper-for-constant-construction — first-explicit-observation. §the-named-twenty-one-line-magic-number-module — first-explicit-observation. The module is intentionally tiny: 21 lines of which most are the constant declarations themselves; one small helper; one ESLint directive for `no-bitwise`. The discipline: when a module's only job is to export named constants, it should be SHORT — readers should be able to see the entire format-signature taxonomy at a glance.
