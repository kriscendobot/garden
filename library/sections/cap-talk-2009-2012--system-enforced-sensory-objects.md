Abstract: A December 2010 thread on whether the KeyKOS/EROS notion of a **sensory object** — an object reached through a **sense key**, a capability that grants *transitively read-only* access with system-level verification of the read-only attribute — can be reconstructed in a *language*-enforced capability system rather than an OS-enforced one. Bill Frantz posed the mapping: the important ideas are "system enforced transitive read-only access via the sense key" and "system level verification of the read-only attribute," and the difficulty is that language auditors like E's operate at the *method* level, not the *object* level, so any reference passing through the language's equivalent of a sense key "must have its read-write methods suppressed." **Kevin Reid** showed E can already do this within current semantics: write a *Selfless* auditor parameterized with a method's verb+arity (`Sensory["x", 1]`), have each read-only method carry that audit, and then a generic wrapper "which will forward only messages whose methods are audited Sensory" *is* a sense key. **David Wagner** generalized to the type system: some languages (Joe-E) already let a programmer claim a type is transitively read-only in a system-verifiable way; one could give every type `T` a companion `readonly T` with a side-effect-free subset of `T`'s methods and fields, making every type "implicitly polymorphic over the type qualifier 'readwrite' vs 'readonly'" (cf. Javari) — but "I'm not sure whether the security benefits would be worth the additional complexity in the language." Wagner also named the deep asymmetry: in language ocap "a capability is just a reference to an object, nothing more," while in OS ocap "a capability is the pair of a reference to an object and a set of access rights," and this difference "may make it harder to take ideas from EROS and translate them directly." **Jonathan Shapiro** pushed further: what he actually wants is something frozen during a parallel phase and *thawed* (mutable) during a subsequent sequential phase, usable at *compile time* to change concurrency-guard code emission — and Kevin Reid confirmed E's `EventuallyDeepFrozen` auditor does not provide that. The open design question (read-only as a first-class, system-verified type qualifier versus method-level auditing/wrapping) is recorded as open question 55.

## The mapping and the three constructions

**The KeyKOS original.** A *sense key* is a read-only capability: through it you can observe an object's state but not mutate it, and the property is *transitive* (the objects you reach *through* a sensory object are themselves sensory) and *system-verified* (the kernel guarantees the read-only attribute, you don't take it on trust). Frantz's question is whether the two load-bearing properties — transitive read-only, system-verified — survive translation into a language-enforced system where enforcement is at method granularity.

**Kevin Reid — auditors + a forwarding wrapper (works today in E).** Because E auditors can be *Selfless* (identity-free, so audit checks match structurally) and can be parameterized, you can define `Sensory["x", 1]` as an auditor that inspects only the code of the method `x/1` and certifies it side-effect-free. Each read-only method is written to pass that audit. A sense key is then a *generic membrane*: a wrapper that forwards a message only if the target method is audited `Sensory`, dropping (suppressing) the read-write methods Frantz worried about. This reconstructs transitive read-only as a composable membrane rather than a kernel primitive.

**David Wagner — a `readonly T` type qualifier (a language extension).** The typed alternative: for every type `T`, a `readonly T` exposing only the non-mutating methods/fields, declared by annotations and *compiler-verified* to grant no side-effecting authority — every type "implicitly polymorphic over 'readwrite' vs 'readonly'." Joe-E already supports transitive read-only reasoning; Javari is prior art for the qualifier. Wagner's own reservation is the honest open question: is the security benefit worth the language complexity? And he flags that the OS model's *reference+rights pair* does not map cleanly onto the language model's *reference is the whole capability*.

**Jonathan Shapiro — freeze-for-parallel-then-thaw (not currently available).** Shapiro's use is different from read-only-for-security: he wants a *phase* discipline — frozen for the duration of a parallel phase, then mutable in a subsequent sequential phase — and wants it decidable *at compile time* because it "changes the emission of concurrency guard code." He asked whether Kevin's `EventuallyDeepFrozen` auditor supplies this; Kevin answered no, and that its design offers no hints toward it. Compile-time phase-frozenness for concurrency-guard elision is left as an unmet want.

## The design question (open question 55)

The thread does not settle whether a capability *language* should add read-only as a first-class, system-verified **type qualifier** (`readonly T`, compiler-checked, transitive — Wagner's route, mapping the OS reference+rights pair into the type system) or should express transitive read-only purely by **method-level auditing plus a forwarding membrane** (Kevin Reid's route, already expressible with no language change). Wagner explicitly leaves open whether the type-qualifier route's security benefit is worth its complexity, and whether the OS "reference + rights" model is even superior to the language "reference is the capability" model. That is open question 55.

## Bearing on Endo

This thread is a direct ancestor of Endo's *hardening* and *pass-style* machinery, which resolves the read-only question by a third route the thread did not have: deep immutability. `harden()` transitively freezes an object graph, and `passStyle` classifies each value, so a "sensory" (read-only, non-authority-bearing) datum in Endo is simply a *hardened copy-data* value — pure data with no methods, hence no mutation and no authority, verified structurally rather than by a per-method audit or a `readonly` type qualifier. Kevin Reid's "forward only Sensory-audited messages" membrane is the ancestor of the [[caretaker-pattern]] / attenuating-forwarder Endo uses when a *live* object (not copy-data) must be exposed read-only. Wagner's language-versus-OS "is a capability a reference, or a reference+rights pair?" observation is the reason Endo (a language system) makes rights a property of *which object you hold* (a facet) rather than a rights-mask on a shared reference. See the `pass-style` and `hardened-javascript` topics, the [[object-capability]] concept, and open question 55.
