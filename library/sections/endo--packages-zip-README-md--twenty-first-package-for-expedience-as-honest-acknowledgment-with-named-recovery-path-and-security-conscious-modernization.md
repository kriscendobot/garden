The doc's single most structurally interesting move is §the-named-for-expedience-as-honest-acknowledgment-with-named-recovery-path: the README uses the phrase *"for expedience"* FIVE TIMES to acknowledge features that COULD be supported but weren't, AND for each omission names a specific RECOVERY PATH. The five omissions: (1) INFLATE compression (recovery: convert the dependency to ECMAScript modules; factor out shared CRC32); (2) asynchronous mode (recovery: restore using same underlying utilities; async/await and async iterators would make maintenance easier); (3) lazy Zip reader (recovery: build on same foundations given an async seekable reader); (4) streaming compression and data descriptors (recovery: data descriptors are redundant with central directory; recovering them would add integrity checks); (5) explicit directory records on read/write + enumeration API (recovery: straightforward to implement). Tier-3 framing: when omitting features from a specialization for non-essential reasons, name the omission with the prefix "for expedience" AND name the specific recovery path. The doc names the SES integration explicitly: in a locked-down environment, the ambient Date constructor is absent (per cycle 345 SES README's §the-named-Math-random-and-Date-now-disabled-by-default); a library that depended on it would break in that environment. The modernization REQUIRES the caller to provide a date instead — making the SES integration explicit at the API surface. §the-named-attack-via-magic-numbers-in-comment — first-explicit-observation as a tier-3 meta-pattern. The doc names a specific Zip-format attack: Zip files have an "end of central directory block" (EOCDB) with magic numbers; Zip implementations scan backward from the end of file looking for those magic numbers; *"a specially crafted Zip file may contain those magic numbers before the end"*. An attacker can craft a file with multiple "valid"-looking EOCDB positions, causing implementations that don't carefully validate to read different "central directory" data. The mitigation: drop support for the variable-width archive comment (which is what would normally come after the EOCDB). Tier-3 framing: when a format has a backward-scanning parser, an attacker can plant decoy magic numbers in any preceding content (comments, embedded files, file names). The mitigation is to LIMIT the search region OR to verify uniqueness OR to drop the feature that allows attacker-controlled content before the magic number. §the-named-prefix-can-be-arbitrary-length-attack — first-explicit-observation. The doc names a SECOND related attack: *"a comment that is itself a valid Zip file with a long prefix, since Zip files allow an arbitrary length prefix"*. Even with careful comment handling, the arbitrary-prefix nature of Zip means a comment could be embedded as a long-prefix Zip. Tier-3 framing: file formats with arbitrary-length prefix bytes are structurally vulnerable to nested format attacks; the mitigation is to drop comment support entirely. §the-named-modernization-and-specialization-from-named-predecessor — first-explicit-observation as a tier-3 meta-pattern.
