The doc's single most structurally interesting move is §the-named-Object-freeze-not-harden-in-pre-lockdown-modules-with-named-rationale: index.js opens with a SUBSTANTIAL comment block explaining WHY Object.freeze is used at module-evaluation time rather than @endo/harden. The full text: *"Each source module applies `Object.freeze` to its export at module-evaluation time, so the bindings are hardened on both the public path through this module and on the pre-lockdown shim path that `@endo/init/pre.js` uses (`@endo/base64/shim.js` -> `./atob.js` / `./btoa.js`). Using `Object.freeze` rather than `@endo/harden` keeps the shim path free of any module that would install a fallback `harden` before SES `lockdown()` freezes the well-known properties of `globalThis`."* Tier-3 framing: cycle 352 named §the-named-pre-lockdown-modules-use-freeze-not-harden in @endo/eventual-send/src/local.js; cycle 356's @endo/base64/index.js provides the FULL EXPLANATION of WHY in a multi-paragraph comment block. The discipline: a substrate package that gets installed via the pre-lockdown shim path MUST NOT pull in @endo/harden (which would install a fallback harden before SES lockdown runs); the workaround is to use Object.freeze directly at the file level. §the-named-pre-lockdown-shim-path-must-not-import-harden — first-explicit-observation as a tier-3 meta-pattern. §two-cycles-with-named-Object-freeze-not-harden-discipline (352 + 356) — first-explicit-observation. Cycle 352 named the discipline; cycle 356 names the full rationale + the specific consumer path that forces it. §the-named-mixed-forwarder-and-implementation-cluster — first-explicit-observation as a tier-3 meta-pattern. The base64 entry cluster has THREE structural shapes mixed at the same level: (1) single-line forwarders to src/ (decode.js + encode.js each 1 line forwarding to src/decode.js or src/encode.js); (2) thin implementations at the top level (atob.js + btoa.js each 11-18 lines wrapping the src/ functions with platform-API semantics — atob produces a binary string via fromCharCode; btoa validates byte range before encoding); (3) an aggregator with rationale (index.js 14 lines re-exporting all four bindings + the long comment block). This is STRUCTURALLY DIFFERENT from both cycle 346's all-forwarders SES cluster (the foundational package has the SIMPLEST entry-cluster) AND cycle 344's all-rungs init cluster (multiple variant entry points). §the-named-third-shape-of-tiny-files-orchestration — first-explicit-observation. The three shapes are: (1) rung-as-entry-point (cycle 344 init); (2) stability-via-thin-forwarder (cycle 346 ses); (3) mixed-forwarder-and-implementation (cycle 356 base64). Each shape suits a different package-purpose. §three-shapes-of-tiny-files-orchestration extending cycle 346's §the-named-rung-as-entry-point-vs-stability-via-thin-forwarder with a THIRD shape. §the-named-conditional-install-discipline — shim.js uses `if (globalThis.atob === undefined) { globalThis.atob = atob; }`. Sibling to cycle 187's §two-shim-strategies-side-by-side (conditional-install vs unconditional-replacement); cycle 356 reaffirms the conditional-install discipline. §three-cycles-with-named-conditional-install-discipline (187 + 343 + 356) — first-explicit-observation as a tier-2 multi-cycle pattern. §the-named-greek-wordplay-as-discipline-naming — src/common.js's `monodu64` is named with a Greek wordplay: *"If an alphabet is named for the Greek letters alpha and beta, then clearly a monodu is named for the corresponding Greek numbers mono and duo."* The variable holds the reverse mapping (char → number); the name MAKES THE REVERSE-DIRECTION OBVIOUS through the etymology. §the-named-named-reverse-mapping-with-etymological-rationale — first-explicit-observation as a tier-3 meta-pattern. When you need a reverse-direction lookup table paired with a forward-direction one, name the reverse with a clearly DIFFERENT etymology so the asymmetry is visible in code. §the-named-alphabet64-with-monodu-counterpart — alphabet64 (forward) + monodu64 (backward) pair as named symmetric+asymmetric pair. The naming convention itself is the discipline: alphabet for sequential letter-labels; monodu for sequential number-labels (in this case 0-63 mapped to the alphabet positions). §the-named-padding-as-const-export — `export const padding = '='` exports the padding character as a named constant rather than embedding the magic literal `=` throughout decode.js. Tier-3 framing: when a magic literal has a SEMANTIC MEANING that's important to readers, export it as a named constant so the meaning is searchable and the constant is reusable. §the-named-btoa-character-out-of-range-validation — btoa.js throws `Error("btoa: character out of range: ${char}")` for any character above 0xff. The discipline: when implementing a function whose input domain is BYTES but JavaScript strings are UTF-16 characters, validate that each character is in the byte range BEFORE processing. The error message names BOTH the function (`btoa:`) and the offending character. §the-named-atob-built-on-decodeBase64-with-fromCharCode — atob.js is one-liner composition: decode base64 string to bytes, then convert bytes back to a binary string via String.fromCharCode. The discipline: when implementing a platform-native function (atob/btoa) on top of a packaged primitive (decodeBase64/encodeBase64), the wrapper should be a thin composition that names the platform-API semantics. Tier-3 framing: substrate packages can both EXPORT primitives (encodeBase64/decodeBase64 for byte-level work) AND PROVIDE PLATFORM-COMPATIBLE WRAPPERS (atob/btoa for string-level work matching the standard browser API). §the-named-substrate-with-primitive-plus-platform-wrapper-pair — first-explicit-observation as a tier-3 meta-pattern.
