The 113-line README for @endo/ses-ava is the twenty-third package in the pivot cluster, and it opens a shape that is neither runtime substrate nor data format nor control-flow primitive nor bundling-and-transport machinery nor developer-discipline tooling. §the-named-testing-substrate-bridge-as-package marks it. The package's purpose is to bridge AVA, the JavaScript test runner, and SES, the substrate the project layers on top of the JavaScript heap. The bridge is asymmetric. AVA does not know about SES; SES, configured by lockdown, redacts error messages and stack traces by default. The bridge brings the two together by initializing SES with a debugging-friendly configuration and giving AVA's `test` function the ability to surface SES errors as authored rather than as redacted. The README names the three concrete debugging affordances explicitly: deep stacks of prior turns, unredacted stack traces, and unredacted error messages. The first connects upward to @endo/eventual-send's turn machinery, where deep async causality is tracked across promise resolutions; the second and third connect upward to @endo/errors, where the redaction discipline lives. §the-named-three-debugging-affordances names the affordance set itself, since the README presents it as a list. The single most structurally interesting move is the choice to ship this functionality as a separate package rather than as a flag on SES or AVA. §the-named-explicit-unredaction-only-where-trusted names the move. SES purposefully redacts error messages and stack traces because an attacker should not be able to read internal state through the error surface. Production code that surfaces a redacted error is functioning as designed. The test environment is different: the developer writes the tests, owns the code, and is inside the trust boundary, so unredaction is safe there. The choice to package the unredaction as a SEPARATE module rather than as a flag is the structural insight. A flag could be flipped accidentally; a separate package must be opted into explicitly. §the-named-trust-boundary-aware-unredaction-package and §the-named-default-safety-with-named-exception-package together name the tier-3 meta-pattern: when a default is safety-driven, the exception that turns it off is a NAMED PACKAGE rather than a flag. The README reinforces this with a specific warning. The "devDependencies" note is unusually explicit: it observes that putting ses-ava in regular dependencies causes bundlers to bundle all of AVA into production. §the-named-devDependencies-not-dependencies-warning names the warning; §the-named-bundler-implication-of-dependency-placement names the tier-3 meta-pattern. The same redaction-trust-tradeoff motivates the warning: AVA shipped to production is itself a foot-gun, and the README treats the user as someone who would understand the bundling implication once it is stated. The "Supporting multiple configurations" section opens a second feature surface. The `ses-ava` CLI consumes `package.json`'s `avaConfigs` field and runs the same test source under multiple environments. §the-named-multi-config-test-runner names the feature. The example given is testing with-and-without lockdown via the same test file; the formal concept underlying it is §the-named-Hardened-Modules-with-varying-defense-degrees: modules using `harden` to defend interface integrity with varying degrees of defense depending on whether they are used in composition with HardenedJS's `lockdown`.
