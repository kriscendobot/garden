The 532-line SES secure-coding guide is the canonical text for the principles every cluster member's discipline composes from. Cycle 377 ingests the first 180 lines — the intro and motivating examples through "harden recursively freezes surface" — and treats the document as partial-ingest, leaving later sections for future complementary-lens cycles. The single most structurally interesting move sits in lines 3 through 7: SES exists "to make it easier to write *defensively consistent* programs. We define **defensive consistency** as a program (or function, or service.. something written in code) that provides correct service to its correctly-behaving customers, despite also being subjected to incorrectly-behaving customers." §the-named-defensive-consistency-as-core-discipline names the move. The discipline is asymmetric — the program is NOT required to give bad service to bad customers, but IS required to keep serving good customers correctly even when bad customers attack. §the-named-correct-service-to-correct-customers-despite-bad-customers names the tier-3 meta-pattern. Three principles ladder up from this. §the-named-trusted-computing-base-must-be-explicit marks lines 8-12's framing: a program is allowed to rely on a TCB, but it must be CLEAR about which code is in the TCB. The discipline is not "trust nothing" but "name what you trust." §the-named-TCB-must-be-named-not-implicit names the tier-3 meta-pattern. §the-named-mutually-suspicious-code-co-existing marks lines 15-16: "Two pieces of mutually-suspicious code can safely interact if both are written in a defensively-consistent style." Two parties, neither trusts the other, both safe via discipline. §the-named-bilateral-discipline-replaces-trust names the tier-3 meta-pattern. §the-named-internet-vs-local-code-same-discipline marks lines 22-28: defensive consistency applies internet-grade discipline to LOCAL code. The OCAP principles are stated explicitly. §the-named-Principle-of-Least-Authority-POLA marks lines 26-28: "We apply the **Principle of Least Authority** (POLA) to these separate components, giving each one the barest minimum of power necessary to do its job. This limits the damage if/when a component becomes compromised or confused." POLA is named with its acronym; this is the canonical text where the principle every competitor's pitch echoes ("least privilege", "scoped access") is named with rigor. §the-named-POLA-as-named-canonical-principle names the tier-3 meta-pattern. The cycle's most structurally important pairing sits in lines 142-146. §the-named-no-ambient-authority-and-connectivity-begets-connectivity-as-twin-principles names the move. The text reads: "Two principles of object-capability security are **no ambient authority**, and **connectivity begets connectivity**. That means the *only* way for two objects to talk to each other or have any causal influence over each other is for there to be a path in the object graph that reaches both of them. Every object in that path gets to decide how much influence to allow." The OCAP discipline distilled into two pithy phrases. The first says nothing is available unless explicitly granted — no implicit globals, no implicit context, no ambient `Math.random` or `Date.now` or `fetch` that any code can grab. The second says causal influence requires an object-graph path — Alice cannot affect Carol unless there is a chain of references from Alice to Carol, and every object in that chain decides how much influence to forward. Together they mean: the object graph IS the authority graph. §the-named-object-graph-IS-authority-graph names the tier-3 meta-pattern. This is the substrate property that makes the social-network model from cycle 374 possible: when the object graph is the authority graph, passing references between principals is passing authority, and a recipient can attenuate before forwarding. The document teaches by exhibiting the attacks SES prevents. §the-named-non-SES-failure-modes-as-named-vulnerabilities marks lines 38-77. Two concrete vulnerabilities are exhibited: (1) returning a mutable Array to a "reader" lets the reader delete entries (too much authority for the reader role); (2) prototype pollution lets writer1 redefine `Array.prototype.push` to swallow writer2's messages. §the-named-teach-by-exhibiting-attack names the tier-3 meta-pattern. The same makeLogger source code is then shown verbatim under SES. §the-named-same-source-different-meaning-pre-and-post-SES marks lines 89-103. The identical code produces a different security posture in SES (intrinsics frozen) versus non-SES (intrinsics mutable). The "in SES but not secure" version still has the reader-deletion vulnerability but no longer has prototype pollution. SES fixes the background vulnerabilities; the foreground application-logic vulnerabilities still require careful coding. §the-named-SES-fixes-background-not-foreground names the tier-3 meta-pattern. The application discipline above SES is named explicitly. §the-named-array-pop-still-works-after-SES marks the local-mutable-Array reality (lines 117-118). §the-named-return-copy-not-the-mutable-original marks the fix on lines 126-138: `read()` returns `[...log]` rather than `log` itself. §the-named-return-copy-as-application-discipline names the tier-3 meta-pattern. A subtle channel is named explicitly. §the-named-functions-are-callable-objects-channel marks lines 149-163: a `write` function shared between writer1 and writer2 is itself a communication channel because Functions are mutable Objects. writer1 can set `write.messageToWriter2 = "psst hey buddy"` and writer2 reads it. SES freezes intrinsics but not application-created Function instances. §the-named-function-as-mutable-channel-without-harden names the tier-3 meta-pattern. The fix is harden. §the-named-harden-recursively-freezes-surface marks lines 165-172: harden applies Object.freeze recursively to enumerable properties and prototype. It does NOT require immutability: hardened Set and Map can still be modified through get/set/add methods. Hardened Arrays ARE immutable. §the-named-harden-freezes-surface-not-state names the tier-3 meta-pattern. The surface (function/method bindings) is locked but internal state remains accessible through the surface API. The final framing sits on lines 174-176. §the-named-hardened-objects-can-close-over-mutable-state marks the observation that "extremely common for the hardened object to close over mutable state. This is a standard pattern for the construction of object-oriented behavior in SES." §the-named-closure-state-as-hardened-class-substitute names the tier-3 meta-pattern; the OO pattern under SES is hardened exports plus closure-captured private state.
