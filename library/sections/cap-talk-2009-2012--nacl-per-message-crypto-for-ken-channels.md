Abstract: Brian Warner's proposal, from a friam discussion of transport security for Ken nodes, is the closest 2012 precursor to Endo's secure-transport design. He observes that E, Waterken, and Foolscap all use verified-certificate TLS, where the object identifier (a SturdyRef/FURL) combines three things: the hash of the expected TLS certificate (the VatID/TubID), a set of connection hints (IP and port), and an unguessable swissnum pointing at a specific object. A node dials the hints, does TLS with each, compares each peer's certificate against the intended VatID, drops mismatches, and sends the swissnum over the first channel that verifies. TLS used this way (trusting a specific cert, not CA signatures) is secure but has three practical failures: implementations expose the peer certificate badly and browser-XHR contexts not at all, so people get validation wrong catastrophically; porting the protocol tempts implementors into the ubiquitous-but-insecure CA path (buying certs, using DNS names as VatIDs, trusting CA roots), and most TLS stacks skip CA checks by default, so the lowest-energy path is wide open to an active attacker; and TLS is *connection-centric*, dragging in `notifyOnDisconnect`, "dead references," and not-yet-live sturdy refs that mismatch Ken's connectionless "send forever" model. His fix separates cryptographic security from transport: apply djb's NaCl `box`/`unbox` (Curve25519) to each message independently. The recipe makes **the VatID the base32-encoded public key** itself; higher/lower VatID split even/odd nonces; a nonce bit marks ACKs and the rest is the sequence number; messages are boxed before checkpoint storage and unboxed on receipt (integrity failures silently discarded); plain TCP (not TLS) carries the bytes; and each vat resends until an authenticated ACK arrives. Because security rides each message rather than a session, encrypted messages can be **store-and-forwarded** through relays, easing intermittently-online nodes, mesh networks, and hybrid realtime/polled delivery — precisely what TLS's full-time-connection assumption forbids.

## The identifier is the key; the channel is incidental

Two moves in Warner's design are the load-bearing ones. First, **self-authenticating identity**: when the VatID *is* the public key, there is no certificate, no CA, and no name-to-key binding to get wrong — verifying a peer is checking that it can `unbox` what you `box`ed to that key, which collapses the whole "expose the peer cert and validate it yourself" failure surface. The identifier carries its own authentication. Second, **per-message rather than per-connection crypto**: security becomes a property of the datagram, not of a live socket, so the programming model stops caring whether a connection is up. That is what lets the same secure channel run over store-and-forward, mesh, or polled transports, and it is what dissolves the connection-state machinery (dead refs, disconnect notifications) that TLS forces into the object model. Warner is explicit that TCP is still useful for reliability and congestion control but should not be *exposed* to the programming model — connections are an illusion the transport keeps to itself.

## Bearing on Endo

This thread is, in outline, the OCapN-over-Noise transport the garden's Endo work later builds. Endo's peer identity is a per-agent keypair and the node is named by its public key, exactly Warner's "VatID is the base32 public key"; the connection is a hardened, mutually-authenticated channel (Noise IK rather than raw NaCl box, but the same Curve25519 lineage and the same self-authenticating-key principle), and the swissnum survives as the unguessable object pointer sent once the peer is authenticated. Warner's per-message, store-and-forwardable framing is the argument for `captp` being able to run over an asynchronous, possibly-relayed transport rather than demanding a live TLS session — the intermittent-node and mesh cases he names are the same ones a personal-agent mesh faces. His warning that the CA path is the seductive insecure default is the standing reason Endo never trusts a certificate authority for peer identity.
