Abstract: Norman Hardy opened the month by pointing at the Microsoft Research paper "Uniqueness and Reference Immutability for Safe Parallelism" (MSR-TR-2012-79), noting it extends the common reference-as-capability notion with uniqueness and immutability patterns not available in ordinary references. Brad Cox — a longtime capability-curious observer (of Objective-C fame) newly "thinking about diving in for real" — hijacked the thread with the field's oldest adoption question: how does making *languages* secure do anything against viruses, which won't be written in a secure language anyway? Doesn't the virus problem demand capabilities at the operating-system or hardware level? The answers split three ways. David Barbour argued the *opposite* of Cox's intuition: it is far easier to build a new VM or language runtime than to convince the world onto a new OS or hardware, so progress should start *high* — web-apps, browsers, extension/app-stores — and work down; if you simply refuse to accept code (apps, libraries, extensions) written in insecure languages, malign code becomes much easier to prevent, and performance need not suffer (compile and cache, or trust a signing intermediary). He added that authorization and authentication are *symptoms*, not causes, of secure systems; the real basis for security should be dataflow and modular structure. Monty Zukowski pointed to FreeBSD **Capsicum** as the OS-level answer already shipping (Cox: "Exactly what I was hoping for"). On hardware capabilities, Barbour noted real resistance — people fear sparse caps baked into hardware would challenge their ability to *own* the hardware they use, and at the lowest levels many prefer physical security for consumer electronics. Cox's rejoinder framed the stakes historically: the industry chose authentication-based over authorization-based security in the 1970s, "with viruses the delayed consequence," and his question was how to "dig out of this hole" — with the pointed closing "Isn't that exactly what we've been doing for the last 40 years? Are we winning yet?"

## Start high and refuse insecure code, or start low at the OS

The thread's live disagreement is *where the leverage is*. Cox's model is bottom-up: viruses are native code, so only the OS or hardware can contain them, and language-level capabilities give "no leverage against the virus example." Barbour's model is top-down and turns on a different premise: if the platform *refuses to run code in insecure languages at all*, the virus written in an insecure language never gets admitted, so the containment moves to admission plus language safety rather than to runtime OS interposition. The two are not really opposed on mechanism — Capsicum (OS) and a memory-safe VM (language) are both cited approvingly — but on *transition strategy*: Barbour bets the higher layers are where a new security model can actually be deployed, because you can ship a runtime without replacing anyone's kernel. Barbour's deeper claim, that authorization and authentication are symptoms and the true basis is dataflow and modular structure, reframes the whole question: security is not primarily an access-check bolted on, it is a consequence of *how authority flows through a well-modularized system* — the "security as extreme modularity" thesis. Cox's "are we winning yet?" is the honest scoreboard note the optimism has to answer to.

## Bearing on Endo

Endo is the top-down bet made concrete, and it is Barbour's argument nearly verbatim. Endo runs guest code in Hardened JavaScript — a memory-safe, capability-disciplined *language* runtime — precisely because you can ship that runtime to an ordinary computer without replacing its OS or hardware, which is the deployment path Barbour said would actually move. "Refuse code in insecure languages" is Endo's compartment/`lockdown` posture: guest code that could reach ambient authority is simply not admitted to the confined evaluator. Barbour's "authorization and authentication are symptoms; the basis is dataflow and modular structure" is the Endo thesis that security *is* extreme modularity — a guest can only affect what it was handed, so reasoning about authority reduces to reasoning about what references flow where. Cox's OS/hardware point is not wrong so much as a different layer: Endo composes *with* an OS sandbox (or Capsicum-like confinement) when available, treating process confinement and the object-capability protocol as separate, complementary layers rather than substitutes. See [nacl-descriptors-confinement-not-capabilities](cap-talk-2009-2012--nacl-descriptors-confinement-not-capabilities.md) and [capsicum-practical-capabilities-for-unix](cap-talk-2009-2012--capsicum-practical-capabilities-for-unix.md), and the concept [[security-as-extreme-modularity]].
