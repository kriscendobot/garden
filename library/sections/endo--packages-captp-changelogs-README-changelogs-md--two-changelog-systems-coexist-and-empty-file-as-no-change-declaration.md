The 13-line `packages/captp/changelogs/README-changelogs.md` is a convention document describing the older per-PR per-package changelog file system used in select @endo packages. The structurally interesting move is what this file's mere existence reveals: the @endo monorepo runs TWO changelog systems concurrently. The newer `.changeset/*.md` files at the repo root are consumed by `@changesets/cli` to manage versioning and CHANGELOG generation. The older `packages/<pkg>/changelogs/$ISSUENUMBER.txt` files in select packages are consumed by a separate NEWS.md generator. §the-named-two-changelog-systems-coexist names the move; §the-named-evidence-of-in-progress-migration-via-coexistence names the tier-3 meta-pattern. The older system survives in packages that haven't fully moved over (captp and marshal both have identical 13-line copies of this README in their `changelogs/` directories). The post-pivot quartet (eslint-plugin from cycle 359, ses-ava from cycle 361, benchmark from cycle 363, skel from cycle 365) all use the newer .changeset/ system only; they have no `changelogs/` directory. §the-named-system-restricted-to-some-packages-not-all names the structural fact; §the-named-legacy-discipline-not-applied-to-new-packages names the tier-3 meta-pattern. In-progress migrations often look like this — old packages keep both systems, new packages start fresh with only the new one. The naming convention is itself worth marking. §the-named-per-PR-changelog-file-named-by-issue-number marks the `$ISSUENUMBER.txt` convention: one file per PR, the filename IS the cross-reference to the issue tracker. The contents describe the downstream-visible changes; the filename carries the issue number for rendering as a link in NEWS.md. §the-named-filename-as-issue-number-as-cross-reference names the tier-3 meta-pattern. The scope of recording is explicitly named. §the-named-downstream-visible-changes-as-recording-scope marks lines 2-5: "describe any downstream-visible changes in it (one per line). For libraries, this should include anything a developer using this library needs to know when they upgrade to the new version (API changes, new features, significant bugs fixed)." The scope is consumer-facing; a downstream developer is the imagined reader. §the-named-consumer-facing-changelog-scope names the tier-3 meta-pattern. Internal refactorings, lint fixes, build script tweaks do not belong in this file UNLESS they have downstream consequences. The most structurally interesting framing is the empty-file discipline. The empty file is the answer when no downstream effect.
