Root cause: this runner spawns two long-running subprocesses with no wall-clock bound of their own — `provision_project()`'s `git fetch`/`checkout`/`submodule update --init` (lines ~53-83, and the quarantine-and-reclone retry path at ~103-122 which can force a full fresh clone+submodule-init on corruption) and the `cargo +$TOOLCHAIN fuzz run … -max_total_time="$secs"` invocation (lines ~141-146). `-max_total_time` only bounds libFuzzer's *run* phase — the cargo-fuzz *build* phase (ASAN-instrumented, per one of 9 targets) is unbounded, so a cold cache, a toolchain drift, or a stuck network fetch can silently blow the per-tick budget across 9 targets and exceed the unit's 3600s TimeoutStartSec. Second, ironhorse-fuzz.sh (the caller) runs this runner synchronously in its foreground, so its own TERM trap (`cleanup; exit 143` — only removes ART_ROOT, never signals the child) cannot preempt or reap the in-flight cargo/libFuzzer process tree; combined with the unit's `KillMode=mixed` (SIGTERM to the main process only, not the whole cgroup), the fuzz subprocess never receives SIGTERM at all, so systemd's 30s TimeoutStopSec SIGKILL backstop fires every time instead of the graceful shutdown path the service's own comments describe. Fix: wrap both the provisioning git calls and the `cargo fuzz run` invocation in `timeout --signal=TERM --kill-after=<n> <budget>` (new `GARDEN_IRONHORSE_FUZZ_PROVISION_TIMEOUT_SECS`/derive the cargo budget from the existing per-target `$secs` plus a fixed build-time allowance), and propagate SIGTERM into the timeout'd child instead of relying on the cgroup-wide kill, so a stuck build/fetch is bounded, diagnosable, and self-terminating well inside both `TimeoutStartSec` and `TimeoutStopSec`.
