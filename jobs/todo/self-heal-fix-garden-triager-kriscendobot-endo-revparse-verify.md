In scripts/jobs/triager.sh, the new_sha resolution (lines 55-57) is corrupted on any repo where the first candidate ref doesn't resolve (e.g. a bare clone lacking `refs/remotes/origin/<ref>`). Bug: `new_sha="$(git --git-dir="$BARE" rev-parse "refs/remotes/origin/$ref" 2>/dev/null || git --git-dir="$BARE" rev-parse "$ref" 2>/dev/null)"` — plain `git rev-parse` echoes the literal, unresolvable argument to stdout (verified: `git rev-parse refs/remotes/origin/master` prints `refs/remotes/origin/master`, exit 128), and since the `||` fallback shares the command substitution, that echoed arg is concatenated with the real sha from the fallback. Result: `new_sha` = `"refs/remotes/origin/master\n<sha>"`, a two-line value that then breaks the handler with `fatal: ambiguous argument 'refs/remotes/origin/master\nf859ca06...'` and exits 1; the failcount breaker keys on the bad value so it never clears. Failure signature (garden-triager@kriscendobot-endo): log line `change on kriscendobot-endo:master: <none> → refs/remotes/origin/master` followed by a bare sha on the next line, then `fatal: ambiguous argument`. Fix: add `-q --verify` to both rev-parse invocations so a failed resolve produces NO stdout (and peel to a commit), e.g. `new_sha="$(git --git-dir="$BARE" rev-parse -q --verify "refs/remotes/origin/$ref^{commit}" 2>/dev/null || git --git-dir="$BARE" rev-parse -q --verify "$ref^{commit}" 2>/dev/null)"`. Verify against a bare clone whose remote refs land under `refs/heads/*` (so the `refs/remotes/origin/*` candidate misses) that `new_sha` is a single clean sha and triage proceeds.
