In `/home/kris/scripts/jobs/self-heal-run.sh`, a signalled shutdown is treated as clean for the responder but still preserves the signal exit code: the `is_expected` branch runs `exit "$rc"`, so a SIGTERM-driven stop returns 143 (or 130 for SIGINT). systemd records that as `Main process exited, code=exited, status=143` → `Failed with result 'exit-code'` on EVERY `systemctl stop`/`restart` of a self-heal-wrapped continuous unit (observed on garden-bulletin at 2026-06-27T05:30:11Z), polluting the warning stream and leaving the unit flapping to a false `Failed` state. The wrapper's own header says a systemd stop "is a CLEAN shutdown, never a diagnosed failure" — make the exit code agree. Change the clean-exit path so that a signalled shutdown returns 0 instead of the signal code: introduce a `clean_shutdown` flag set when `got_signal=1` OR `rc` is 143/130 (the existing `case "$rc" in 143|130)` arm), and in the `if [ "$is_expected" -eq 1 ]` block do `exit 0` when `clean_shutdown=1`, otherwise `exit "$rc"` (so genuine non-signal `--expect` codes still pass through unchanged and real failures still preserve rc for Restart=/OnFailure=). This is a single-point fix that corrects the false-failure for every continuous garden-* unit (bulletin, foreman, watchman, proxy, mention/repo/comment watchers) at once. As a belt-and-suspenders, also add `SuccessExitStatus=143 130 SIGTERM SIGINT` to the `[Service]` section of the long-running unit templates under `scripts/systemd/` (garden-bulletin.service first) so any future bypass of the wrapper still doesn't mark a SIGTERM stop as failed.
