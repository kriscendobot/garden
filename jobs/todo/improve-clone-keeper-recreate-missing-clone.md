Make `scripts/jobs/clone-keeper.sh` remediate a *missing* tracked bare clone instead of warning-and-skipping it forever. `keep_clone` currently does `log "WARN: tracked clone $dir is missing…"; return 0` when `rev-parse --git-dir` fails, so a vanished clone (observed for `worktrees/endojs-endo.git`) blocks upstream re-ingestion exactly like the six-week stale-clone incident the script header cites — the one thing this keeper exists to prevent. Extend the `GARDEN_TRACKED_CLONES` row format from `<dir>|<remote>|<branch>` to an optional `<dir>|<remote>|<branch>|<url>` (default the endo row's url to `https://github.com/endojs/endo.git`); when the clone is missing AND a url is configured, deterministically recreate it with `git clone --bare "$url" "$abs"` followed by `git -C "$abs" config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'` (the exact recipe `scripts/jobs/ensure-project-worktree.sh` prints), then fall through to the normal fetch+fast-forward. If no url is configured for a missing clone, escalate via `alert_maintainer`/the maintainer inbox rather than an un-drained WARN, so a vanished clone surfaces to a human instead of sitting invisible for weeks. Add a case to `scripts/jobs/test/clone-keeper-test.sh` covering the recreate-when-missing path and the escalate-when-no-url path.
