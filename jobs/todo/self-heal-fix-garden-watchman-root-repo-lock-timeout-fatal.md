`scripts/jobs/watchman.sh` exits with code 1 (`FATAL: cannot resolve deployed HEAD in /Users/dom/garden`) when another process holds the root repo's lock exclusively for longer than its retry window. In this failure, PID 649847 held `.garden-state/repo-locks/a267950e…/repo.lock` from epoch 1792157832 (13:37:12Z). The holder status was `busy`, so it was alive and not yet stale; it was most likely root-repo maintenance or a repack, and it has since exited. Every `git rev-parse HEAD` attempt hit `garden repo lock: timeout after 10s … (shared)`, and the earlier fetch failed for the same reason. The read loop swallows the exit status with `|| true`, so a timeout on the lock wrapper (`_garden_lock_wait`/`_garden_lock_open` in `scripts/jobs/common.sh` return **124**) looks the same as a HEAD that can't be resolved. Three attempts with a 1s sleep (~33s in total) can't outlast a normal exclusive hold.

Fix: in the HEAD-resolve loop in `watchman.sh`, capture the exit status of `git rev-parse` instead of discarding it. If the final failure was 124, which is the documented lock-timeout code, log a WARN such as "root repo lock busy; skipping tick" and `exit 0`. The next timer tick will retry, so there's no point failing the unit and waking the self-heal responder. Keep the `die` for any other non-zero status, since a HEAD that really can't be resolved still needs an alert. Do the same for the `origin/main2` rev-parse, falling back to `local_sha` as it already does. Add a case to `scripts/jobs/test/` that stubs `git` to return 124 and asserts that the watchman exits 0 without the FATAL line.
