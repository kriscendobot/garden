scripts/jobs/deadmail.sh
Recurring scheduled fan-out drivers (e.g. the hourly `endo-sturdyref-press`) structurally dead-letter every sub-job reply: `scheduler.sh` dispatches each tick as a fresh short-lived doer with a timestamped base, and per-doer inboxes are destroyed at completion (skills/message-bus/SKILL.md), so a sub-job's completion report addressed to the tick that spawned it can never reach the next tick. Today `deadmail.sh` salvages it by promoting to a *generic* gardener ("do what the message asked / carry the reply forward"), which — as the recovered entry 193734Z-progress-gardener-c436db.md shows — can only restate the report unverified and then merely *hope* the next scheduled tick discovers the standalone journal entry. Harden the routing: when a dead-mail entry's `to:` base strips down to an active recurring schedule's `job_basename_prefix` (match `schedules/<name>` frontmatter), deposit the carried-forward report into a durable per-schedule mailbox keyed by the schedule name (timestamp-free) instead of spawning a generic gardener. Pair this with a small `scheduler.sh` change that injects any pending per-schedule carry-forward into the next dispatched job body — mirroring the existing `anchored_window` context-injection block — so the report reaches the schedule's next tick deterministically as the addressed reader, rather than by hope. Non-schedule recipients keep today's generic-gardener promotion path unchanged. This turns a per-tick guaranteed dead-letter + unverified-restate into a mechanical hand-off to the true reader. Most-implicated script is `scripts/jobs/deadmail.sh` (the routing/promotion decision point); the paired injection lands in `scripts/jobs/scheduler.sh`.
