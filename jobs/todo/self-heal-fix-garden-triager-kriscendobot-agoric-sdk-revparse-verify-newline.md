In `scripts/jobs/triager.sh` (around lines 55-57), the `new_sha` capture uses bare `git rev-parse` in a `cmd1 || cmd2` command substitution. When `refs/remotes/origin/$ref` does not resolve (a real, recurring race on cold/partial fetches), `git rev-parse` echoes the literal argument to stdout *before* exiting nonzero, so the `||` fallback's SHA gets newline-appended, producing `new_sha="refs/remotes/origin/master\n<sha>"`. This poisoned value is later passed to the triage handler's git command, yielding `fatal: ambiguous argument 'refs/remotes/origin/master\n<sha>'` and the triager's exit 1 / FATAL. Fix: add `--verify -q` to BOTH rev-parse calls so an unresolved rev produces empty stdout instead of echoing its argument:
```sh
new_sha="$(git --git-dir="$BARE" rev-parse --verify -q "refs/remotes/origin/$ref" 2>/dev/null \
            || git --git-dir="$BARE" rev-parse --verify -q "$ref" 2>/dev/null)" \
  || die "cannot resolve ref '$ref' in $slug"
```
(Verified: `--verify -q` on a missing ref emits nothing and exits nonzero, so only the fallback's clean SHA survives; on a good ref it emits just the SHA.) Also audit `handlers/triager-claude.sh` for any other bare `rev-parse`/`git log` on an interpolated ref that could inherit the same echo-the-arg pollution.
