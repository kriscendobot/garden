Add a `timeout` bound around the job-handler invocation in `scripts/jobs/gardener.sh` (the `"$GARDEN_GARDENER_ID=... "$GARDEN_JOB_HANDLER" "$base" "$jobfile" "$report"` call at gardener.sh:111), not inside individual handlers, so the bound covers every handler (`handlers/gardener-claude.sh`'s unbounded `claude -p` at line 102, the gardening state machine, etc.) uniformly. Today a handler has no upper runtime bound: a wedged/runaway `claude -p` (network hang, infinite tool loop) runs forever, holding one of the ~100 scarce gardener instances and its `$BUSY_MARKER` indefinitely; that stuck busy marker also blocks every `deploy-garden.sh` quiesce (forcing the full `GARDEN_DEPLOY_DRAIN_TIMEOUT`=600s wait then abort on each deploy), and after `GARDEN_CLAIM_TTL` the reaper requeues the SAME base while the original handler is still running, so the job executes concurrently on two gardeners. Wrap the call as `timeout --signal=TERM "${GARDEN_HANDLER_TIMEOUT:=2400}" <handler...>` with a new env knob defaulting comfortably below `GARDEN_CLAIM_TTL` (3600) and above `GARDEN_DEPLOY_DRAIN_TIMEOUT` (600) — the `< CLAIM_TTL` invariant guarantees no handler outlives the reaper's stale-claim window, closing the duplicate-claim hole. The discrimination this preserves is deliberate: a genuine external kill (deploy drain) still surfaces as `rc=143` and stays transient via `is_external_kill_rc`, while `timeout`'s own `rc=124` is a non-signal code that falls through to the real-failure branch and escalates to the gardener inbox immediately — so a true self-hang is surfaced now instead of silently TTL-requeuing for ~5h. State the `GARDEN_HANDLER_TIMEOUT < GARDEN_CLAIM_TTL` constraint in a comment at the call site and add a test alongside `scripts/jobs/test/signal-kill-classifier-test.sh` asserting a `124` capture is classified real (not transient).
