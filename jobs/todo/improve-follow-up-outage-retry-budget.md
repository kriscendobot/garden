scripts/jobs/follow-up.sh
The bounded-retry counter cannot distinguish "this digest is wedged" from "the whole fleet is down", so a fleet-wide outage silently spends the quarantine budget and then discards good work. `garden-follow-up` failed 4 consecutive ticks at 08:48:07, 08:58:06, 09:08:12, 09:18:06 (`FATAL: follow-up handler failed (N/5)`), inside the same storm that took down ~30 gardener handlers from 08:04. The pending set was unchanged, so `$FAILCOUNT` incremented each tick; one more environmental tick reaches `GARDEN_FOLLOWUP_MAX_RETRIES=5` and the ceiling branch (~line 158) advances the seen-marker, **quarantining tada reports whose follow-ups were never actually attempted** — permanent loss of the follow-up actions, on a purely environmental cause.

The distinguishing signal already exists and is already computed nearby. `handlers/follow-up-claude.sh` classifies its inner `claude -p` failure with `is_transient_claude_signature` and deliberately `die`s only on the transient arm (routing non-transient failures to the maintainer and exiting 0), and `common.sh` exports `fleet_brake_engaged`. Gate the increment: when the handler failed *and* (`fleet_brake_engaged` is true, or `is_transient_claude_signature "$(cat "$handler_out")"` matches, or the handler's output is empty per `is_transient_empty_failure`), leave `$FAILCOUNT` unchanged — log and retry next tick without consuming budget — so only failures attributable to the digest itself count toward quarantine. Optionally cap the un-counted stretch with a separate wall-clock bound so a permanently-offline host still surfaces to the maintainer rather than retrying forever. Consider also having the handler distinguish its two arms to the caller by exit code (e.g. a dedicated rc for "transient, do not count") rather than making `follow-up.sh` re-derive the classification from captured text.
