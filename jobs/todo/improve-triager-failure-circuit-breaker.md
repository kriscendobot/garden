Add a per-change consecutive-failure circuit breaker so a persistently-failing triage handler stops crash-looping. Today when `$GARDEN_TRIAGE_HANDLER` fails (line 56/62) the cursor is left unadvanced and the systemd timer re-invokes the identical `${old_sha:-<none>} → $new_sha` transition every ~2 minutes with no backoff — observed live for `kriscendobot-minion.town`, an endless FATAL/restart loop filling the journal. Because the failing transition is deterministic (same old→new SHAs, same change), retrying it thousands of times cannot help. Keep a durable failure count in the journal cursor keyed to the current `new_sha` (extend `CURSOR_KEY`/`cursor-set.sh` with e.g. `fail_sha:`/`fail_count:` fields, or a sibling `activity/<slug>/failcount` key): on handler success clear it and advance as today; on handler failure, if `fail_sha` matches the current `new_sha` increment the count, else reset it to 1 and record `fail_sha: $new_sha`. Once the count reaches a threshold (default e.g. `GARDEN_TRIAGE_FAIL_THRESHOLD=5`), stop re-triaging that SHA: log a single WARN, open one maintainer-inbox message (message-bus) naming the slug and failing range so the failure is surfaced instead of silently hammered, and `exit 0` (not `die`) so systemd stops flapping the unit. A newly-observed `new_sha` clears the breaker automatically, so a later legitimate change still triages. Mirror the shape of the existing `ci-watcher.sh` cascade circuit-breaker for consistency. This moves crash-loop suppression off "systemd restart forever" and into deterministic script logic.
