In `--changed` mode the gate re-checks entire touched files and so fails (exit 1) on pre-existing dangling links that live on rows the current change never touched. Because every scholar ingest appends a row to shared index files (`sources/README.md`, `sections/README.md`, `topics/*.md`, `concepts/*.md`), any long-lived pre-existing dangler in one of those files turns the prescribed post-ingest gate RED for breakage the scholar did not introduce — forcing each cycle to hand-reason "these two are pre-existing, not mine" (see the 2026-07-05 221248Z scholar result: `[[engine-implementation]]`/`[[local-model-serving]]` in `sources/README.md`). Move that attribution off the agent and into the gate: the `--changed` exit status must fire ONLY on newly-introduced danglers. Recommended approach — when a dangling link is found under `--changed`, test whether the same referrer→target link also dangles at `$BASE_REF` (it existed and dangled there); if so, classify it advisory (report it, like the `--all` leaf-body advisory count, but do NOT set the failing DANGLING count), and fail exit only on danglers absent at base. A lighter alternative is to restrict the whole-file `check_links_in` on shared index files to just the changed hunks (`git diff $BASE_REF -- <file>` added/context lines) rather than the entire file, so untouched pre-existing rows are never re-surfaced; the baseline-diff approach is more precise and also covers the source/section pages. Preserve current behavior when `$BASE_REF` is unavailable (fall back to whole-file, as today). This keeps the scholar's post-ingest gate a trustworthy skip-proof signal instead of a per-cycle false alarm the agent must talk itself past.
