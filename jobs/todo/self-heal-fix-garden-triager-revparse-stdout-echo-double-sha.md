In `scripts/jobs/triager.sh` (~lines 55-56), the ref-resolution `new_sha="$(git --git-dir="$BARE" rev-parse "refs/remotes/origin/$ref" 2>/dev/null || git --git-dir="$BARE" rev-parse "$ref" 2>/dev/null)"` produces a corrupted TWO-LINE `new_sha` whenever the primary ref is unresolvable. Bare `git rev-parse <bad-rev>` echoes the literal argument to **stdout** (exit 128); `2>/dev/null` suppresses only stderr, so the echoed `refs/remotes/origin/master` line survives and the `||` fallback appends the real SHA (`37a4fa31…`). The concatenated value is later passed as a git revision, giving `fatal: ambiguous argument 'refs/remotes/origin/master\n37a4fa31…': unknown revision`, and the triager dies exit 1 on every tick (circuit breaker never advances the cursor). Fix: add `--verify -q` to BOTH rev-parse calls (`git --git-dir="$BARE" rev-parse --verify -q "refs/remotes/origin/$ref" || git --git-dir="$BARE" rev-parse --verify -q "$ref"`), which makes rev-parse silent and empty-on-failure instead of echoing its argument, so `new_sha` is always a single clean SHA. Observed on garden-triager@kriscendobot-agoric-sdk (ref `master`), where the bare clone has `refs/heads/master` but no `refs/remotes/origin/master`. Add/extend a triager test covering the "primary ref unresolvable, fallback resolves" path asserting `new_sha` is one line.
