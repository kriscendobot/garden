In `scripts/jobs/gardener.sh`, the transient-handler-failure branch (the `if [ "$transient" -eq 1 ]` block, ~line 188) emits a generic progress line with no indication of how many times the SAME job has already failed this way, so a job that dies deterministically-by-signal (rc=143/130/137 + empty capture) looks identical on its 1st and 5th transient requeue and only surfaces after the reaper's ~5×TTL poison cycle (~5h). Harden the transient classification's observability: before emitting the transient progress line, read the reaper's already-present `<!-- garden-reaped: N -->` marker from `$jobfile` (format defined in `scripts/jobs/reaper.sh` as `REAP_MARKER_RE`; extract with the same `sed -n 's/^<!-- garden-reaped: \([0-9][0-9]*\) -->$/\1/p' | tail -1` the reaper uses) and include that count in the progress line (e.g. `... transient handler outage (requeue cycle N) ...`, defaulting to 0 when the marker is absent). This is read-only of an existing marker — no new state, no CAS interaction, and it does NOT re-open the OPEN failed-job-lane design decision flagged in the comment for maintainer review. It makes a not-actually-transient job greppable in the journal before the multi-hour poison threshold fires, so a human or a future watchman self-test can catch a deterministically-killed job (a wedged scholar fetch, an OOM) early instead of after ~5h of invisible looping. Cover it in `scripts/jobs/test/empty-output-classifier-test.sh` with a case asserting the count appears in the transient line.
