# Port the XS 65535-locals-per-frame limit check to Iron Horse

Repo: endojs/endo-but-for-bots, branch `llm`. Crate: `rust/engine/ironhorse-compile`
(parser/compiler). Related: `rust/engine/ironhorse-vm`, `rust/engine/ironhorse-262`,
`rust/engine/xs-oracle`.

## Background (kriskowal, 2026-09-14)

XS has a hard limit of **65535 locals in a frame**. The XS parser was not checking
it, so it generated byte code that could crash in various ways. OSS-Fuzz found
several paths to it; Fuzzilli never did, because it does not tend to generate cases
that ridiculous. The XS fix rejects such scripts at parse time and ships in
Moddable's next release.

**The XS fix is NOT upstream yet** as of 2026-09-14
(`Moddable-OpenSource/moddable` master tip `b6e06ba70`, 2026-09-04). Do not wait
for it and do not try to cherry-pick it. Construct the Iron Horse solution
independently from the semantics described here. A separate weekly schedule
(`xs-frame-locals-limit-upstream-watch`) is watching for the upstream fix and will
reconcile your port against it once it lands.

## Task

1. **Establish the ceiling.** Find where `ironhorse-compile` assigns frame-local
   slots and what width that index is. Determine whether Iron Horse has the same
   65535 ceiling (a u16 slot index) or a wider one, and state the answer explicitly
   in the PR description. The whole change hinges on that fact.
2. **Enforce at compile time.** A script whose frame would exceed the ceiling is
   rejected with a clean, catchable error and never lowered to bytecode. Rejection
   at parse/compile time, not a runtime trap and not a debug assertion.
3. **Cover every path that accumulates frame locals**, not just plain `var`/`let`
   declarations: parameters, destructuring bindings, function declarations, catch
   bindings, and anything else `ironhorse-compile` lowers into a frame slot. A check
   that counts only one of these leaves the bug reachable through the others.
4. **Regression tests.** A frame just under the limit compiles and runs; one just
   over it is rejected with the expected error; at least one case per accumulation
   path from step 3. Generate the sources programmatically in the test rather than
   checking in megabyte fixtures.
5. **Run the engine suites from `rust/engine`** per the crate README. This touches
   the compiler, so watch for test262 movement and report any delta rather than
   silently absorbing it. Note the standing Iron Horse test262 floor before you
   start so a regression is visible.

If Iron Horse turns out **not** to share the ceiling (a wider slot index), the
change is about XS conformance rather than memory safety. Say so plainly, and
implement whatever limit keeps Iron Horse's observable behavior aligned with XS on
these inputs. Do not invent a limit Iron Horse does not need without explaining
why.

## Notes

- `ironhorse-fuzz` differential findings have a known oracle-artifact class; if you
  touch or run it, do not read a divergence there as a port bug without checking
  against that class first.
- A fresh worktree needs the `c/moddable` submodule and generated JS bundles before
  the engine builds. Budget for that.
