Add per-worker memory confinement so an out-of-memory spike is contained to the offending gardener's own cgroup instead of letting the host-wide kernel OOM killer pick an arbitrary victim. Concretely, add to the `[Service]` section: `MemoryAccounting=yes`, a soft `MemoryHigh=` throttle, and a hard `MemoryMax=` cap (suggested starting values e.g. `MemoryHigh=6G` / `MemoryMax=8G` — size to comfortably hold one `claude -p` handler plus the node/yarn toolchains a job builds with; leave a comment tying the choice to the handler footprint so it can be tuned). Rationale: the observed sequence was two consecutive `enable --now garden-gardener@8.service` 5s-bound timeouts followed by `Failed with result 'oom-kill'` — a start-under-memory-pressure loop. Today the unit has no `Memory*` or `OOMPolicy` keys, so the OOM killer chooses a victim across the whole host; it happened to catch gardener-8 (which self-restarts, tolerable), but the same unconfined pressure can instead kill a leader-only singleton (foreman/scheduler/watchers double-nothing but simply die) or a mid-job peer, whose SIGKILLed `claude -p` handler then requeues and burns a poison TTL cycle — the very rc=143/requeue outage class the unit's `KillMode=mixed`/`TimeoutStopSec` block already guards against on the stop/restart path but leaves open on the OOM path. `MemoryHigh` (soft) applies reclaim/swap pressure before any kill, so a transient spike degrades into swap (the host has 8G swap, 128G RAM) rather than a hard kill; `MemoryMax` (hard) confines the eventual OOM to the offending worker's cgroup so the killer targets it deterministically and it restarts cleanly, never sniping an innocent process. Keep the change to this one unit — do not add a `background.slice` aggregate cap, which would let one hungry worker starve its idle peers' headroom. Note the interaction with the `xs2rust`/rust-build family of jobs, which are the memory-heaviest handlers, when picking the cap so a legitimately large build is not OOM'd below its real need.
