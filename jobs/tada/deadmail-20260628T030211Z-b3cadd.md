## Completion report

**Job:** dead-lettered message for `issue-kriskowal-garden-9`. Maintainer (kriskowal) commented on kriskowal/garden issue #9 asking: *"investigate whether simply recompiling XS with a taller stack limit would resolve the issue."* I picked up the intent and answered it empirically.

**What I did:** Ran a controlled single-variable experiment against the v320 ymax0 contract bundle on this host — driving a fresh `importBundle(bundle-ymax0.json)` through a from-source `xsnap-worker` 0.15.0 (gcc 13, the instrumented build), varying only `stackCount` in `xsnap-worker.c`. The surviving artifacts (cached prebuilt + from-source build tree, instrumented worker, driver `/tmp/xs6/`, bundle b64) were all intact.

**Result (decisive):**
| `stackCount` | outcome |
|---|---|
| 4096 (on-chain default) | overflow, exit 12, value stack 4096/4096, 9 frames |
| 4224 / 4352 / 8192 | import OK |

So a taller stack **does** resolve this crash, and the margin is razor-thin — the v320 import overflows the default by only **~128 value-stack slots** (a +128 bump to 4224 already clears it). This matches the prior instrumented mechanism (fixed bundle *width*, not per-incarnation growth), so it wouldn't creep back for this contract.

**Caveats I surfaced:** `stackCount` is a compile-time constant with no runtime knob; it's the *on-chain* xsnap that matters, and raising it is a consensus-affecting lockstep validator upgrade (agoric-sdk/governance — out of garden scope); it globally relaxes the limit for all contracts; and it masks a cheaper non-consensus fix (shrink the wide frame — the `hex.js decodings` loop alone reclaims ~1000 slots, far more than the 128-slot deficit).
