# Weekly Qwen watch — completion report

**Outcome: nothing new is harnessable this week**, but the watch turned up two things worth more than the usual one-liner.

## What I did
Probed the live host state first (`model-routing-defaults.tsv`, journal `config/model-routing`, `ollama list`, `/v1/models`, `journal/hosts/<this-host>`, GTT sysfs, disk), then swept for post-3.6 Qwen releases and checked each for an ollama tag via library pages plus **read-only registry manifest fetches** — no pulls, no state changed anywhere.

## Findings
1. **`qwen.ai/blog` is not readable as data.** Fully client-rendered SPA; its backing `GET /api/v2/article/list` returns `{"success":true,"data":[]}` for every param/locale/Referer I tried; `sitemap.xml`/`robots.txt` serve the SPA shell. `qwenlm.github.io/blog` is stale (last post Sept 2025). I said so plainly in the report rather than inventing entries, and grounded the watch in the ollama registry + HF `Qwen` org + dated coverage — which is what actually decides harnessability.

2. **The job's premise was wrong.** The hermit lane does *not* serve `qwen3.6`. The live tracked default is **`qwen3:0.6b`** (0.6B dense), no journal override exists, `ollama list` is **empty** (nothing pulled at all), and this host is at **`hermits: 0`** — the lane isn't running. `qwen3.6` is a real ollama library name, which is likely how the two got conflated.

3. **Nothing newer has weights.** Qwen3.8-Max (2.4T MoE, previewed Jul 19 at WAIC) is a closed API preview — `/library/qwen3.8` and `qwen3.8-max` both 404, and 2.4T is out of reach regardless. Qwen3.7 VL Flash (Jul 25) — `qwen3.7`, `qwen3.7-vl`, `qwen3.7-flash` all 404, and no Qwen3.7 weights on the HF `Qwen` org (newest there is `Qwen3-ASR-0.6B/1.7B-hf`, ASR not chat). **Watch, don't act.**

4. **An upgrade is already on the shelf**, independent of this week's news: `qwen3.6:35b-a3b-q4_K_M` (= `:latest`), manifest-verified **22.3 GiB**, MoE 35B/~3B-active, 256K ctx — fits the 50 GiB GTT with ~2.2× headroom and lands on the ops-doc's measured `~35B-A3B (Q4) MoE → ~50 tok/s` row. Also flagged the trap: the `-mlx`/`-mxfp8`/`-nvfp4` tags are Apple-MLX and NVIDIA-FP4, unusable on gfx1151/ROCm, and the dense `27b` would cost ~5× throughput per the ops doc's dense-31B measurement.

## What changed
**No commits, no pulls, no routing or hermit-count changes.** A 22 GiB pull plus a fleet-wide routing change is the maintainer's call, not a watch job's — I gave the exact command sequence instead.

- Re-probe `ollama.com/library/qwen3.7` weekly; the 404→200 flip is the trigger.
- Decide the lane's fate: promote the local default to the 35B-A3B MoE, or accept `hermits: 0` and drop the pretense — `qwen3:0.6b` is small enough that it isn't obviously useful.
- **Fix the recurring job spec**: point it at the ollama library + HF `Qwen` org as primary sources (the blog isn't fetchable), and have it read the live routing table + `ollama list` rather than hardcoding a baseline — the hardcoded "serves qwen3.6" is what produced the wrong premise.
