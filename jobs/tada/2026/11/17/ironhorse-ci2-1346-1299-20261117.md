## endojs/endo-but-for-bots#1346 (feat/ironhorse-ocap-frozen-objects)
- **Before:** all three lanes failed on `harden_and_petrify_survive_sqlite_sleep_cycles` (run 36336540205, 09-27). After the store is suspended and resumed, its final export was 6 bytes larger than the export from a machine that never paused.
- **Cause:** a real bug in the PR, not an outdated golden.
  - The PR adds an integrity cache that is not saved with the snapshot, so a resumed machine starts with it empty.
  - With the cache empty, the freeze/seal check (`test_integrity_level`) builds the object's full list of property keys. That allocates temporary strings on the heap.
  - With the cache filled, the same check skips that step and allocates nothing. So the resumed machine's heap no longer matched the machine that never paused.
- **Fix:** when the cache is empty, the check now reads the stored property flags directly. If they show the object is sealed or frozen, it charges exactly what the filled-cache path charges, records the result in the cache, and returns without building the key list. If they don't, it runs the original full check, which never uses the cache.
- **Local checks:** these all pass:
  - the engine suites under both providers;
  - `ironhorse-store-sqlite` (all 74 `engine_lifecycle` tests);
  - `golden_computrons` with the `cost-calibration` and `consensus` features;
  - `cargo fmt` and `clippy`.
  - The parity lane could not run here: the sandbox couldn't download a crate (`memchr`).
- **Commit pushed:** `7694b07273`.
- **After:** all three lanes pass.
